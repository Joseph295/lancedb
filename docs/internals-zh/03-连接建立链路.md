# 03 · 连接建立链路：从 `connect(uri)` 到一张能用的 `Table`

> **本篇追踪的链路**：`connect(uri).execute()` → `ConnectBuilder` → 选实现（`ListingDatabase` / `RemoteDatabase`）→ `Connection.open_table(name).execute()` → `Database::open_table` → `NativeTable::open` → 包成 `Table`
> **涉及源码**：`rust/lancedb/src/connection.rs`、`database.rs`、`database/listing.rs`、`table.rs`、`catalog/listing.rs`、`lib.rs`
> **前置阅读**：`00 全景地图`（餐厅各角色就位）、`01 Rust 垫脚石`（trait / `dyn` / `Arc` / async / 条件编译五节）、`02 三大基石`
> **留给哪篇深潜**：`09 Table 解剖（上）` 讲 `BaseTable` 合同与 `Table` 门面的全部方法；`10` 讲 `DatasetConsistencyWrapper`（金库保安）的锁与一致性。本篇只追到"表被打开、交到你手上"为止。

## 0. 这条链路要回答的问题

你写下这一行：

```rust
let db = lancedb::connect("/tmp/mydb").execute().await?;
let table = db.open_table("users").execute().await?;
```

两行代码，但中间发生了什么？**谁解析 URI？谁去对象存储里找那个目录？谁把磁盘上的 `users.lance` 加载成内存里的表对象？lancedb 自己写了多少，又转包给谁？** 这就是本篇要逐跳拆开的"请求的一生（连接版）"。

### 比喻锚点：进店、配服务员、点第一道菜

| 代码动作 | 餐厅比喻 |
|---|---|
| `connect("/tmp/mydb")` | 在门口拿一张**点菜单**（`ConnectBuilder`），还没进店、还没下单 |
| `.execute().await` | 把菜单交给前台。前台看你报的**桌号前缀**（URI 是不是 `db` 开头），决定带你去**本地店面**（`ListingDatabase`）还是**连锁云店**（`RemoteDatabase`），然后给你配一个固定的**服务员**（`Connection`） |
| `db.open_table("users")` | 你向服务员点菜。服务员**不亲自下厨**，而是复印一份**用工合同**（`Arc<dyn Database>`），交给一个跑堂（`OpenTableBuilder`） |
| `.execute().await` | 跑堂拿着合同去**后厨**（`Database` 实现），后厨到**仓库灶台**（lance）按编号 `users.lance` 取出一盘菜（`Dataset`），罩上**金库保安**（`DatasetConsistencyWrapper`），最后端给你一个**服务员**（`Table`） |

## §1 入口：`connect()` 与 `ConnectBuilder`

### 1.1 `connect` 从哪来？crate 根的重导出

`lib.rs:292`：

```rust
pub use connection::connect;                       // ① 把 connect 提到 crate 根
```

`connection` 模块在 `lib.rs:195` 用 `pub mod connection;` 暴露，配套还有 `pub use connection::Connection;`（`lib.rs:216`）和 `pub use table::Table;`（`lib.rs:219`）。

> **Rust 知识点：`pub use` = 重导出。** `connect` 真身住在 `connection` 模块里，但 `pub use` 把它"搬"到 crate 根，所以你写 `lancedb::connect` 而不是 `lancedb::connection::connect`。类比 Python 在 `__init__.py` 里 `from .connection import connect`——给用户一个干净的顶层 API，内部目录结构随便重构都不影响。

### 1.2 `connect()` 是同步的，且零 IO

`connection.rs:867`：

```rust
pub fn connect(uri: &str) -> ConnectBuilder {       // ① 注意: 不是 async!
    ConnectBuilder::new(uri)                          // ② 只造一个 Builder 就返回
}
```

**第一个反直觉点**：`connect` 不是 `async fn`，它**不连接任何东西**。它只是把你给的字符串包进一张"点菜单"。真正的网络/磁盘 IO 推迟到 `.execute().await`。

> **为什么要两段式（Builder + execute）？** 因为连接需要一堆可选配置：region、api_key、storage_options、读一致性间隔……如果都塞进 `connect()` 的参数列表，签名会爆炸。Builder 模式让你**链式勾选**，最后 `.execute()` 一次性触发。这套"Builder 攒参数 / execute 触发委托"的套路会在链路的**每一层**重复出现——记住它，后面就不用反复解释了。

### 1.3 `ConnectBuilder::new` 攒了什么

`connection.rs:640`：

```rust
pub fn new(uri: &str) -> Self {
    Self {
        request: ConnectRequest {
            uri: uri.to_string(),
            #[cfg(feature = "remote")]
            client_config: Default::default(),       // ① 只在启用 remote 时才有这个字段
            read_consistency_interval: None,
            options: HashMap::new(),                  // ② 所有配置先攒进一个 map
        },
        embedding_registry: None,                     // ③ 暂不指定, execute 时兜底
    }
}
```

`ConnectRequest` 的字段定义在 `connection.rs:603-630`：`uri: String`、`options: HashMap<String, String>`、`read_consistency_interval: Option<Duration>`，以及条件编译的 `client_config`。

注意**所有配置最终都化成 `HashMap<String, String>`**。你调 `.region("us-east-1")`（`connection.rs:678`）、`.storage_option(k, v)`（`connection.rs:764`）、`.database_options(&opts)`（`connection.rs:709`）本质都是往这个 map 里塞键值对。这是 lancedb 跨语言（Python/JS 也走这套）传配置的统一手法。

### 1.4 URI 的三种形态

`ConnectRequest.uri` 的文档注释（`connection.rs:606-610`）列出三类：

| URI 形态 | 例子 | 走哪条分支 | 谁来处理 |
|---|---|---|---|
| 本地文件系统路径 | `/path/to/db`、`./mydb` | 本地 | `ListingDatabase` |
| 云对象存储 | `s3://bucket/db`、`gs://bucket/db` | 本地（！） | `ListingDatabase` → lance 对象存储 |
| LanceDB Cloud | `db://dbname` | 远程 | `RemoteDatabase` |

⚠️ **注意第二行**：`s3://`/`gs://` 也走"本地"分支（`ListingDatabase`）。这里"本地"指的是"**直连对象存储、自己管理目录布局**"，与"经过 LanceDB Cloud 的 HTTP 服务"相对。`ListingDatabase` 一样能读写 S3——它把对象存储的活儿转包给 lance。下一节看分流逻辑就明白了。

## §2 `ConnectBuilder::execute`：分流 + 装箱 + 配服务员

`connection.rs:845`：

```rust
pub async fn execute(self) -> Result<Connection> {
    if self.request.uri.starts_with("db") {                                   // ①
        self.execute_remote()                                                 // ② 云店
    } else {
        let internal = Arc::new(                                              // ④ 装箱!
            ListingDatabase::connect_with_options(&self.request).await?       // ③ 本地店
        );
        Ok(Connection {
            internal,
            uri: self.request.uri,
            embedding_registry: self.embedding_registry
                .unwrap_or_else(|| Arc::new(MemoryRegistry::new())),          // ⑤ 兜底
        })
    }
}
```

逐点拆：

**① 分流就这一行 `starts_with("db")`。** 这是整个连接层的"策略选择点"。注意是 `"db"` 不是 `"db://"`——`db://`、`db+ssl://` 都命中。命中走云端，否则一律本地。

**② / ③ 两个分支都产出"实现了 `Database` 的东西"。** 这是多态的实战意义：`execute_remote` 返回的 `RemoteDatabase` 和 `connect_with_options` 返回的 `ListingDatabase` 是**两个完全不同的类型**，但对上层完全透明——它们都被塞进同一个 `Arc<dyn Database>` 槽位。

**④ `Arc::new(...)` 是"装箱成 trait object"的边界。** `connect_with_options` 返回的是具体类型 `ListingDatabase`（`Result<Self>`）。`Arc::new` 把它包成 `Arc<dyn Database>`——从这一刻起，上层只看见"一份用工合同"，看不见它是本地后厨还是云端后厨。**记住"谁负责装箱成 `dyn`"这条边界**：是 `execute`，不是 `connect_with_options`。

**⑤ `unwrap_or_else` 惰性兜底。** embedding registry 没指定时才造一个默认的 `MemoryRegistry`。

> **Rust 陷阱：`unwrap_or_else(|| ...)` vs `unwrap_or(...)`。** 两者都是"`Option` 为 `None` 时给默认值"。区别在 `unwrap_or_else` 接受一个**闭包**（`|| ...`），只有真的需要时才执行；`unwrap_or` 接受一个**已经算好的值**，无论用不用都先造出来。这里造 `MemoryRegistry` 有成本，所以用惰性版本——别每次连接都白造一个又扔掉。类比 JS 的 `x ?? expensive()` 写成函数式版本。

### 2.1 远程分支与条件编译

`execute_remote` 写了**两遍**，按 feature 二选一编译：

启用 remote 时（`connection.rs:806`）真正去连 `RemoteDatabase::try_new(...)`（`connection.rs:819`）。**没启用** remote 时（`connection.rs:836`）：

```rust
#[cfg(not(feature = "remote"))]
fn execute_remote(self) -> Result<Connection> {
    Err(Error::Runtime {
        message: "cannot connect to LanceDb Cloud unless the 'remote' feature is enabled"
            .to_string(),
    })
}
```

> **Rust 知识点：`#[cfg(feature = "remote")]` 条件编译。** 同名函数写两份，编译器按你有没有打开 `remote` feature 只挑一份编进去。类比 C 的 `#ifdef`。**这解释了一个常见坑**：有人编译后连 `db://` 报 "cannot connect ... unless the 'remote' feature is enabled"——不是 URI 错了，是编译时没启用 `remote` feature。贡献代码前，先看你改的函数有没有 `#[cfg(...)]` 帽子。

## §3 `Connection` 是什么：一个纯门面

`connection.rs:454`：

```rust
#[derive(Clone)]                                    // ① 可廉价克隆
pub struct Connection {
    uri: String,
    internal: Arc<dyn Database>,                     // ② 唯一干活的字段: 一份用工合同
    embedding_registry: Arc<dyn EmbeddingRegistry>,
}
```

`Connection` 是**服务员**：它自己几乎不存任何数据库状态，核心就是握着一个 `Arc<dyn Database>`（`internal`）。所有表操作的实现方式高度一致——**clone 这份合同，交给次级 Builder**：

| `Connection` 方法 | 行号 | 把 `internal.clone()` 交给谁 |
|---|---|---|
| `open_table(name)` | `connection.rs:551` | `OpenTableBuilder::new` |
| `create_table(name, data)` | `connection.rs:493` | `CreateTableBuilder::<true>::new` |
| `create_empty_table(name, schema)` | `connection.rs:531` | `CreateTableBuilder::<false>::new` |
| `table_names()` | `connection.rs:483` | `TableNamesBuilder::new` |

看 `open_table`（`connection.rs:551`）的实现就一目了然：

```rust
pub fn open_table(&self, name: impl Into<String>) -> OpenTableBuilder {
    OpenTableBuilder::new(
        self.internal.clone(),                       // ① clone 合同(只加引用计数)
        name.into(),
        self.embedding_registry.clone(),
    )
}
```

> **Rust 陷阱：`self.internal.clone()` 不复制数据库！** `internal` 是 `Arc<dyn Database>`——"引用计数的 trait object"。`.clone()` 只把引用计数 +1，**底层那个 `ListingDatabase` 一份都不复制**。所以一个 `Connection` 能廉价地 fan-out 给无数个 Builder，每个 Builder 都握着同一个后厨。类比带引用计数的智能指针（C++ `shared_ptr`），或 Python 对象的引用计数。这就是"服务员复印用工合同"的真相——复印的是合同（指针），不是后厨（数据）。

> **Rust 知识点：`impl Into<String>` 参数。** `name: impl Into<String>` 表示"任何能转成 `String` 的类型都收"——你传 `&str`、`String`、`&String` 都行。编译期会为每种实际类型生成专门代码（单态化）。类比鸭子类型，但有静态检查、零运行时开销。

## §4 `Database` trait：为什么连接层也要"用工合同"

`Connection` 把活儿委托给 `internal: Arc<dyn Database>`。那 `Database` 这份合同长什么样？`database.rs:150`：

```rust
#[async_trait::async_trait]                                                   // ①
pub trait Database:
    Send + Sync + std::any::Any + std::fmt::Debug + std::fmt::Display + 'static  // ②
{
    async fn table_names(&self, request: TableNamesRequest) -> Result<Vec<String>>;
    async fn create_table(&self, request: CreateTableRequest)
        -> Result<Arc<dyn BaseTable>>;                                       // ③ 产出另一份合同!
    async fn open_table(&self, request: OpenTableRequest)
        -> Result<Arc<dyn BaseTable>>;                                       // ③
    async fn rename_table(&self, old_name: &str, new_name: &str) -> Result<()>;
    async fn drop_table(&self, name: &str) -> Result<()>;
    async fn drop_all_tables(&self) -> Result<()>;
    fn as_any(&self) -> &dyn std::any::Any;
}
```

**① `#[async_trait::async_trait]`**：让 trait 里能写 `async fn`。

> **Rust 知识点：为什么 async trait 要靠宏？** Rust 原生 trait 当年不能直接写 `async fn`——因为 async 方法返回的 `Future` 大小不定，没法塞进 trait object 的 vtable（虚函数表）。`#[async_trait]` 宏在背后把 `async fn foo() -> T` 改写成 `fn foo() -> Box<dyn Future<Output = T>>`，绕开这个限制。**非 Rust 读者只需记住**：看见这个属性，就当 trait 里能写 async 方法。`Database`（`database.rs:150`）和 `BaseTable`（见 09 篇）都用了它。

**② supertrait 约束**：`Send + Sync`（线程安全通行证）、`Any`（支持向下转型）、`Debug + Display`（可打印）、`'static`（不借用短命引用）。意思是"想当 `Database`，先满足这五项"。

**③ 三层契约的核心**：`open_table`/`create_table` 返回的是 `Arc<dyn BaseTable>`——**又一份用工合同**！所以整条链路是**两次 trait object 跳转**：

```
Connection ──握──> Arc<dyn Database>  ──产出──> Arc<dyn BaseTable> ──被包进──> Table
  (服务员)          (后厨用工合同)              (表用工合同)            (服务员)
```

### 4.1 为什么连接层也要 trait？三种实现

`Database` 不是只有 `ListingDatabase` 一个实现。设计上至少有三类后厨：

| 实现 | 场景 | 对应"后厨" |
|---|---|---|
| `ListingDatabase` | 本地路径 / S3 / GS，自己管目录布局 | 本地店面 |
| `RemoteDatabase`（feature=remote） | LanceDB Cloud，走 HTTP | 连锁云店中央厨房 |
| （catalog 下的）`ListingDatabase` | catalog 子目录里的 database | 连锁分店 |

正因为有 trait 这层抽象，`Connection`（服务员）才能"不关心后厨是哪家"。你换 URI 前缀，`execute` 换一个实现塞进 `Arc<dyn Database>`，上层代码一个字都不用改。**这就是连接层也要 trait 的理由：屏蔽"本地 vs 云端"的差异。**

### 4.2 `DatabaseOptions`：强类型选项 ↔ map 的桥

`database.rs:33`：

```rust
pub trait DatabaseOptions {
    fn serialize_into_map(&self, map: &mut HashMap<String, String>);
}
```

还记得 §1.3 说"所有配置都化成 `HashMap<String, String>`"吗？`DatabaseOptions` 就是那座桥：你用强类型结构体配置，`serialize_into_map` 把它写进 map；连上去之后，`ListingDatabaseOptions::parse_from_map`（`listing.rs:69`，见下节）再反向从 map 解析回来。`ConnectBuilder::database_options`（`connection.rs:709`）就是调这个方法。

## §5 `ListingDatabase`：以"目录"为数据库

`ListingDatabase` 的核心思想，看它结构体上方的文档注释（`listing.rs:195-201`）：一个目录下，每个 `xxx.lance` 子目录就是一张表。`/data/table1.lance` + `/data/table2.lance` → 两张表 `table1`、`table2`。**"以目录为数据库，以 `.lance` 子目录为表"**——简单到不需要任何元数据服务。

### 5.1 连接：`connect_with_options`

`database/listing.rs:252`：

```rust
pub async fn connect_with_options(request: &ConnectRequest) -> Result<Self> {
    let uri = &request.uri;
    let parse_res = url::Url::parse(uri);                                     // ①
    let options = ListingDatabaseOptions::parse_from_map(&request.options)?;  // ② map→强类型
    match parse_res {
        Ok(url) if url.scheme().len() == 1 && cfg!(windows) => { /* C:\ 盘符 */ }  // ③
        Ok(mut url) => { /* 正常 URL: 过滤 query param, 建对象存储 */ }            // ④
        Err(_) => { /* 解析失败当本地路径 */ }                                   // ⑤
    }
}
```

三分支（`listing.rs:259-336`）：

- **③ Windows 盘符**：`C:\foo` 会被 url 解析成 scheme 长度为 1（`c:`），特判走 `open_path`。
- **④ 正常 URL 分支**（`listing.rs:268`）：遍历 query 参数，抽出 lancedb 私有的 `engine`（`listing.rs:277`）和 `mirroredStore`（`listing.rs:279`），**把它们从 URL 里过滤掉**（`listing.rs:293`），剩下的才传给 lance。然后调对象存储工厂（见下）。
- **⑤ 解析失败**（`Err`）：当成本地文件路径处理。

**④ 分支里最关键的一跳**——`listing.rs:321`：

```rust
let (object_store, base_path) =
    ObjectStore::from_uri_and_params(registry, &plain_uri, &os_params).await?;  // 委托 lance!
```

`ObjectStore::from_uri_and_params` 是 **lance** 提供的对象存储工厂。lancedb **自己不挖仓库**——S3 客户端、GCS 客户端、本地文件系统的所有适配，全是 lance 早就建好的。lancedb 只负责：解析 URL、过滤私有 query param、把 storage_options 透传进去。这是"**组装而非重造**"最干净的一处铁证。

连上后，`ListingDatabase` 结构体（`listing.rs:203-220`）把这些填好备用：`object_store`、`base_path`、`store_wrapper`、`read_consistency_interval`、`storage_options`、`new_table_config`。**注意 `storage_options` 被存了下来**——开表/建表时会"继承"给每张表（见 §5.3）。

> **Rust 陷阱：`.context(CreateDirSnafu { path })?` 是什么？** `listing.rs:324` 出现这种写法。这是 `snafu` 错误库的用法：给底层的 `io::Error` **附加上下文**（"是在创建目录 path 时出错的"），再用 `?` 向上抛。`?` 运算符 = "出错就提前 `return Err`，否则取出 `Ok` 里的值"。类比 Go 的 `if err != nil { return err }`，但浓缩成一个问号。

> **Rust 知识点：返回 `Result<Self>` 的关联函数。** `connect_with_options` 返回 `Result<Self>`（`Self` = `ListingDatabase`），造的是**具体类型**。它**不负责**装箱成 `dyn Database`——那是上层 `execute`（`connection.rs:849`）用 `Arc::new(...)` 干的。再次强调这条边界：**底层造具体类型，上层负责装箱成 trait object**。

### 5.2 列表：`table_names` 怎么扫对象存储

`database/listing.rs:448`：

```rust
async fn table_names(&self, request: TableNamesRequest) -> Result<Vec<String>> {
    let mut f = self.object_store
        .read_dir(self.base_path.clone()).await?                             // ① 列目录
        .iter().map(Path::new)
        .filter(|path| {                                                     // ② 只留 .lance
            path.extension().and_then(|e| e.to_str())
                .map(|e| e == LANCE_EXTENSION).unwrap_or(false)
        })
        .filter_map(|p| p.file_stem().and_then(|s| s.to_str().map(String::from)))  // ③ 去扩展名
        .collect::<Vec<String>>();
    f.sort();                                                                // ④ 字典序
    if let Some(start_after) = request.start_after { /* 分页 */ }            // ⑤
    if let Some(limit) = request.limit { f.truncate(limit as usize); }
    Ok(f)
}
```

逻辑朴素到不能再朴素：**`read_dir` 列目录 → 过滤扩展名 `== "lance"`（`LANCE_EXTENSION`，`listing.rs:240`）→ 取 file_stem（`users.lance` → `users`）→ 排序 → 按 `start_after`/`limit` 分页**。没有数据库元表，目录列表就是表列表。这就是"以目录为数据库"在读路径上的体现。

它的入口是 `Connection::table_names`（`connection.rs:483`），经 `TableNamesBuilder::execute`（`connection.rs:70`）`self.parent.clone().table_names(...)` 委托到这里——又一次"Builder execute 委托回 Database trait"。

### 5.3 开表：`open_table` 逐跳

`database/listing.rs:564`：

```rust

            storage_options.insert(key.clone(), value.clone());
        }

        NativeTable::open_with_params(                                       // ④ 委托后厨!
            &table_uri, &request.name, self.store_wrapper.clone(),
            Some(read_params), self.read_consistency_interval,
        ).await?,
    );
    Ok(native_table)                                                         // ⑤ Arc<dyn BaseTable>
}
```

**① `table_uri("users")` 拼路径**——`listing.rs:390`：

```rust

    let table_uri = path.join(format!("{}.{}", name, LANCE_FILE_EXTENSION)); // users → users.lance
```

`/tmp/mydb` + `users` → `/tmp/mydb/users.lance`。**注意这里的常量是 `LANCE_FILE_EXTENSION`（值也是 `"lance"`，`listing.rs:30`），和 §5.2 列表用的 `LANCE_EXTENSION`（`listing.rs:240`）是两个同值常量**——读源码时别看花眼。

**② 继承 storage_options**：连接时存下的 `self.storage_options`，在开表时补进 read params（表自己没指定的键才补）。"连接级配置下沉到表级"——这就是为什么连接对象 = 攒好的配置 + 一个对象存储句柄。

**④ 委托给后厨 `NativeTable::open_with_params`**，包成 `Arc`（`listing.rs:595`）返回 `Arc<dyn BaseTable>`。

### 5.4 最后一跳：`NativeTable::open_with_params` → lance

`table.rs:1233`：

```rust
pub async fn open_with_params(
    uri: &str, name: &str,
    write_store_wrapper: Option<Arc<dyn WrappingObjectStore>>,
    params: Option<ReadParams>,
    read_consistency_interval: Option<std::time::Duration>,
) -> Result<Self> {
    let params = params.unwrap_or_default();
    let params = match write_store_wrapper.clone() { ... };                   // 打补丁
    let dataset = DatasetBuilder::from_uri(uri)                               // ① 委托 lance!
        .with_read_params(params)
        .load().await
        .map_err(|e| match e {                                               // ② 翻译错误!
            lance::Error::DatasetNotFound { .. } => Error::TableNotFound {
                name: name.to_string(),
            },
            source => Error::Lance { source },
        })?;
    let dataset = DatasetConsistencyWrapper::new_latest(dataset, read_consistency_interval);  // ③ 罩保安
    Ok(Self { name: name.to_string(), uri: uri.to_string(), dataset, read_consistency_interval })
}
```

**① 真正加载数据集的活儿，转包给 lance 的 `DatasetBuilder::from_uri(uri).load()`。** 跑堂到仓库灶台（lance）按编号 `users.lance` 取出一盘菜（`Dataset`）。lancedb 自己没写任何"读取 manifest、解析列存文件"的代码——全是 lance 的。

**② 错误翻译边界（`table.rs:1252`）。** lance 报 `DatasetNotFound`，lancedb 把它**翻译**成自己词汇里的 `TableNotFound`。这是分层 API 的礼貌：每跨一层，就把下层的错误翻成本层用户认得的话。用户调 `open_table` 找不到表，应该收到 "TableNotFound" 而不是 "DatasetNotFound"——后者会泄露"表底下其实是个 lance dataset"的实现细节。

**③ 罩上金库保安（`table.rs:1258`）。** `DatasetConsistencyWrapper::new_latest` 把裸 `Dataset` 包一层，负责读一致性/版本控制。它的内部机制留给 `10` 篇深潜——本篇只需知道"取出的菜会被罩一层保安再端出去"。

至此 `Arc<dyn BaseTable>` 诞生，沿着调用栈一路返回到 `OpenTableBuilder::execute`（`connection.rs:445`），被 `Table::new_with_embedding_registry`（`table.rs:569`）包成 `Table` 服务员，交到你手上。**开表链路闭环。**

## §6 建表链路：`const generics` 怎么区分有无初始数据

开表只读，建表要写。`create_table` 链路结构与开表同构（Builder → execute → Database → NativeTable），但有一个值得专门讲的 Rust 招法：**用常量泛型 `CreateTableBuilder<const HAS_DATA: bool>` 在编译期区分"有初始数据"和"空表"两条路径。**

`connection.rs:92`：

```rust
pub struct CreateTableBuilder<const HAS_DATA: bool> {                        // ① 布尔进类型系统
    parent: Arc<dyn Database>,
    embeddings: Vec<(EmbeddingDefinition, Arc<dyn EmbeddingFunction>)>,
    embedding_registry: Arc<dyn EmbeddingRegistry>,
    request: CreateTableRequest,
    data: CreateTableBuilderInitialData,
}
```

两个入口产出两个**不同类型**：

| `Connection` 入口 | 行号 | 返回类型 | 含义 |
|---|---|---|---|
| `create_table(name, data)` | `connection.rs:493` | `CreateTableBuilder<true>` | 有初始数据 |
| `create_empty_table(name, schema)` | `connection.rs:531` | `CreateTableBuilder<false>` | 空表（只给 schema） |

关键在于：**两个类型的方法集不同**。`new`/`new_streaming`/`into_request` 只在 `impl CreateTableBuilder<true>`（`connection.rs:103`）里有；`<false>` 的 `new`（`connection.rs:190`）走另一套。各自有独立的 `execute`：

```rust
// connection.rs:143  —— impl CreateTableBuilder<true>
pub async fn execute(self) -> Result<Table> {
    let request = self.into_request()?;                  // ① 把攒的数据塞进 request
    Ok(Table::new_with_embedding_registry(
        parent.create_table(request).await?,             // ② 委托 Database::create_table
        embedding_registry,
    ))
}

// connection.rs:207  —— impl CreateTableBuilder<false>
pub async fn execute(self) -> Result<Table> {
    Ok(Table::new(
        self.parent.clone().create_table(self.request).await?,  // 同样委托, 但无 embedding 路径
    ))
}
```

两个 `execute` 殊途同归，都委托回 `Database::create_table`（`database.rs:157`）。`ListingDatabase` 的实现（`listing.rs:478`）继承 storage_options、设置 write params，最后委托 `NativeTable::create`（`listing.rs:525`）——与开表对称的"组装而非重造"。

> **Rust 知识点：`const HAS_DATA: bool` 常量泛型。** 普通泛型是"类型参数"（`Vec<T>`），常量泛型是把一个**值**（这里是布尔）塞进类型系统。`CreateTableBuilder<true>` 和 `CreateTableBuilder<false>` 在编译期是**两个不同的类型**，能各自拥有不同的方法、被编译器分别检查。好处：编译期就杜绝"建空表却想塞数据"的误用——零运行时成本。类比 TypeScript 用字面量类型 `Builder<true>` 做条件，但 Rust 是真·编译期单态化。共享的方法（如 `.mode()`、`.write_options()`）放在 `impl<const HAS_DATA: bool> CreateTableBuilder<HAS_DATA>`（`connection.rs:214`）里，对两个类型都生效。

## §6.5 旁支：Catalog —— 可选的第四层容器

主线之外还有一条**平行入口**：`connect_catalog`。Catalog 是比 database 更高一层的容器，形成**三级嵌套**：

```
catalog（连锁集团总部） → database（分店） → table（菜品）
```

入口 `connect_catalog(uri)`（`connection.rs:910`）返回 `CatalogConnectBuilder`，它的 `execute`（`connection.rs:897`）：

```rust
pub async fn execute(self) -> Result<Arc<ListingCatalog>> {                  // ① 注意返回类型!
    let catalog = ListingCatalog::connect(&self.request).await?;
    Ok(Arc::new(catalog))
}
```

**① 对比主线**：`ConnectBuilder::execute` 返回 `Connection`（内部藏 `Arc<dyn Database>` trait object），而 `CatalogConnectBuilder::execute` 返回的是 **`Arc<ListingCatalog>` 具体类型**——两条入口设计风格略有不同。

`Catalog` trait（`catalog.rs:68`）约束 `Send + Sync + Debug + 'static`，方法含 `database_names`（`catalog.rs:70`）、`open_database`（`catalog.rs:76`）、`create_database`。`ListingCatalog::connect`（`catalog/listing.rs:121`）与 `ListingDatabase::connect_with_options` **几乎同构**——一样 `url::Url::parse` + `ObjectStore::from_uri_and_params`，只是把"以 `.lance` 子目录为表"换成"以子目录为 database"。

最妙的是**嵌套委托**：`ListingCatalog::open_database`（`catalog/listing.rs:231`）和 `create_database`（`catalog/listing.rs:186`）内部，检查路径后**构造一个 `ConnectRequest` 再回头调 `ListingDatabase::connect_with_options`**（`catalog/listing.rs:227` / `:254`）：

```rust
Ok(Arc::new(
    ListingDatabase::connect_with_options(&connect_request).await?,          // catalog 委托 database 连接逻辑
))
```

> **比喻**：catalog 是有多家分店的连锁集团总部。`open_database` 就是"进某家分店"——而进店后，照样要在分店门口拿一张点菜单（`ConnectRequest`），走一遍 `ListingDatabase` 的连接流程。**"打开一个 database 等于在 catalog 子目录里建一个连接。"** 复用得彻底。

三个 ★ 委托点（lance 对象存储、lance dataset 加载、ConsistencyWrapper）+ 一个 ★ 错误翻译点，构成了 lancedb 在这条链路上**全部的"自有逻辑"**。其余的解析、分流、拼路径、装箱，都是"编排"。


## 小结 & 下一篇

**这条链路最值得带走的四句话：**

1. **两段式 Builder 贯穿全程**：`connect`/`open_table`/`create_table` 都先返回一张"点菜单"，`.execute().await` 才真正碰 IO 并委托下去。
2. **`Connection` 是纯门面**：自己不干活，握一个 `Arc<dyn Database>`，所有表操作都 `clone` 这份合同 fan-out 给次级 Builder。
3. **三层契约 + 两次 trait object 跳转**：`connect` 产出 `Arc<dyn Database>` → `Database` 产出 `Arc<dyn BaseTable>` → `Table` 包装它。trait 让"本地 vs 云端"对上层透明。
4. **组装而非重造**：lancedb 只解析 URI、选实现、拼 `name.lance` 路径、翻译错误；开仓库（`ObjectStore::from_uri_and_params`）和取菜（`DatasetBuilder::from_uri`）全转包给 lance。
