# 06 · 查询链路：一次 `query().execute()` 的一生

> **本篇追踪的链路**：`Table::query()` / `Table::vector_search()` → `Query` / `VectorQuery`（Builder）→ 链式配置 → `ExecutableQuery::execute()` → `BaseTable::create_plan()` → `NativeTable` 用 lance `Scanner` 装配 DataFusion `ExecutionPlan` → `execute_plan` 驱动 → `RecordBatch` 流
>
> **涉及源码**：`rust/lancedb/src/query.rs`（Builder 三件套 + 三层 trait）、`rust/lancedb/src/table.rs`（门面、`BaseTable` 契约、`NativeTable::create_plan`、`multi_vector_plan`）
>
> **前置阅读**：`00 全景地图`、`01 Rust 垫脚石`（trait / `dyn` / `Arc` / async 四节）、`02 三大基石`（Arrow / DataFusion / lance）、`09 Table 解剖（上）`（`BaseTable` 合同、`Table` 门面、`NativeTable` 骨架）。本篇所有论断都带真实行号，形如 `query.rs:734`。
>
> **留给哪篇深潜**：混合搜索（FTS+向量）的 reranker 合并细节、`DatasetConsistencyWrapper` 的锁与一致性（→ `10 Table 解剖（下）`）。

## 0. 这条链路要回答的问题

你写下这一行：

```rust
let stream = table.query().limit(10).only_if("price > 5").execute().await?;
```

或者这一行向量搜索：

```rust
let stream = table.vector_search(vec![0.1, 0.2, 0.3])?.nprobes(20).execute().await?;
```

从这行代码出发，到底发生了什么？谁把 `limit(10)` 这样的"勾选"记下来？`execute()` 是不是立刻就开始算了？最后那个 `stream` 里的数据是从哪冒出来的？

**这一篇就是把这条链路逐跳拆开**，告诉你每一跳"做了什么、委托给谁、在第几行"。

读完你会建立一个核心心智模型——**三跳心法**：

```
   服务员                点菜单                  后厨
（Table 门面）  →   （Query/VectorQuery）  →   （NativeTable）
 只递菜单不做菜      记下你的勾选，喊            把菜单翻译成对
                    execute 时折好塞回         lance 灶台的吩咐
```

> **比喻总钥匙**（延续 `09` 的比喻家族）：
> - **服务员 `Table`**：只负责把"后厨入口卡"（`Arc<dyn BaseTable>`）塞进点菜单，自己一点 IO 都不做。
> - **点菜单 `Query` / `VectorQuery`（Builder）**：把你勾的 `limit` / `filter` / `nprobes` 记在一张表格（`QueryRequest`）里。
> - **后厨 `NativeTable`**：`create_plan` 是"照单备菜"——不发明菜谱，只把菜单每一项翻译成对**仓库灶台 lance `Scanner`** 的一句吩咐，最后让灶台出一张**传菜工单**（DataFusion `ExecutionPlan`）。
> - **传菜流水线 DataFusion**：拿到工单才真正开动，把一盘盘**餐盘（Arrow `RecordBatch`）**端出来。
>
> 记住一句话:**`execute()` 之前一切都只是写工单，没真做菜。**

## 1. 入口：`Table::query()` 与 `vector_search()`

链路的起点是门面 `Table` 上的两个方法。先看 `Table` 的字段（`table.rs:500-503`），呼应 `09 §2`：

```rust
#[derive(Clone)]
pub struct Table {
    inner: Arc<dyn BaseTable>,                 // ① 后厨入口卡（合同指针）
    embedding_registry: Arc<dyn EmbeddingRegistry>,
}
```

`Table` 自己不存任何数据，只握着一张"后厨入口卡" `inner`。

### 1.1 `query()`：造一张空白点菜单

`table.rs:941-943`：

```rust
pub fn query(&self) -> Query {                 // ① 注意:不是 async
    Query::new(self.inner.clone())             // ② 只把后厨入口卡 clone 一份塞进点菜单
}
```

这一跳**没有任何 IO**。它做的全部事情就是：把 `self.inner`（`Arc<dyn BaseTable>`）clone 一份，交给 `Query::new` 构造一张空白点菜单。

> **Rust 知识点：`self.inner.clone()` 不是深拷贝**。`inner` 是 `Arc`（原子引用计数指针），`clone` 只让计数 +1，廉价得很——**不是复制整张表**。非 Rust 读者别被满屏的 `.clone()` 吓到，它在这里只是"再印一张遥控器壳，背后还是同一台电视"。（类比 Java 的接口引用 + 自动 GC，但这里靠计数而非 GC。）

> **Rust 知识点：为什么不是 `async`？** 因为它不碰磁盘/网络，只在内存里 `new` 一个结构体。返回值 `Query` 是个 Builder——真正的执行被推迟到你调 `.execute()`。这就是 `09 §2.2` 讲过的"Builder 工厂型"方法。

### 1.2 `vector_search()`：便捷封装

`table.rs:950-952`：

```rust
pub fn vector_search(&self, query: impl IntoQueryVector) -> Result<VectorQuery> {
    self.query().nearest_to(query)            // 先建普通 Query，再升级成 VectorQuery
}
```

源码注释（`table.rs:947-949`）已经挑明：`vector_search(v)` **就等于** `query().nearest_to(v)`。它只是个便捷封装，省你一次 `nearest_to`。所以两条入口路径在第 1 跳之后就汇合了：先有一张普通点菜单 `Query`，向量搜索再把它升级成 `VectorQuery`（见 §3）。

> **Rust 陷阱：`impl IntoQueryVector` 作参数**（`table.rs:950`）。这是"argument-position impl Trait"，等价于一个静态泛型：编译期会为每种实参类型（`Vec<f32>`、`&[f32]`、Arrow `Array`…）单独生成一份代码。它让你既能传原生 `Vec<f32>`，也能传 Arrow 数组，各自有不同的 `to_query_vector` 实现（`query.rs:114`）。Python/JS 里最接近的是"鸭子类型 + 多态函数"，但这里是编译期零成本的。

**本跳小结**：门面只是"递菜单"，把后厨入口卡塞进 Builder 就走人。下一跳进点菜单本身。

## 2. 三层查询 trait：各管一摊

在进入参数装配之前，必须先认清 Builder 背后的**三层 trait 分工**。这是整个 `query.rs` 的骨架，也是非 Rust 读者最容易迷路的地方。

| Trait | 定义处 | 管什么 | 一句话 |
|---|---|---|---|
| `HasQuery` | `query.rs:453` | "我持有一张请求表格" | 只要求一个方法：`mut_query() -> &mut QueryRequest` |
| `QueryBase` | `query.rs`（`impl` 在 :457） | 通用配置 setter | `limit` / `offset` / `only_if` / `select` / `with_row_id` … |
| `ExecutableQuery` | `query.rs:546` | "我能被执行" | `create_plan` / `execute` / `execute_with_options` |

它们的关系是：**`Query` 和 `VectorQuery` 各自实现 `HasQuery` 和 `ExecutableQuery`；而 `QueryBase` 的全部 setter 通过一行"批量实现"白送给所有 `HasQuery` 类型。**

### 2.1 `HasQuery`：只要求"交出可变表格"

`query.rs:453-455`：

```rust
pub trait HasQuery {
    fn mut_query(&mut self) -> &mut QueryRequest;   // 交出底层请求表格的可变引用
}
```

`Query` 的实现直接返回自己的 `request`（`query.rs:755-759`）：

```rust
impl HasQuery for Query {
    fn mut_query(&mut self) -> &mut QueryRequest {
        &mut self.request
    }
}
```

`VectorQuery` 的实现则返回**嵌套在向量请求里的那张基础表格** `request.base`（`query.rs:1134-1138`）：

```rust
impl HasQuery for VectorQuery {
    fn mut_query(&mut self) -> &mut QueryRequest {
        &mut self.request.base                       // 注意:.base
    }
}
```

这个 `.base` 的小差别是后面"两个 Builder 共用一套 setter"的关键——它们都能交出一张 `QueryRequest`，只是位置不同。

### 2.2 `QueryBase`：一处实现，两个 Builder 通吃

`query.rs:457-510` 是全篇最妙的一段：

```rust
impl<T: HasQuery> QueryBase for T {                  // ① 对所有实现了 HasQuery 的 T 统一实现
    fn limit(mut self, limit: usize) -> Self {       // ② mut self:消费自身的链式 setter
        self.mut_query().limit = Some(limit);        // ③ 经 mut_query() 拿到表格，写一个字段
        self                                         // ④ 把自己交还，支持链式
    }
    fn offset(mut self, offset: usize) -> Self {
        self.mut_query().offset = Some(offset);
        self
    }
    fn only_if(mut self, filter: impl AsRef<str>) -> Self {
        self.mut_query().filter = Some(QueryFilter::Sql(filter.as_ref().to_string()));
        self
    }
    // …… select / fast_search / postfilter / with_row_id / rerank / norm 同款
}
```

> **Rust 陷阱：blanket impl（一揽子实现）**。`impl<T: HasQuery> QueryBase for T` 的意思是"**为所有满足 `HasQuery` 约束的类型 `T` 统一实现 `QueryBase`**"。于是 `Query` 和 `VectorQuery` 只要各自实现了 `HasQuery`（§2.1），就**免费获得**全部 `QueryBase` setter，一行不用重写。
>
> Python/JS 没有等价物，最接近的是 mixin，但这是**编译期零成本**的。**比喻**：给所有"有可变菜单"的对象批量装上同一套点菜按钮。

> **Rust 陷阱：`mut self) -> Self`（消费自身）**（`query.rs:458`）。每个 setter 拿走 `self` 的**所有权**，改一个字段，再把自己**整个交还**。所以你能 `.limit(10).offset(1).only_if("…")` 一路串下去。代价是：调用一次后原变量被"移动"走、不能再用。这是 Rust builder 的标准形态（`09 §3.1` 讲过 `AddDataBuilder` 也是这套）。

> **`full_text_search` 的小心机**（`query.rs:473-479`）：它在设置 FTS 时，如果 `limit` 还没设，会自动补上 `DEFAULT_TOP_K`（=10，`query.rs:34`）。原因是全文检索和向量检索一样，不该默认返回全表。

### 2.3 `ExecutableQuery`：能下单的能力

`query.rs:546-583` 定义了"可执行"的契约，三个核心方法：

```rust
pub trait ExecutableQuery {
    fn create_plan(&self, options: QueryExecutionOptions)            // ① 只编计划，不执行
        -> impl Future<Output = Result<Arc<dyn ExecutionPlan>>> + Send;

    fn execute(&self)                                               // ② 默认方法:用默认选项执行
        -> impl Future<Output = Result<SendableRecordBatchStream>> + Send {
        self.execute_with_options(QueryExecutionOptions::default())
    }

    fn execute_with_options(&self, options: QueryExecutionOptions)  // ③ 真正执行
        -> impl Future<Output = Result<SendableRecordBatchStream>> + Send;
}
```

注意 `execute()`（`query.rs:559-561`）是**默认方法**：它什么都不干，直接转调 `execute_with_options(QueryExecutionOptions::default())`。默认选项里 `max_batch_length = 1024`、`timeout = None`（`query.rs:533-540`）。

> **Rust 陷阱：`async fn ... -> impl Future<...> + Send` 与到处的 `.await`**。这是协程：`.await` 处让出执行权（而非阻塞线程）。`create_plan` 返回的 `Arc<dyn ExecutionPlan>` 是个**惰性算子树**——拿到它时什么都还没算。`execute_with_options` 才会真正驱动它。所以"编计划"和"执行计划"在这里是两个分开的动作，这点贯穿全篇。

**本跳小结**：`HasQuery` 提供表格、`QueryBase` 提供 setter、`ExecutableQuery` 提供下单。下一跳看 `Query` 怎么升级成 `VectorQuery`。

## 3. 升级：`Query` → `VectorQuery`（`nearest_to`）

普通扫描用 `Query`，向量搜索用 `VectorQuery`。从前者变后者的唯一入口是 `nearest_to`。

`query.rs:734-744`：

```rust
pub fn nearest_to(self, vector: impl IntoQueryVector) -> Result<VectorQuery> {
    let mut vector_query = self.into_vector();                          // ① Query 包成 VectorQuery
    let query_vector = vector.to_query_vector(&DataType::Float32, "default")?;  // ② 原生向量 → Arrow Array
    vector_query.request.query_vector.push(query_vector);              // ③ 压入向量列表

    if vector_query.request.base.limit.is_none() {                    // ④ 向量查询缺省补 limit
        vector_query.request.base.limit = Some(DEFAULT_TOP_K);        //    DEFAULT_TOP_K = 10  query.rs:34
    }

    Ok(vector_query)
}
```

逐步拆：

- **① `into_vector()`**（`query.rs:696-698`）转调 `VectorQuery::new(self)`（`query.rs:858-863`）。`VectorQuery::new` 把原 `Query` 的 `parent` 原样搬过来，再用 `VectorQueryRequest::from_plain_query(base.request)` 把原来的普通请求"升格"成向量请求（`query.rs:834-839`）——后者把普通 `QueryRequest` 塞进 `base` 字段，其余向量专属字段取默认。
- **② `to_query_vector`**（`IntoQueryVector` trait，`query.rs:114`）把用户的原生 `Vec<f32>` 转成 `Arc<dyn Array>`（Arrow 数组）。这里默认 `data_type` 传 `DataType::Float32`、embedding 模型标签传 `"default"`（`query.rs:736`）。
- **③** 把转好的 Arrow 向量 `push` 进 `query_vector`——注意它是个 **`Vec`**（向量列表），为多向量查询（§6）留好了位置。
- **④** 向量查询若没设 `limit`，补上 `DEFAULT_TOP_K = 10`。这是为了避免"对全表逐个算距离再排序"这种灾难。

> **对比记忆**：普通 `Query` **不**自动补 `limit`（`QueryRequest::default()` 里 `limit: None`，`query.rs:653`），所以纯扫描可以返回全表；而向量/FTS 查询都会补 10。

升级后，`VectorQuery` 同样实现了 `HasQuery`（§2.1）和 `ExecutableQuery`（§5），所以你能继续 `.nprobes(20).limit(5)` 链式配置——通用 setter 来自 `QueryBase`，向量专属 setter（`nprobes`/`column`/`ef`/`bypass_vector_index`…）则定义在 `impl VectorQuery` 块里。

**本跳小结**：`nearest_to` 把点菜单"换成大号的"，并把你的查询向量翻译成 Arrow 餐盘格式压进去。下一跳看这张表格到底记了什么。

## 4. 表格里装了什么：`QueryRequest` 与 `VectorQueryRequest`

Builder 的所有"勾选"最终都落在两个请求结构体里。**Builder 本身不存逻辑，只是这两张表格的填写器。**

### 4.1 `QueryRequest`：普通查询的 10 个字段

`query.rs:611-648`：

```rust
#[derive(Debug, Clone)]
pub struct QueryRequest {
    pub limit: Option<usize>,                       // 返回行数上限
    pub offset: Option<usize>,                      // 跳过前几行
    pub filter: Option<QueryFilter>,                // 过滤条件(SQL / Substrait / DataFusion 表达式)
    pub full_text_search: Option<FullTextSearchQuery>,  // 全文检索
    pub select: Select,                             // 列投影(All / Columns / Dynamic)
    pub fast_search: bool,                          // 只搜已索引数据(更快但可能漏新数据)
    pub with_row_id: bool,                          // 是否返回 _rowid 元列
    pub prefilter: bool,                            // 先过滤再搜(true) vs 搜完再过滤
    pub reranker: Option<Arc<dyn Reranker>>,        // 混合搜索重排器
    pub norm: Option<NormalizeMethod>,              // 混合搜索分数归一化方式
}
```

默认值（`query.rs:650-665`）里值得记的：`prefilter: true`（默认先过滤后搜，召回更准）、`select: Select::All`、其余多为 `None`/`false`。

### 4.2 `VectorQueryRequest`：在基础上叠向量专属字段

`query.rs:790-814`：

```rust
#[derive(Debug, Clone)]
pub struct VectorQueryRequest {
    pub base: QueryRequest,                  // ★ 嵌套基础请求(所以 mut_query 返回 &mut base)
    pub column: Option<String>,              // 在哪个向量列上搜(None 则自动推断)
    pub query_vector: Vec<Arc<dyn Array>>,   // 查询向量(Vec → 支持多向量)
    pub nprobes: usize,                      // IVF 搜索的分区数(精度/速度旋钮)
    pub lower_bound: Option<f32>,            // 距离下界
    pub upper_bound: Option<f32>,            // 距离上界
    pub ef: Option<usize>,                   // HNSW 候选数
    pub refine_factor: Option<u32>,          // 精排阶段多取几倍候选
    pub distance_type: Option<DistanceType>, // 距离度量(L2/Cosine/Dot…)
    pub use_index: bool,                     // false 则强制暴力(flat)搜索
}
```

默认值（`query.rs:816-830`）的两个关键缺省：**`nprobes: 20`**、**`use_index: true`**。即默认走索引、探测 20 个分区。

> **设计要点：为什么 `VectorQueryRequest` 把 `QueryRequest` 嵌在 `base` 里，而不是平铺所有字段？** 因为这样向量请求天然"包含"普通请求的一切能力（过滤、投影、分页都复用），向量专属字段只是在外层叠加。这也正是 §2.1 里 `VectorQuery::mut_query` 返回 `&mut self.request.base` 的原因——通用 setter 写的就是这张内层表格。**组装而非重造**，连数据结构都遵循这个哲学。

### 4.3 `from_plain_query`：把普通请求"升格"

`query.rs:833-839`：

```rust
impl VectorQueryRequest {
    pub fn from_plain_query(query: QueryRequest) -> Self {
        Self {
            base: query,                 // 普通请求塞进 base
            ..Default::default()         // 其余向量字段全取默认(nprobes=20, use_index=true…)
        }
    }
}
```

> **Rust 知识点：`..Default::default()`（struct update 语法）**。意思是"剩下没写的字段全用 `Default::default()` 的值填"。这是 Rust 表达"只指定我关心的字段、其余走默认"的惯用法，省去逐字段赋值。

这个方法在两处出现：`nearest_to` 升级时（§3），以及后厨 `create_plan` 开头统一请求时（§5.1）。记住它，下一跳就懂为什么普通查询和向量查询能共用一段后厨代码。

**本跳小结**：所有参数都静静躺在 `QueryRequest` / `VectorQueryRequest` 里，等着被翻译。下一跳——点菜单喊 `execute`，把表格折进信封递回后厨。

## 5. 执行：`execute` → `create_plan` → DataFusion `ExecutionPlan`

这是全篇的主跳，分三段：Builder 怎么委托回后厨、后厨怎么把表格翻译成 lance `Scanner` 调用、最后怎么产出 DataFusion 物理计划。

### 5.1 Builder 端：把自己折进 `AnyQuery` 信封，委托回 `parent`

以 `VectorQuery` 为例。`execute()`（默认方法 `query.rs:559`）转到 `execute_with_options`（`query.rs:1109-1121`）：

```rust
async fn execute_with_options(&self, options: QueryExecutionOptions)
```

主路 `inner_execute_with_options`（`query.rs:1088-1100`）：

```rust
async fn inner_execute_with_options(&self, options: QueryExecutionOptions)
    -> Result<SendableRecordBatchStream> {
    let plan = self.create_plan(options.clone()).await?;     // ① 先编计划
    let inner = execute_plan(plan, Default::default())?;     // ② 再驱动执行(lance_datafusion 提供)

```

而 `create_plan`（`query.rs:1103-1107`）做的事情极简——**把请求折进 `AnyQuery` 信封，委托回 `parent`**：

```rust
impl ExecutableQuery for VectorQuery {
    async fn create_plan(&self, options: QueryExecutionOptions) -> Result<Arc<dyn ExecutionPlan>> {
        let query = AnyQuery::VectorQuery(self.request.clone());   // ① 折进信封
        self.parent.clone().create_plan(&query, options).await    // ② 委托回 Arc<dyn BaseTable>
    }
}
```

普通 `Query` 完全对称（`query.rs:761-765` / `767-775`）：`create_plan` 包成 `AnyQuery::Query(...)` 委托 `parent.create_plan`，`execute_with_options` 包成 `AnyQuery::Query(...)` 委托 `parent.query`。

> **`AnyQuery` 是 Builder 与后厨之间的传输契约**（`table.rs:398-401`）：
> ```rust
> pub enum AnyQuery {
>     Query(QueryRequest),
>     VectorQuery(VectorQueryRequest),
> }
> ```
> 它是一个枚举（携带数据的 union）。点菜单把自己折进这个标准信封，后厨用模式匹配拆开看是哪种。

> **Rust 陷阱：`self.parent.clone()`** 又来了——clone 的是 `Arc`（计数 +1，廉价），不是整张表。`parent` 字段类型是 `Arc<dyn BaseTable>`（`query.rs:853`），即"实现了 `BaseTable` 合同的某个后厨"。运行时动态分发，到底是 `NativeTable` 还是 `RemoteTable`，编译期并不知道（`09 §1` 讲的 trait object 多态）。

### 5.2 契约端：`BaseTable::create_plan` 抽象方法

委托的落点是合同上的抽象方法（`table.rs:418-422`）：

### 5.3 后厨端：`NativeTable::create_plan` 照单备菜

`table.rs:2051-2059`，开头第一件事是**统一普通/向量请求**：


> **Rust 陷阱：穷尽式 `match`**（`table.rs:2056`）。类似 `switch`，但编译器**强制**覆盖枚举的所有变体（漏一个就编译不过）。这里把 `AnyQuery::Query` 用 `from_plain_query`（§4.3）升格成向量请求，于是后面一整段 `Scanner` 装配代码**普通/向量共用**——普通查询的 `query_vector` 为空，自然跳过 `nearest`，退化成纯扫描。这就是"一段代码两用"的秘密。

> **金库保安出场**（`table.rs:2061`）：`self.dataset.get().await?` 经 `DatasetConsistencyWrapper::get()`（`table/dataset.rs:137`）拿到一份一致性数据快照 `DatasetReadGuard`。保证这次查询自始至终看到的是同一个数据版本。机制细节留给 `10`。

拿到快照后，是本篇最该刻进脑子的一段——**把表格逐条翻译成 lance `Scanner` 的吩咐**（`table.rs:2119-2216`）：

```rust

```

> **"组装而非重造"的最强证据就在这里。** `lancedb` 从头到尾**没写一行搜索算法**：没有 IVF 探测逻辑、没有 HNSW 遍历、没有距离计算。它只是把你点菜单上的每一项（`nprobes` / `filter` / `nearest` / `refine`…）**翻译**成对 lance `Scanner` 的一句 setter，最后 `scanner.create_plan().await?` 让 **lance** 产出一棵 DataFusion `ExecutionPlan`（物理算子树）。`lancedb` 在这里扮演的是"翻译官 + 编排者"，不是"算法实现者"。

> **Rust 陷阱：`scanner.create_plan().await?` 的 `?`**（`table.rs:2216`）。这是错误传播糖：出错就提前 `return Err`，成功就解包 `Ok` 里的值。等价于 Go 的 `if err != nil { return err }`，但一个字符搞定。

> **`Scanner` 从哪来？** `table.rs:25` `use lance::dataset::scanner::Scanner;`——它是 **lance** 的类型，不是 lancedb 自己的。再次印证：灶台是 lance 的，lancedb 只负责吩咐。

### 5.4 驱动执行：`execute_plan`

回到 §5.1 的 `inner_execute_with_options`：拿到 `plan` 后调 `execute_plan(plan, Default::default())?`（`query.rs:1093`）。这个函数来自 `lance_datafusion::exec`（`table.rs:36` 的 import），它才**真正驱动**DataFusion 的"传菜流水线"，把惰性的 `ExecutionPlan` 跑成 `RecordBatch` 流。

普通查询走的是 `NativeTable::query`（`table.rs:2219-2225`）→ `generic_query`（`table.rs:1791-1804`），里面同样是"先 `create_plan` 再 `execute_plan`"：

```rust
async fn generic_query(&self, query: &AnyQuery, options: QueryExecutionOptions)
    -> Result<DatasetRecordBatchStream> {
    let plan = self.create_plan(query, options.clone()).await?;   // ① 编计划  :1796
    let inner = execute_plan(plan, Default::default())?;          // ② 驱动执行  :1797
    let inner = if let Some(timeout) = options.timeout {          // ③ 可选超时
        TimeoutStream::new_boxed(inner, timeout)
    } else { inner };
    Ok(DatasetRecordBatchStream::new(inner))                      // ④ 包成流  :1803
}
```

> **`execute()` 是"下单"，不是"上菜"**。它先 `create_plan` 拿到惰性的算子树（什么都还没算），再 `execute_plan` 才真正开动流水线。想看计划长啥样、又不真跑，用 `explain_plan`（合同上的默认方法，`table.rs:430-435`，内部 `create_plan` + `DisplayableExecutionPlan` 渲染成文本）；想跑一遍顺带拿运行时统计，用 `analyze_plan`（`NativeTable` 实现，调 `lance_analyze_plan`，`table.rs:36` import）。

**本跳小结**：点菜单折进信封委托回后厨 → 后厨统一请求、拿快照、把表格逐条翻译成 lance `Scanner` 吩咐 → `scanner.create_plan()` 出工单 → `execute_plan` 驱动。下一跳看一个 lancedb 少有的"亲自拼算子"场景。

## 6. 多向量查询：lancedb 亲自拼 DataFusion 算子树

§3 里 `query_vector` 是个 `Vec`。当你压进**多个**查询向量（且目标列不是 multivector 列）时，`create_plan` 会分叉（`table.rs:2099-2116`）：

```rust
} else {
    // 多个查询向量:给每个向量单独建计划，再 union
    let query_vecs = query.query_vector.clone();
    let plan_futures = query_vecs.into_iter().map(|query_vector| {
        let mut sub_query = query.clone();
        sub_query.query_vector = vec![query_vector];                  // ① 每个向量一个子请求
        let options_ref = options.clone();
        async move {
            self.create_plan(&AnyQuery::VectorQuery(sub_query), options_ref).await  // ② 递归建子计划
        }
    }).collect::<Vec<_>>();
    let plans = futures::future::try_join_all(plan_futures).await?;   // ③ 并发建好所有子计划
    return Table::multi_vector_plan(plans);                          // ④ 合并成一棵树
}
```

合并逻辑在 `Table::multi_vector_plan`（`table.rs:1109-1156`）。**这是少数 lancedb 不依赖 lance `Scanner`、亲手用 DataFusion 算子拼装的地方**，是读懂"lancedb 如何直接编排 DataFusion"的最佳样本：

```rust
pub(crate) fn multi_vector_plan(plans: Vec<Arc<dyn ExecutionPlan>>)
    -> Result<Arc<dyn ExecutionPlan>> {
    // ① 给每个子计划套 ProjectionExec，注入一列 query_index 标记"这盘菜属于哪个查询向量"
    let projected_plans = plans.into_iter().enumerate().map(|(plan_i, plan)| {
        let query_index = datafusion_common::ScalarValue::Int32(Some(plan_i as i32));
        // …构造 Literal 表达式 + 原有所有列…
        let projection = ProjectionExec::try_new(projections, plan).unwrap();   // :1143
        Arc::new(projection) as Arc<dyn ExecutionPlan>
    }).collect::<Vec<_>>();

    let unioned = Arc::new(UnionExec::new(projected_plans));         // ② 合流  :1148
    let repartitioned = RepartitionExec::try_new(                   // ③ 收成 1 个分区  :1150
        unioned,
        datafusion_physical_plan::Partitioning::RoundRobinBatch(1),
    ).unwrap();
    Ok(Arc::new(repartitioned))
}
```

三个算子都直接 import 自 `datafusion_physical_plan`（`table.rs:17-19`）：`ProjectionExec`、`UnionExec`、`RepartitionExec`。

> **比喻**：多向量搜索像"一桌点了几份相同套餐"。后厨为每份单独备菜（递归 `create_plan`），给每盘贴上桌号标签（`query_index`，由 `ProjectionExec` 注入），再把几条流水线合并成一条（`UnionExec`），最后收口到单一出餐窗（`RepartitionExec` 收成 1 分区）。

> **呼应 `09 §2.4`**：`multi_vector_plan` 是 `pub(crate)` 的（仅本 crate 可见），定义在 `impl Table` 块里——它是个关联函数（无 `self`），纯粹的算子树拼装工具。

**本跳小结**：单向量时 lancedb 全程委托 lance；多向量时它亲自登场拼 DataFusion 算子。这两种姿态合起来就是 lancedb 的全部本事——**编排，而非重造**。

## 7. 结果回流：`RecordBatch` 流（Arrow 餐盘）

无论哪条路，最终返回的都是一个 **Arrow `RecordBatch` 流**：

- `Query::execute_with_options` 返回 `SendableRecordBatchStream`（`query.rs:772`，由 `parent.query` 的 `DatasetRecordBatchStream` 转成）。
- `generic_query` 把 `execute_plan` 的产物包进 `DatasetRecordBatchStream::new(inner)`（`table.rs:1803`）。

> **比喻**：传菜流水线（DataFusion）拿到工单才真正开动，把一盘盘餐盘（Arrow `RecordBatch`）顺着流水线端出来。每个 `RecordBatch` 是一批行（默认每批最多 `max_batch_length = 1024` 行，`query.rs:528`/`536`），列式存储，零拷贝切片。你在外层这样消费它（呼应 `table.rs:937-938` 文档示例）：
> ```rust
> let stream = tbl.query().execute().await?;
> let batches: Vec<RecordBatch> = stream.try_collect().await?;   // 边产边收，背压可控
> ```

> **为什么是流而不是一次性返回全部？** 大结果集分批处理，能限制单次查询的内存峰值；如果你消费得慢，背压会传导回去、限制预读量（`query.rs:572-576` 注释）。这正是 Arrow + DataFusion 流式模型的价值，lancedb 直接复用、没有重造。

### 旁路一瞥：混合搜索不进主路

§5.1 提到，一旦 `full_text_search.is_some()`，`VectorQuery::execute_with_options` 就转 `execute_hybrid`（`query.rs:1014`），**不走 `create_plan` 主路**：

```rust
let (fts_results, vec_results) = try_join!(                       // 并发跑两个子查询  query.rs:1026
    fts_query.execute_with_options(options.clone()),             // 全文灶
    vector_query.inner_execute_with_options(options)             // 向量灶
)?;
// …collect 全部结果 → normalize_scores → reranker.rerank_hybrid 合并…  query.rs:1049-1070
```

> **比喻**：混合搜索是后厨开的"两个灶同时炒"特别通道。全文灶和向量灶并行出菜（`try_join!`），菜端齐后由领班（reranker）按综合评分重新摆盘。这一步在 Rust 侧 `collect` 后合并，难以表达成单一 `ExecutionPlan`，所以走旁路。

> **Rust 陷阱：`try_join!`**（`query.rs:1026`）并发跑多个 Future，任一出错即短路返回 `Err`。类比 JS 的 `Promise.all`，但带错误短路。细节留给后续篇章。

## 11. 小结 & 下一篇

- **入口**：`Table::query()`（`table.rs:941`）和 `vector_search()`（`:950`）都只造点菜单、零 IO；后者等价于 `query().nearest_to(v)`。
- **三层 trait**：`HasQuery`（持有表格）+ `QueryBase`（一处 blanket impl 送全套 setter）+ `ExecutableQuery`（能下单），共同支撑 `Query` / `VectorQuery`。
- **升级**：`nearest_to`（`query.rs:734`）把 `Query` 升成 `VectorQuery`，向量转成 Arrow 餐盘压进 `query_vector`，缺省补 `limit=10`。
- **参数**：所有勾选静躺在 `QueryRequest`（9 字段）/ `VectorQueryRequest`（叠 `nprobes=20`、`use_index=true` 等）里。
- **执行**：Builder 把请求折进 `AnyQuery` 委托回 `parent`；`NativeTable::create_plan`（`table.rs:2051`）统一请求、拿快照、把字段逐条翻译成 lance `Scanner` 吩咐，`scanner.create_plan()`（`:2216`）产出 DataFusion `ExecutionPlan`，`execute_plan` 驱动成 `RecordBatch` 流。
- **两种姿态**：单向量全程委托 lance；多向量时 lancedb 亲自用 `ProjectionExec`/`UnionExec`/`RepartitionExec` 拼算子树（`:1109`）。混合搜索走 `execute_hybrid` 旁路。
- **一句话**：**lancedb 不重造搜索引擎，它把你的点菜单翻译成对 lance/DataFusion 的吩咐——组装，而非重造。**
