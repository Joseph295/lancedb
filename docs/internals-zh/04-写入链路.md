## 0. 这条链路要回答的问题

你写下这一行：

```rust
table.add(batch).execute().await?;
```

一条 `RecordBatch` 从你手里出发，要穿过 **5 层**才能躺进磁盘。这一篇就当一次"跟单"：盯着这一条数据，看它每过一道门，**被谁接手、交给了谁、在第几行**。

读完你应该能回答：

1. 为什么 `add` 写完不报错也不写盘——它根本**没执行**？
2. 我传 `Vec`、传 `RecordBatchIterator`、传 Pandas 转来的流，凭什么都能进去？（`IntoArrow` 的"万能转换"）
3. embedding 列我没填，它怎么自己冒出来的？
4. lancedb 到底自己写没写一行存储代码？（剧透：没有，它**编排** lance）

> **比喻总钥匙**（延续 09）：`Table` 是**服务员**，`AddDataBuilder` 是你手里的**点菜单**，`BaseTable` 是后厨的**用工合同**，`NativeTable` 是**本地后厨**、`RemoteTable` 是**外卖分店**，`MaybeEmbedded` 是**按订单现做**的工序，`DatasetConsistencyWrapper` 是金库门口的**保安**，而 `lance` 是真正的**灶台**。这一篇，我们跟着一盘菜从点单到上桌走一遍。

## §1 第一跳 · `Table::add`：为什么不立即执行

入口签名（`table.rs:619`）：

```rust
pub fn add<T: IntoArrow>(&self, batches: T) -> AddDataBuilder<T> {   // ① 注意：没有 async
    AddDataBuilder {
        parent: self.inner.clone(),          // ② 把"后厨电话"塞进菜单（Arc 计数 +1，不搬表）
        data: batches,                       // ③ 你给的原始数据，泛型 T，原样收下
        mode: AddDataMode::Append,           // ④ 默认追加
        write_options: WriteOptions::default(),
        embedding_registry: Some(self.embedding_registry.clone()),  // ⑤ 带上 embedding 注册表
    }
}
```

**这一跳做了什么？** 几乎什么都没做。它不碰 IO、不校验、不写盘，只是 `new` 出一个 `AddDataBuilder` 还给你。返回类型是 `AddDataBuilder<T>`，不是 `Result`，也不是 `Future`——所以你**没法 `.await` 它**，只能继续往菜单上勾选项。

这正是 09 讲过的 **Builder 工厂模式**：Rust 没有"可选参数 / 默认参数 / 重载"，要表达"加数据时可选追加还是覆盖、可配写选项"，最地道的写法就是先返回一个能继续填的对象，填完再 `.execute()`。

| 字段 | 含义 | 比喻 |
|---|---|---|
| `parent: Arc<dyn BaseTable>` | 真正干活的后厨（本地或远程） | 菜单背面印着后厨电话 |
| `data: T` | 你给的原始数据，**还没转成 Arrow** | 你点的菜，还没下锅 |
| `mode` | `Append` / `Overwrite` | 加菜还是重做一桌 |
| `embedding_registry` | 一张"哪列要现算 embedding"的函数表 | 厨房的特调配方本 |

> **Rust 知识点：`<T: IntoArrow>` 泛型约束**。`add` 接受**任意类型 `T`**，前提是 `T` 实现了 `IntoArrow`。类比 TypeScript 的 `add<T extends IntoArrow>(x: T)`、Java 的 `<T extends IntoArrow>`。"凭什么 `Vec`、`RecordBatchIterator` 都能传"——答案在 §2。

> **Rust 陷阱：`self.inner.clone()` 不是复制表**。`inner` 是 `Arc<dyn BaseTable>`（原子引用计数指针）。`clone` 只把计数 +1，背后还是同一张表。你会在整个链路里见到无数次 `clone`——心里要清楚那是廉价的"再印一张遥控器"，不是搬电视。

下一跳：你调 `.execute()`，菜单才真正送进厨房。

## §2 第二跳 · `execute`：泛型数据 → Arrow（`IntoArrow` 的万能转换）

入口签名（`table.rs:309`）：

```rust
pub async fn execute(self) -> Result<()> {          // ① 这次是 async，self 被消费
    let parent = self.parent.clone();               // ② 留一份后厨电话给最后一步
    let data = self.data.into_arrow()?;             // ③ 泛型 T → Arrow 流；出错就 ? 抛出
    let without_data = AddDataBuilder::<NoData> {    // ④ 造一张"去掉数据"的菜单（只剩配置）
        data: NoData {},
        mode: self.mode,
        parent: self.parent,                        //   原 parent 移进这里
        write_options: self.write_options,
        embedding_registry: self.embedding_registry,
    };
    parent.add(without_data, data).await            // ⑤ 委托给 BaseTable::add（合同方法）
}
```

**这一跳做了什么？** 三件事：把数据转成 Arrow（③）、把"配置"和"数据"拆成两份（④）、交给合同方法（⑤）。

### 万能转换：`IntoArrow` 的 blanket impl

`into_arrow()` 凭什么能吃下各种类型？看 `arrow.rs:119`：

```rust
pub trait IntoArrow {
    fn into_arrow(self) -> Result<Box<dyn arrow_array::RecordBatchReader + Send>>;
}

// ★ blanket impl：为"所有实现了 RecordBatchReader 的类型"统一实现 IntoArrow
impl<T: arrow_array::RecordBatchReader + Send + 'static> IntoArrow for T {  // arrow.rs:126
    fn into_arrow(self) -> Result<Box<dyn arrow_array::RecordBatchReader + Send>> {
        Ok(Box::new(self))      // 只是装箱成 trait 对象，零拷贝
    }
}
```

这就是答案：**任何 Arrow 的 `RecordBatchReader` 都自动满足 `IntoArrow`**——你传 `RecordBatchIterator`、传从 Pandas/Polars 桥接过来的批流，统统中招。转换的全部动作就是 `Box::new(self)`：把具体类型**装箱**成一个统一的 trait 对象 `Box<dyn RecordBatchReader + Send>`。

> **Rust 知识点：blanket impl（覆盖式实现）**。`impl<T: ...> Trait for T` 是给"所有满足约束的类型"一次性实现某 trait 的写法。类比"凡是会写字的，都自动算会签名"。它让 lancedb 不必为每种数据源各写一个适配器——**这就是"组装而非重造"在类型层面的体现**：Arrow 已经定义好 `RecordBatchReader` 抽象，lancedb 只搭一座桥。

> **Rust 知识点：`Box<dyn ... + Send>`（堆上的 trait 对象 + 跨线程通行证）**。`dyn RecordBatchReader` 是"任意能产出 RecordBatch 的东西"，编译期不知道大小，所以用 `Box` 放堆上。`+ Send` 是"能安全转移到别的线程"的标记——写盘可能在别的 async 任务里跑，没有这个标记编译器不放行（见 §7 速查）。

### 为什么要拆成 `without_data` + `data` 两份？

注意合同方法 `add(&self, add: AddDataBuilder<NoData>, data: Box<...>)` 收**两个**参数：一份**没有数据的配置菜单**，外加**独立的 Arrow 数据流**。`execute` 用 `AddDataBuilder::<NoData>` 把数据字段换成空壳 `NoData {}`，把配置（mode、write_options、embedding_registry）单独打包。

> **Rust 陷阱：`NoData` 是零大小类型 + 类型状态（typestate）**。`AddDataBuilder<NoData>`（`table.rs:312`）里 `data: NoData {}` 是个**零字节占位**。换成它，等于用类型系统在编译期标注"这张菜单的数据已经被取走了，别再当数据用"。数据走 `data` 参数单独传，配置走 `add` 参数——职责分清，签名自解释。

下一跳：`parent.add(...)` 触发 `dyn` 动态分发，选中真正的后厨。

## §2.5 过渡跳 · `BaseTable::add`：合同只写签名，不写做法

`parent` 的静态类型是 `Arc<dyn BaseTable>`。`parent.add(...)` 调的是合同方法（`table.rs:443`）：

```rust
async fn add(
    &self,
    add: AddDataBuilder<NoData>,                          // 配置菜单
    data: Box<dyn arrow_array::RecordBatchReader + Send>, // Arrow 数据流
) -> Result<()>;
```

这里**只有签名，没有方法体**——合同只规定"想当表就得会 `add`"，具体怎么做由后厨决定（参见 09 §1：`BaseTable` 全 trait 解剖）。运行时 `parent` 实际指向谁，就**动态分发**到谁的实现：本地是 `NativeTable::add`，云端是 `RemoteTable::add`。

> **Rust 知识点：动态分发（dynamic dispatch）**。`Arc<dyn BaseTable>` 背后藏着一张虚函数表（vtable），`.add()` 在运行时查表跳转。类比 Java 接口方法调用、Python 的鸭子类型。**好处**：上层 `execute` 这行代码同时服务本地表和云表，一字不改——这正是 09 反复强调的"一份合同，两家后厨"。

我们先走本地这条主路。

## §3 第三跳 · 数据进 `NativeTable::add`：本地后厨接单

入口签名（`table.rs:1957`）：

```rust
async fn add(
    &self,
    add: AddDataBuilder<NoData>,
    data: Box<dyn RecordBatchReader + Send>,
) -> Result<()> {
    let data = Box::new(MaybeEmbedded::try_new(           // ① 按需包一层"现做 embedding"工序
        data,
        self.table_definition().await?,                  //   取表定义：哪几列是 embedding 列
        add.embedding_registry,                          //   embedding 函数表
    )?) as Box<dyn RecordBatchReader + Send>;

    let lance_params = add.write_options.lance_write_params.unwrap_or(WriteParams {  // ② mode → lance 参数
        mode: match add.mode {
            AddDataMode::Append => WriteMode::Append,
            AddDataMode::Overwrite => WriteMode::Overwrite,
        },
        ..Default::default()
    });

    let dataset = {
        // Limited scope for the mutable borrow of self.dataset avoids deadlock.
        let ds = self.dataset.get_mut().await?;          // ③ 找"保安"拿写锁  dataset.rs:147
        InsertBuilder::new(Arc::new(ds.clone()))         // ④ 交给 lance 的 InsertBuilder
            .with_params(&lance_params)
            .execute_stream(data)                        // ⑤ lance 流式落盘  table.rs:1981
            .await?
    };

    self.dataset.set_latest(dataset).await;              // ⑥ 把新版本"扶正"  table.rs:1985
    Ok(())
}
```

这是整条链路的**心脏**。它干六件事：现做 embedding（§4）、翻译 mode、拿写锁、调 lance 落盘、扶正新版本（§6）。本节先讲"接单 + sanitize/校验"的部分，embedding 单列 §4，落盘单列 §5。

### sanitize / 校验：数据进门要不要"摆盘"

`MaybeEmbedded::try_new`（①）顺便就把**表定义 vs 来料**对齐了：它读 `self.table_definition()`（拿到目标 schema 与列定义），后续 lance 的 `InsertBuilder` 会按这份 schema 把数据对齐写入。

如果来料 schema 和目标 schema 不完全一致（比如 float64 来料要写进 float32 列），就需要"摆盘"——这就是 `data/sanitize.rs` 的活儿。核心是 `coerce_schema`（`sanitize.rs:166`）：

```rust
pub fn coerce_schema(
    reader: impl RecordBatchReader + Send + 'static,
    schema: Arc<Schema>,
) -> Result<Box<dyn RecordBatchReader + Send>> {
    if reader.schema() == schema {                       // ① schema 已经一致 → 直接放行，零拷贝
        return Ok(Box::new(RecordBatchIterator::new(reader, schema)));
    }
    let s = schema.clone();
    let batches = reader
        .zip(repeat_with(move || s.clone()))
        .map(|(batch, s)| coerce_schema_batch(batch?, s)); // ② 否则逐批"强制对齐"
    Ok(Box::new(RecordBatchIterator::new(batches, schema)))
}
```

`coerce_schema_batch`（`sanitize.rs:143`）逐列按名字找到来料、用 `coerce_array` 转成目标类型（数值列的 float16/32/64 互转就在这里），找不到列就报 `Column ... not found`。

> **比喻**：`sanitize` 是上菜前的**摆盘工序**——餐盘（Arrow schema）规定了盘型，来料若尺寸不符就裁切对齐；已经合规的盘子直接端走，不折腾。

另有一个相关的"看菜识盘"工具 `infer_vector_columns`（`inspect.rs:45`）：扫描 schema，把 `FixedSizeList<float>` 直接认定为向量列，把 `List<float>` 在非严格模式下尝试推断维度。**注意：它在 `add` 主路上并不被调用**（建索引等场景才用到），这里点一笔是为了让你别把它误当作写入必经之站。

> **Rust 知识点：`impl Trait` 参数（`reader: impl RecordBatchReader`）**。等价于 `<R: RecordBatchReader>` 泛型，是"任意满足约束的类型"的语法糖，**静态分发**（编译期单态化，无 vtable 开销）——和 §2.5 的 `dyn`（动态分发）正好是一对。

下一跳：进 `MaybeEmbedded`，看 embedding 列怎么自己长出来。

## §4 第四跳 · embedding 列的按需生成

`MaybeEmbedded` 是个枚举（`embeddings.rs:131`）：

```rust
pub enum MaybeEmbedded<R: RecordBatchReader> {
    Yes(WithEmbeddings<R>),   // 要现做 embedding
    No(R),                    // 不用，原样透传
}
```

`try_new`（`embeddings.rs:143`）决定走哪个分支：

```rust
pub fn try_new(inner, table_definition, registry: Option<...>) -> Result<Self> {
    if let Some(registry) = registry {
        let mut embeddings = Vec::with_capacity(...);
        for cd in table_definition.column_definitions.iter() {
            if let ColumnKind::Embedding(embedding_def) = &cd.kind {     // ① 这列是 embedding 列吗？
                match registry.get(&embedding_def.embedding_name) {      // ② 注册表里有对应函数吗？
                    Some(func) => embeddings.push((embedding_def.clone(), func)),
                    None => return Err(Error::EmbeddingFunctionNotFound { .. }),  // ③ 定义了却没注册 → 报错
                }
            }
        }
        if !embeddings.is_empty() {
            return Ok(Self::Yes(WithEmbeddings { inner, embeddings }));  // ④ 有活儿 → Yes
        }
    };
    Ok(Self::No(inner))                                                  // ⑤ 没活儿 → No，零成本透传
}
```

**逻辑**：遍历表定义的列，凡 `ColumnKind::Embedding` 的列，就去 registry 找它的生成函数。找到就收进待办；表里**声明了** embedding 列却**没注册**对应函数，直接 `EmbeddingFunctionNotFound` 报错（②③）。一个都没有就走 `No`，**完全零成本透传**。

真正"现算"发生在 `WithEmbeddings` 的迭代器里——**惰性**，每拉一个 batch 才算一批（`embeddings.rs:262`）：

```rust
fn next(&mut self) -> Option<Self::Item> {
    let batch = self.inner.next()?;                  // ① 先从上游拉一批
    match batch {
        Ok(mut batch) => {
            for (fld, func) in self.embeddings.iter() {
                let src_column = batch.column_by_name(&fld.source_column).unwrap();
                let embedding = func.compute_source_embeddings(src_column.clone())?;  // ② 算 embedding
                // ...
                batch = batch.try_with_column(dst_field.clone(), embedding)?;          // ③ 把新列接到 batch 上
            }
            Some(Ok(batch))                          // ④ 返回"长出新列"的 batch
        }
        Err(e) => Some(Err(e)),
    }
}
```

`compute_source_embeddings(src)`（②）拿源列算出向量，`try_with_column(dst, emb)`（③）把它当新列拼回 batch。**关键是惰性**：embedding 不是写入前一次性全算完，而是随着 lance `execute_stream` 一批批往下拉、一批批现算现拼——内存友好。

> **比喻**：embedding 列是**按订单现做**的菜。你只点了"原料列"（如 `text`），后厨照配方本（registry）把它现炒成"向量列"（如 `text_embedding`），且**来一桌做一桌**，不预先囤货。

> **Rust 知识点：迭代器适配器 = 惰性流水线**。`MaybeEmbedded`/`WithEmbeddings` 都实现了 `RecordBatchReader`（即 `Iterator`），它们**包裹**上游 reader，在 `next()` 里转一道手。多个这样的包装层叠起来，就是一条"拉一下、动一下"的惰性流水线——和 §3 的 `coerce_schema` 同构。这正是 Arrow + Rust 迭代器的标准组合拳。

下一跳：拼好 embedding 的数据流，交给 lance 落盘。

## §5 第五跳 · 委托 lance 落盘（`InsertBuilder` / Append vs Overwrite / `WriteParams`）

回到 `NativeTable::add` 的尾段（`table.rs:1976`）：

```rust
let dataset = {
    // Limited scope for the mutable borrow of self.dataset avoids deadlock.
    let ds = self.dataset.get_mut().await?;          // ① 拿写锁，得到 DatasetWriteGuard
    InsertBuilder::new(Arc::new(ds.clone()))         // ② 构造 lance 的写入 Builder
        .with_params(&lance_params)                  //   带上 Append/Overwrite 等参数
        .execute_stream(data)                        // ③ ★ lance 流式落盘
        .await?
};                                                   // ④ 作用域结束，写锁在此释放
self.dataset.set_latest(dataset).await;              // ⑤ 把 lance 返回的新版本扶正
```

**这一跳做了什么？** lancedb 自己**不写任何存储代码**，它把"写盘"整件事交给 lance 的 `InsertBuilder::execute_stream`。lancedb 负责的只是：翻译参数、拿锁、把 lance 还回来的新 `Dataset` 装回保安手里。

### mode 怎么变成 lance 参数

§3 的 ② 处已经把 lancedb 的 `AddDataMode` 翻译成 lance 的 `WriteMode`：

| lancedb `AddDataMode` | lance `WriteMode` | 语义 |
|---|---|---|
| `Append`（默认） | `WriteMode::Append` | 在现有数据后追加，老数据不动 |
| `Overwrite` | `WriteMode::Overwrite` | 用新数据整体替换（仍是新版本，旧版本保留） |

注意 `add.write_options.lance_write_params.unwrap_or(...)`：如果用户在菜单上**直接塞了完整的 lance `WriteParams`**，就用用户的；否则用 mode 拼一个默认的。这又是"Rust 表达可选参数"的 `unwrap_or` 惯用法。

### `get_mut` 的写锁与"避免死锁"的花括号

`self.dataset.get_mut()`（`dataset.rs:147`）做两件守门事，再交出写锁：

```rust
pub async fn get_mut(&self) -> Result<DatasetWriteGuard<'_>> {
    self.ensure_mutable().await?;        // ① 时间旅行模式下不许写 → 报错（dataset.rs:210）
    self.ensure_up_to_date().await?;     // ② 必要时先刷新到最新版（dataset.rs:247）
    Ok(DatasetWriteGuard { guard: self.0.write().await })  // ③ 真正拿写锁
}
```

`ensure_mutable`（`dataset.rs:210`）若发现表正 checkout 在某个历史版本（`TimeTravel`），直接报 `table cannot be modified when a specific version is checked out`——**回溯态只读**，呼应时间旅行设计（细节留 10）。

> **Rust 知识点：RAII 守卫 + 花括号控制锁的生命周期**。`DatasetWriteGuard` 是一把"锁住的钥匙"：它**活着**，锁就**被持有**；它被 drop（离开作用域），锁**自动释放**。源码故意用 `let dataset = { ... };` 把 `ds`（写锁）圈在花括号里——这样 `execute_stream` 一结束、花括号一闭合，写锁立刻还回去，紧接着的 `set_latest`（⑤，它内部要重新拿写锁）才不会和自己**死锁**。源码注释 `table.rs:1977` 原话就是 *"Limited scope ... avoids deadlock"*。这是 Rust 并发里极常见、也极容易写错的一手。

> **比喻**：`get_mut` 是去金库取"独占钥匙"。保安先确认你不是在参观历史展厅（`ensure_mutable`）、库存是不是最新的（`ensure_up_to_date`），才把钥匙给你。你用完（花括号闭合）必须立刻交还，否则下一个人（`set_latest`）进不去。

下一跳：lance 写完，世界多了一个新版本。

## §6 第六跳 · 只读追加式存储产生新版本（呼应 optimize）

`execute_stream` 返回的不是 `()`，而是一个**全新的 `Dataset`**——代表写入后的最新版本。最后一步 `set_latest`（`dataset.rs:186`）把它装回保安手里：

```rust
pub async fn set_latest(&self, dataset: Dataset) {
    self.0.write().await.set_latest(dataset);    // 把内部 DatasetRef 切到这个新版本
}
```

**为什么是"新版本"而不是"原地改"？** 因为 lance 是**只读、追加式（append-only）存储**：

- 每次 `add`（无论 Append 还是 Overwrite）都**写出新文件**、生成**新版本号**；
- 旧版本的文件**仍在磁盘上**，并不被覆盖。

这带来三个直接后果：

| 后果 | 好处 | 代价 |
|---|---|---|
| 旧版本保留 | 天然支持**时间旅行**（`checkout` 到历史版本） | 占额外磁盘 |
| 写不改旧文件 | **读不加锁**、读写不打架 | 小文件越积越多 |
| 版本单调递增 | 操作可追溯、可 `restore` | 需要定期"大扫除" |

于是就有了 09 §3.3 讲过的 `optimize` 三件套来收尾：`Compact`（并小文件）、`Prune`（删旧版本腾空间，类比 PostgreSQL `VACUUM`）、`Index`（把新写入的数据增量并进已有索引）。

> **一句话连起来**：写入之所以"便宜又安全"（不锁读、可回溯），代价就是日积月累的碎片——这碎片由 `optimize` 来还。**写入链路的终点，正是优化链路的起点。**

> **比喻**：后厨从不"擦掉"旧账本，每次都**翻开新一页**记账（新版本）。账本越来越厚，于是定期请人来归档整理（`optimize`），但任何一天的旧账永远翻得到（时间旅行）。

## §3′ 旁路一跳 · `RemoteTable::add`：外卖分店走 IPC

主路讲完，回头看 §2.5 那个岔口的另一条路。如果 `parent` 指向的是云端表，`add` 分发到 `RemoteTable::add`（`remote/table.rs:526`）：

```rust
async fn add(&self, add, data) -> Result<()> {
    self.check_mutable().await?;                          // ① 同样先校验可写
    let body = Self::reader_as_body(data)?;              // ② 把 Arrow 流序列化成 HTTP body
    let mut request = self.client
        .post(&format!("/v1/table/{}/insert/", self.name))
        .header(CONTENT_TYPE, ARROW_STREAM_CONTENT_TYPE)
        .body(body);
    match add.mode {
        AddDataMode::Append => {}
        AddDataMode::Overwrite => { request = request.query(&[("mode", "overwrite")]); }  // ③ mode 进 query
    }
    let (request_id, response) = self.client.send(request, false).await?;  // ④ 发出去
    self.check_table_response(&request_id, response).await?;
    Ok(())
}
```

关键在 `reader_as_body`（②，`remote/table.rs:107`），它用 Arrow IPC 把数据流式编码：

```rust
let mut writer = arrow_ipc::writer::StreamWriter::try_new(Vec::new(), &data.schema())?;  // remote/table.rs:109
// 每拉一个 batch 就 writer.write(&batch)，边读边发，不在内存里囤整份数据
```

`StreamWriter`（`ipc.rs` 提供同族的 IPC 编解码工具，如 `batches_to_ipc_file`/`ipc_file_to_batches`）把 RecordBatch 序列化成 Arrow IPC 字节流，挂成 `reqwest::Body` 流式上传——**同一份 Arrow 数据，本地交给 lance 灶台，云端通过 IPC 发给服务器**。两条路在 `BaseTable::add` 这个合同方法前完全共用前半程（§1、§2），从 §3 才分叉。

> **比喻**：`RemoteTable` 是**外卖分店**。同一张点菜单、同一盘餐（Arrow 数据），本地店直接进后厨，外卖店则把餐打包成标准箱（IPC 字节流）走快递（HTTP）送到总部厨房。打包规格是统一的，所以前台（`BaseTable` 合同）一行都不用改。

## §7 整条写入链路一图回顾

把八跳合成完整调用栈（本地主路 + 远程旁路）：

```
你的代码:  table.add(batch).execute().await?
   │
   │ ① Table::add                  table.rs:619    不是 async，只造 AddDataBuilder
   ▼
AddDataBuilder { parent, data:T, mode:Append, embedding_registry }

   │     ├─ data.into_arrow()?     arrow.rs:126    blanket impl：任意 RecordBatchReader → Box<dyn ...>
   │     └─ 拆成 NoData 配置 + 独立 data 流（typestate）  table.rs:312
   ▼
   ③ BaseTable::add（合同签名）     table.rs:443    dyn 动态分发，选后厨
   │
   ├───────────────本地主路───────────────┐         └──────────远程旁路──────────┐
   ▼                                       │         ▼                            │
NativeTable::add               table.rs:1957        RemoteTable::add   remote/table.rs:526
   │                                                  │ check_mutable
   │ ④ MaybeEmbedded::try_new    embeddings.rs:143    │ reader_as_body → IPC StreamWriter

   │     （花括号限定写锁作用域，避免与 set_latest 死锁  table.rs:1977）
```

## 8. 本篇出现的 Rust 语法点 · 速查

| 语法 | 一句话 | 出现处 |
|---|---|---|
| `fn add<T: IntoArrow>(...)` | 泛型 + trait 约束：接受任意满足约束的类型 | `table.rs:619` |
| `impl<T: ...> Trait for T`（blanket impl） | 给"所有满足约束的类型"一次性实现 trait | `arrow.rs:126` |
| `Box<dyn Trait + Send>` | 堆上 trait 对象 + 跨线程通行证 | `arrow.rs:121`、`table.rs:446` |
| `AddDataBuilder<NoData>`（typestate） | 用零大小类型在编译期标注状态 | `table.rs:312` |
| `dyn` 动态分发 | 运行时查 vtable，一份代码服务多实现 | `BaseTable::add` `:443` |
| `reader: impl Trait`（静态分发） | 泛型语法糖，编译期单态化，无 vtable | `sanitize.rs:167` |
| `enum Yes/No` + `Iterator` | 包裹上游 reader 的惰性流水线 | `embeddings.rs:131/262` |
| `?` 运算符 | 出错就提前 `return Err` | 全篇（`into_arrow()?` 等） |
| `Option::unwrap_or(default)` | Rust 表达"可选/默认参数"的惯用法 | `table.rs:1968` |
| RAII 守卫（`DatasetWriteGuard`） | 守卫活着=持锁，drop=释放 | `dataset.rs:150` |
| `let x = { ... };` 限定作用域 | 用花括号控制锁的生命周期，避免死锁 | `table.rs:1976` |
| `Arc<dyn T>` + `.clone()` | 引用计数 +1，不复制底层对象 | `table.rs:621/310` |

## 10. 小结 & 下一篇

- **写入是惰性的**：`Table::add`（`:619`）只造点菜单 `AddDataBuilder`，`execute`（`:309`）才下单。
- **数据先统一成 Arrow**：`into_arrow` 的 blanket impl（`arrow.rs:126`）让任意 `RecordBatchReader` 都能进门——**组装而非重造**。
- **选后厨靠合同 + `dyn`**：`BaseTable::add`（`:443`）只写签名，运行时动态分发到 `NativeTable`（`:1957`）或 `RemoteTable`（`remote/table.rs:526`）。
- **本地后厨五步走**：按需 embedding（`embeddings.rs:143/262`）→ 摆盘 sanitize（`sanitize.rs:166`）→ 拿写锁（`dataset.rs:147`）→ 委托 lance `execute_stream`（`table.rs:1979`）→ 扶正新版本（`:1985`）。
- **追加式存储**：每次写入产生新版本、旧版本保留——这是时间旅行的基础，也是 `optimize` 存在的理由。

**下一篇 `10 Table 解剖（下）`** 将钻进本篇刻意留白的金库内部：`DatasetConsistencyWrapper` 的读写锁与"最新版 / 时间旅行"双模式如何保证一致性、`set_latest`/`ensure_up_to_date` 的完整机制、`checkout`/`restore` 的时间旅行语义，以及 `optimize` 三件套如何回收写入链路留下的碎片。
