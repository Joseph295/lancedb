## 0. 这一篇要回答的问题

前面的篇章讲的都是"主菜"：建连接、写数据、建索引、查询。但任何一家餐厅都有一批**贯穿所有岗位的后勤设施**——统一的投诉单、统一的进货标准、统一的餐盘、统一的传菜推车。这些东西不属于任何一道菜，却让每道菜都能做出来。

本篇就把 LanceDB 的这批"后勤设施"一网打尽。读完你能回答：

1. 三方库（lance、arrow、object_store、reqwest）报的错，**怎么统一翻译成一句用户能懂的话**？为什么写一个 `?` 就能自动翻译？
2. 本地磁盘、S3、GCS 这些天差地别的存储，**为什么上层代码一行 if 都不用写**？镜像双写又是怎么做的？
3. 用户传进来的 `Vec`、Polars DataFrame、Arrow Reader……**怎么统一变成内部的标准数据流**？这个扩展点叫什么？
4. 写入前的数据，**怎么自动对齐到表的 schema**（比如 `List<f32>` 自动变成 `FixedSizeList<f16>`）？

## 1. 错误模型 `error.rs`：全库的统一投诉单

### 1.1 一个枚举装下所有错误

`error.rs:9-11`：

```rust
#[derive(Debug, Snafu)]                  // ① 派生 Debug，并用 snafu 宏生成一堆样板代码
#[snafu(visibility(pub(crate)))]         // ② 生成的 selector 设为 pub(crate) 可见
pub enum Error {                         // ③ 全库唯一的错误类型，是个枚举
    // ……
}
```

LanceDB 把**所有可能出错的情况**塞进**一个枚举** `Error`。不管是表名非法、表没找到、还是底层 lance 崩了，最后都收敛成 `Error` 的某个**变体（variant）**。

> **Rust 知识点：枚举不是 C 的枚举**。Rust 的 `enum` 每个变体都能**携带数据**（叫"带数据的枚举 / sum type / tagged union"）。比如 `TableNotFound { name: String }` 这个变体自带一个 `name` 字段。类比：Python 里你可能为每种错误定义一个异常类（`TableNotFoundError`、`InvalidInputError`……），Rust 把它们全合并成**一个类型的多个分支**。好处是函数签名只写 `Result<T, Error>` 就能表达"可能失败成任意一种错误"。

按"自家错误"和"三方错误"分组，列出主要变体（`error.rs:12-84`）：

**① 自家业务错误**（LanceDB 自己定义、面向用户）
| 行号 | 变体 | 触发场景 |
|---|---|---|
| `:13` | `InvalidTableName { name, reason }` | 表名含非法字符（见 §6.3） |
| `:15` | `InvalidInput { message }` | 参数不合法（如非向量列建向量索引） |
| `:17` | `TableNotFound { name }` | 打开不存在的表 |
| `:19/:21` | `DatabaseNotFound / DatabaseAlreadyExists` | 库级错误 |
| `:23` | `IndexNotFound { name }` | 索引名找不到 |
| `:25` | `EmbeddingFunctionNotFound { name, reason }` | embedding 函数没注册 |
| `:28` | `TableAlreadyExists { name }` | 重复建表 |
| `:30` | `CreateDir { path, source }` | 建目录失败（**携带底层 `std::io::Error`**） |
| `:35` | `Schema { message }` | schema 相关错误 |
| `:37` | `Runtime { message }` | 运行时杂项错误 |
| `:78` | `NotSupported { message }` | 功能不支持 |

**② 三方/外部错误**（把别人的错误"包"进来）
| 行号 | 变体 | 包的是谁 |
|---|---|---|
| `:41` | `ObjectStore { source }` | `object_store::Error`（存储层） |
| `:43` | `Lance { source }` | `lance::Error`（核心引擎） |
| `:46` | `Http { source, request_id, status_code }` | `source` 是 `Box<dyn Error + Send + Sync>`，由 `#[snafu(source(from(reqwest::Error, Box::new)))]` 把 `reqwest::Error` 装箱而来；仅 `remote` feature |
| `:63` | `Retry { ... }` | 重试耗尽，携带各类失败计数，仅 `remote` feature |
| `:76` | `Arrow { source }` | `arrow_schema::ArrowError` |
| `:80` | `Other { message, source }` | 兜底"万能错误"（`#[snafu(whatever)]`） |

> **设计要点**：自家错误用**人话**（"Table 'foo' was not found"），三方错误用 `source` 字段**原样裹住**底层错误对象。这样既给用户一句能懂的话，又不丢失底层细节（调试时能顺着 `source` 链一路追下去）。

### 1.2 `snafu` 宏到底生成了什么

`error.rs:9` 的 `#[derive(Snafu)]` 是一个**派生宏**。它读你写的 `enum Error`，自动生成两类东西：

1. **`Display` 实现**——根据每个变体上的 `#[snafu(display("..."))]` 注解（如 `:16` 的 `"Table '{name}' was not found"`）生成"怎么打印给人看"。
2. **每个变体对应的 "selector" 结构体**——名字是 `变体名 + Snafu`。比如 `InvalidTableName` 变体会生成一个 `InvalidTableNameSnafu` 构造器。

第 2 类是非 Rust 读者最容易懵的地方。看它在别处怎么用（`database/listing.rs:399`）：

```rust
validate_table_name(name).context(InvalidTableNameSnafu { ... })?;
//                       └─ .context(XxxSnafu{...}) 把底层错误"贴上"我们的变体标签
```

`.context(InvalidTableNameSnafu { ... })` 的意思是："如果前面出错了，把那个底层错误**包装成** `Error::InvalidTableName` 这个变体，并补上 `name` 等字段。" `CreateDirSnafu`（`catalog/listing.rs:110`）也是同理。

> **Rust 陷阱：宏生成的名字凭空出现**。你在 `error.rs` 里**搜不到 `InvalidTableNameSnafu` 的定义**——它是 `#[derive(Snafu)]` 在编译期凭空造出来的。第一次读会以为是幽灵符号。记住规律：**变体 `Xxx` ⟹ 自动有个 `XxxSnafu` 选择器**。
>
> **`#[snafu(visibility(pub(crate)))]`（`error.rs:10`）的作用**：这些 selector 默认是私有的，加这行把它们设成 `pub(crate)`（本 crate 内可见），这样 `database/`、`catalog/` 等模块才能 `.context(XxxSnafu{...})` 构造它们。这是已验证事实：去掉这行，跨模块的 `.context()` 就编译不过。

### 1.3 `Result<T>`：少打两个字的类型别名

`error.rs:87`：

```rust
pub type Result<T> = std::result::Result<T, Error>;
```

标准库的 `Result` 有两个泛型参数 `Result<T, E>`。LanceDB **把错误类型 `E` 固定成自家 `Error`**，起个别名 `Result<T>`。从此全库函数签名只写 `Result<usize>`、`Result<Table>`，不用每次重复 `, Error`。

> **比喻**：`Result<T>` 是把"投诉单的格式"提前印好的空白单。你只需填"成功时返回什么（`T`）"，"失败长什么样"早已统一成 `Error`。

### 1.4 `From` + `?`：错误自动翻译的魔法

这是整个错误系统**最值得理解的一段**。看一个真实的写入入口（`AddDataBuilder::execute` 风格），里面会有这样一行：

```rust
let data = self.data.into_arrow()?;   // into_arrow 可能返回 arrow 的错误
```

`into_arrow()` 在底层可能产出 `ArrowError`，但这个函数的返回类型是 `Result<_, Error>`（LanceDB 的 `Error`）。两种错误类型不一样，为什么 `?` 能直接用？

答案在 `error.rs:89-123` 的一组 `From` 实现：

```rust
impl From<ArrowError> for Error {           // ① 教编译器：怎么把 ArrowError 变成 Error
    fn from(source: ArrowError) -> Self {
        Self::Arrow { source }              //    包成 Error::Arrow 变体
    }
}

impl From<lance::Error> for Error {         // ② lance 错误 → Error::Lance（error.rs:95）
    fn from(source: lance::Error) -> Self {
        Self::Lance { source }
    }
}

impl From<object_store::Error> for Error {  // ③ 存储错误 → Error::ObjectStore（error.rs:103）
    fn from(source: object_store::Error) -> Self {
        Self::ObjectStore { source }
    }
}
```

`?` 运算符的完整语义是：**"如果是 `Err(e)`，就对 `e` 调用 `.into()`（即触发 `From`）转成本函数的错误类型，再提前 `return`。"** 所以：

```
into_arrow()  →  Err(ArrowError)
                      │  遇到 ?，自动调 From<ArrowError> for Error
                      ▼
                 Err(Error::Arrow { source: 那个 ArrowError })
                      │
                      ▼  提前 return 出去
```

> **Rust 知识点：`From` + `?` 是 Rust 错误处理的灵魂**。你不需要手写 `match` 去转换错误——只要为"外部错误 → 自家 Error"实现了 `From`，`?` 就自动帮你翻译。这也解释了 §1.1 那些"三方错误变体"为什么存在：**它们就是 `From` 的落点**。
>
> **给贡献者的实操规律（teaching point）**：当你引入一条新的三方依赖（比如某个新的 embedding 后端），而它的错误想在 LanceDB 里用 `?` 直接传播，**标准动作就是给它写一个 `impl From<那个错误> for Error`**。`error.rs:125-152` 里 `PolarsError`、`hf_hub::ApiError`、`candle_core::Error` 三个都是这么加进来的（且都用 `#[cfg(feature = ...)]` 守着，feature 没开就不编译）。

一个有意思的特例在 `error.rs:117`：

```rust
impl<T> From<PoisonError<T>> for Error {     // 锁中毒错误（线程持锁时 panic 留下的"毒"）
    fn from(e: PoisonError<T>) -> Self {
        Self::Runtime { message: e.to_string() }   // 转成 Runtime，只保留字符串
    }
}
```

`PoisonError<T>` 带一个泛型 `T`（中毒的那个锁守卫类型），不好原样裹进 `Error`，于是这里**只 `to_string()` 提取消息**，降级成 `Runtime`。这是"无法干净转换时退而求其次"的典型手法。

> **呼应 09 §4.2**：`NativeTable::open_with_params` 里那段 `.map_err(|e| match e { lance::Error::DatasetNotFound => Error::TableNotFound, ... })` 是**手动**翻译（因为要把一种 lance 错误细分翻成不同 LanceDB 错误）；而本节的 `From` 是**自动**翻译（一对一兜底）。两者配合：能细分时手动 `map_err`，不能细分时 `?` 自动兜底成 `Error::Lance`。

## 2. 存储抽象 `io/object_store.rs`：一套接口屏蔽本地/S3/GCS

### 2.1 三层存储抽象

存储抽象**不是 LanceDB 独家发明**，而是三层叠起来的（teaching point）：

```
第三方 crate object_store ── 定义 trait ObjectStore：put/get/list/delete… 的统一接口
        ▲                    （本地 LocalFileSystem、AWS S3、GCS 各实现一份）
        │
       lance ── 用 object_store 读写文件，并提供 WrappingObjectStore 扩展点
        ▲       （允许"在真正的 store 外面再套一层"）
        │
     lancedb ── io/object_store.rs：实现一个 WrappingObjectStore，做"镜像双写"
```

所以"本地/S3/GCS 一套代码"这件事，**主要功劳在 `object_store` crate**：它把"往哪写"抽象成一个 `ObjectStore` trait，谁实现这个 trait 谁就是一种存储后端。LanceDB 和 lance 都只面向这个 trait 编程，自然不用写 `if 本地 else 云端`。

LanceDB 在这一层只加了**一个东西**：镜像存储包装器。

### 2.2 `MirroringObjectStoreWrapper`：主仓 + 快取的双写库管

`io/object_store.rs:161-179`：

```rust
#[derive(Debug)]
pub struct MirroringObjectStoreWrapper {
    secondary: Arc<dyn ObjectStore>,        // 只持有"副存储"
}

impl WrappingObjectStore for MirroringObjectStoreWrapper {
    fn wrap(&self, primary: Arc<dyn ObjectStore>) -> Arc<dyn ObjectStore> {
        Arc::new(MirroringObjectStore {     // 把传进来的"主存储"和自己的"副存储"
            primary,                        // 包成一个 MirroringObjectStore
            secondary: self.secondary.clone(),
        })
    }
}
```

`WrappingObjectStore` 是 lance 定义的 trait（`io/object_store.rs:9` 引入），只有一个方法 `wrap`：lance 在创建真正的存储后，会把它交给 `wrap`，让你"在外面再套一层"。这里套上的就是 `MirroringObjectStore`（`io/object_store.rs:20-24`），它同时握有 `primary`（主，慢但持久）和 `secondary`（副，快但不持久）。

> **比喻**：`MirroringObjectStore` 是一位**双写库管**。每次进货（写文件），他**先放进快取仓（secondary），再放进主仓（primary）**；每次取货（读文件），他**只去主仓拿**。

### 2.3 控制流：写双仓、读单仓、manifest 只进主仓

核心规则在 `ObjectStore` trait 的实现里（`io/object_store.rs:56-134`）。看写入 `put_opts`（`:57`）：

```rust
async fn put_opts(&self, location: &Path, bytes: PutPayload, options: PutOptions) -> Result<PutResult> {
    if location.primary_only() {                    // ① 这个文件是否"只该进主仓"？
        self.primary.put_opts(location, bytes, options).await
    } else {
        self.secondary                              // ② 否则：先写副仓
            .put_opts(location, bytes.clone(), options.clone()).await?;
        self.primary.put_opts(location, bytes, options).await   // ③ 再写主仓
    }
}
```

而读取 `get_opts`（`:92`）一句话——**只读主仓**：

```rust
async fn get_opts(&self, location: &Path, options: GetOptions) -> Result<GetResult> {
    self.primary.get_opts(location, options).await    // 读永远走 primary
}
```

那 `primary_only()` 判断的是什么？`io/object_store.rs:41-45`（**已验证：判断在 :43**）：

```rust
impl PrimaryOnly for Path {
    fn primary_only(&self) -> bool {
        self.filename().unwrap_or("") == "_latest.manifest"   // 文件名是 _latest.manifest 才"只进主仓"
    }
}
```

> **为什么 `_latest.manifest` 不能镜像？** lance 的存储是"写文件 + 写 manifest（版本清单）来提交"。`_latest.manifest` 是**指向当前最新版本的指针**，是事务提交的"那一锤子"。如果它也双写，副仓可能在主仓提交前/后处于不一致状态，读到半成品。所以铁律是：**数据文件可以镜像，提交指针只认主仓**。文件头注释（`io/object_store.rs:54`）也明说 "this object store does not mirror writes to *.manifest files"。
>
> **比喻**：快取仓里可以堆放食材副本（数据文件），但"今天供应哪个版本菜单"这块**唯一的招牌（`_latest.manifest`）只挂在主仓门口**，绝不复制——否则两个仓库各挂一块招牌，顾客会懵。

`delete`（`:100`）、`copy`（`:118`）也遵循同样的"manifest 只动主仓、其余先副后主"模式。`MirroringUpload`（`:136-159`）则把分片上传（multipart）的双写也照此办理：每个分片 `put_part` 时同时发往两仓（`:144`），`complete` 时先副后主（`:151`）。

> **这个包装器怎么被注入？** 用户把 `MirroringObjectStoreWrapper` 塞进 lance 的 `ObjectStoreParams`，再经 §6.1 的 `patch_with_store_wrapper` 打补丁进读写参数。`NativeTable::open_with_params`（`table.rs:1243`）那行 `params.patch_with_store_wrapper(wrapper)?` 就是注入点（呼应 09 §4.2）。这就是为什么"换存储后端"上层零改动——它只是参数里多塞了一个 wrapper。

## 3. Arrow 工具 `arrow.rs`：数据入口的扩展点

> 这一节呼应 `02 三大基石` 与 `04 写入链路`：用户的各种数据形态，**都在这里被统一成 Arrow**。

### 3.1 `IntoArrow`：任何数据"摆上标准餐盘"

`arrow.rs:119-122`：

```rust
pub trait IntoArrow {
    /// 把数据转成一个 Arrow 批次迭代器
    fn into_arrow(self) -> Result<Box<dyn arrow_array::RecordBatchReader + Send>>;
}
```

`IntoArrow` 是 LanceDB **数据入口的统一抽象**：任何想被 `table.add(...)` / `create_table(...)` 直接接收的类型，只要实现这个 trait，就能"摆上标准餐盘"。

最妙的是这个 **blanket impl（覆盖性实现）**（`arrow.rs:126-130`，**已验证**）：

```rust
impl<T: arrow_array::RecordBatchReader + Send + 'static> IntoArrow for T {
    fn into_arrow(self) -> Result<Box<dyn arrow_array::RecordBatchReader + Send>> {
        Ok(Box::new(self))      // 已经是 RecordBatchReader 了，装箱即可
    }
}
```

> **Rust 知识点：blanket impl（覆盖性实现）**。`impl<T: ...> IntoArrow for T` 不是"为某个具体类型实现"，而是**"为所有满足约束 `T: RecordBatchReader + Send + 'static` 的类型一次性实现"**。效果：你（或第三方）随便给出一个 Arrow `RecordBatchReader`，它**自动**就是 `IntoArrow`，无需再写一行。类比 Python 里"鸭子类型"——只要你长得像 RecordBatchReader，就被当作 IntoArrow。
>
> **为什么这是"组装而非重造"的扩展点（teaching point）？** LanceDB 不为每种数据源写专门的导入逻辑。它只定义 `IntoArrow` 这个口子：Polars 集成实现它（`arrow.rs:213-218` 的 `PolarsDataFrameRecordBatchReader`），未来任何新数据源也实现它即可。`Table::add` 内部只调一次 `into_arrow()`（见 09 §3.1 `execute`），就把"千变万化的输入"收敛成"一种内部数据流"。

### 3.2 `IntoArrowStream`：异步版的同款入口

`arrow.rs:137-140`：

```rust
pub trait IntoArrowStream {
    /// 把数据转成 Arrow 批次的【流】
    fn into_arrow(self) -> Result<SendableRecordBatchStream>;
}
```

Arrow 标准库的 `RecordBatchReader` 是**同步迭代器**（`next()` 一次拿一批，会阻塞）。但数据可能是异步产生的（比如从网络流式读入）。文档注释（`arrow.rs:136`）点明 "Arrow has no async equivalent to RecordBatchReader"——Arrow 没有官方的异步版本，于是 LanceDB 自己补了一个 `IntoArrowStream`，产出物是 `SendableRecordBatchStream`（见 §3.3）。

> 注意 §3.1 和 §3.2 的方法**同名都叫 `into_arrow`**，但属于不同 trait、返回不同类型（一个同步 Reader、一个异步 Stream）。Rust 靠"你要的是哪个 trait/哪个返回类型"来区分，不会冲突。

### 3.3 `SendableRecordBatchStream`：标准传菜推车

`arrow.rs:48-57`：

```rust
pub trait RecordBatchStream: Stream<Item = Result<arrow_array::RecordBatch>> {
    fn schema(&self) -> Arc<arrow_schema::Schema>;     // 流自带 schema
}

/// 一个装箱且 Send 的 RecordBatchStream
pub type SendableRecordBatchStream = Pin<Box<dyn RecordBatchStream + Send>>;
```

这是**全库异步数据传输的标准载体**。逐零件拆 `Pin<Box<dyn RecordBatchStream + Send>>`：

| 零件 | 含义 | 类比 |
|---|---|---|
| `Stream<Item = ...>` | 异步迭代器（`async` 版的 `Iterator`） | JS 的 `AsyncIterator` |
| `RecordBatchStream` | 在 `Stream` 基础上加"自带 schema" | 推车上贴着"装的是什么菜" |
| `dyn ... + Send` | 运行时多态，且能跨线程移动 | 接口类型 + 线程安全 |
| `Box<...>` | 堆分配（trait 对象大小不定，必须装箱） | 装进盒子 |
| `Pin<...>` | **固定在内存里不许移动** | 见下方陷阱 |

> **Rust 陷阱：`Pin` 为什么存在？** 异步 `Stream` 内部常含"自引用"结构（poll 到一半的状态机里，某个字段指向同结构的另一个字段）。一旦这种值在内存里被移动，自引用指针就会变成野指针。`Pin<Box<...>>` 的作用就是**"钉住"这个值，保证它在内存里的地址永不变**。非 Rust 读者只需记住：看到 `Pin<Box<dyn Stream>>`，就是"一个被钉死、不可移动、装箱的异步流"。
>
> **比喻**：`SendableRecordBatchStream` 是餐厅唯一标准的**传菜推车**——不管哪个后厨出的菜，最后都装上同款推车送出去。查询结果、写入数据、远程响应，内部传的都是它。

它还有两组转换适配器，体现"和 DataFusion 互通"（呼应 06 查询链路）：
- `From<lance::io::RecordBatchStream>`（`:59`）：把 lance 的流接进来。
- `into_df_stream()`（`:74-82`）：把 LanceDB 的流转成 DataFusion 的流（错误顺手包成 `DataFusionError::External`）。
- 反向 `IntoArrowStream for datafusion ... SendableRecordBatchStream`（`:154-162`）：DataFusion 的流转回 LanceDB 的流（错误转成 `Error::Runtime`）。

> 这三个适配器就是 03/06 篇里"LanceDB 流 ↔ DataFusion 流"无缝衔接的真身。`SimpleRecordBatchStream`（`:85-90`）用 `#[pin_project]` 宏做**安全的字段投影**（见下方陷阱），是这些转换的底层容器。

> **Rust 陷阱：`#[pin_project]` 与字段投影**。当一个结构体被 `Pin` 钉住时，想安全地访问它内部某个字段的 `Pin` 视图并不容易（手写极易出错）。`pin_project` 宏（`arrow.rs:85` 的 `#[pin_project::pin_project]` + `:88` 的 `#[pin]`）自动生成安全的 `project()` 方法（`:99`），把 `Pin<&mut Self>` 拆成各字段的 `Pin`。记住结论：**看到 `#[pin]` + `self.project()`，就是在对 `Pin` 结构做安全拆解**。

## 4. IPC `ipc.rs`：何时把 Arrow 序列化成字节

### 4.1 为什么需要 IPC

前面的 `SendableRecordBatchStream`、`RecordBatch` 都是**进程内的内存对象**——指针、`Arc`，没法直接发给另一台机器。一旦要**跨进程 / 跨网络**传 Arrow 数据，就必须把它**序列化成一段字节**。Arrow 官方为此定义了 IPC（Inter-Process Communication）格式。`ipc.rs` 就是这层"打包/拆包"工具。

> **比喻**：内存里的 `RecordBatch` 是摆在餐盘上的菜，不能直接快递。IPC 就是**打包台**：把菜（Arrow 数据）封进标准快递盒（IPC 字节），到对面再拆盒还原。

### 4.2 四个函数：打包、拆包、只打包 schema

`ipc.rs:14-50`，四个对称的工具函数：

| 行号 | 函数 | 方向 | 用途 |
|---|---|---|---|
| `:15` | `ipc_file_to_batches(buf: Vec<u8>)` | 字节 → 批次 | 收到字节，**拆包**成 `RecordBatchReader` |
| `:22` | `batches_to_ipc_file(batches: &[RecordBatch])` | 批次 → 字节 | 把数据**打包**成 IPC 文件字节 |
| `:39` | `schema_to_ipc_file(schema: &Schema)` | schema → 字节 | 只打包 **0 行的 schema**（建空表/传 schema 用） |
| `:46` | `ipc_file_to_schema(buf: Vec<u8>)` | 字节 → schema | 从字节里**只取 schema** |

看 `batches_to_ipc_file`（`:22`）的实现，干净利落：

```rust
pub fn batches_to_ipc_file(batches: &[RecordBatch]) -> Result<Vec<u8>> {
    if batches.is_empty() {
        return Err(Error::Other { message: "No batches to write".to_string(), source: None });
    }
    let schema = batches[0].schema();
    let mut writer = FileWriter::try_new(vec![], &schema)?;   // ① 用 arrow_ipc 的 FileWriter，写进一个 Vec<u8>
    for batch in batches {
        writer.write(batch)?;                                // ② 逐批写入
    }
    writer.finish()?;                                        // ③ 收尾（写 footer）
    Ok(writer.into_inner()?)                                 // ④ 取出底层字节缓冲
}
```

> **谁在用它？** 主要是 `remote` 模块（云端走 HTTP，必须序列化）。注意：远程模块**自己又另写了一套基于 `StreamWriter` 的序列化**（`remote/util.rs:13` 的 `batches_to_ipc_bytes`、`remote/table.rs:109`），用的是 **IPC Stream 格式**而非 File 格式。所以 `ipc.rs` 这套 File-格式函数和 `remote/util.rs` 那套 Stream-格式函数是**两套并存**的工具——贡献时别把它们搞混（File 格式有随机访问的 footer，Stream 格式是纯顺序流）。

> **`?` 链在这里很密**：`FileWriter::try_new`、`write`、`finish`、`into_inner` 每一步都可能返回 `ArrowError`，全靠 §1.4 的 `From<ArrowError> for Error` + `?` 自动收敛成 `Error::Arrow`。这一节是 §1 错误模型的最佳现场示范。

## 5. 数据清洗 `data/sanitize.rs` 与检查 `data/inspect.rs`

### 5.1 `coerce_schema`：上桌前的摆盘对齐

用户写进来的数据 schema，**不一定和表的 schema 完全一致**：表要 `FixedSizeList<f16>`（定长向量、半精度），用户可能给了 `List<f32>`（变长列表、单精度）。直接写会报错。`coerce_schema`（`data/sanitize.rs:166`，**已验证**）就是写入前的**自动对齐工序**：

```rust
pub fn coerce_schema(
    reader: impl RecordBatchReader + Send + 'static,
    schema: Arc<Schema>,
) -> Result<Box<dyn RecordBatchReader + Send>> {
    if reader.schema() == schema {                              // ① schema 已一致，直接放行
        return Ok(Box::new(RecordBatchIterator::new(reader, schema)));
    }
    let s = schema.clone();
    let batches = reader
        .zip(repeat_with(move || s.clone()))                   // ② 给每个 batch 配一份目标 schema
        .map(|(batch, s)| coerce_schema_batch(batch?, s));     // ③ 逐 batch 转换
    Ok(Box::new(RecordBatchIterator::new(batches, schema)))
}
```

> **比喻**：`coerce_schema` 是上菜前的**摆盘对齐工序**——顾客要的盘子（目标 schema）是这个规格，厨房出的菜（输入数据）规格略有出入，摆盘师傅逐盘调整到位再上桌。

控制流是三层漏斗（`sanitize.rs`）：

```
coerce_schema (:166)          逐 reader：每个 batch 配目标 schema
   └─ coerce_schema_batch (:143)   逐列：按目标 schema 的每个 field 找对应列
        └─ coerce_array (:52)      逐数组：真正做类型转换
```

最里层 `coerce_array`（`:52`）是核心，按"目标类型"分情况处理（`:56-140`）：
- 类型已相同 → 原样返回（`:56`）。
- 普通可转换类型（`can_cast_types` 为真）→ 直接 `cast`（`:61`）。
- 浮点之间（f16/f32/f64）→ 走 `cast_float_array`，且**降精度时打 `warn!` 日志**（`:65-70`）提醒可能丢精度。
- 目标是 `FixedSizeList` 而输入是 `List`/`LargeList` → **先推断维度**（调 `infer_dimension`，见 §5.2），维度对得上才转成定长向量（`:89-127`）。

> **Rust 陷阱：`unreachable!()`**。`sanitize.rs:76` 和 `:106` 出现 `unreachable!()`。它是一个宏，意思是"代码逻辑上**绝不可能**走到这里，若真走到了就 panic（说明有 bug）"。这里的逻辑保证是：外层 `match` 已经判定 `adt` 是浮点类型，所以内层再 match 时除了 f16/f32/f64 不会有别的分支。非 Rust 读者可理解成"防御性断言：到这就是程序员错了"。

> **这是写入前的"保险"（teaching point）**：04 写入链路里，数据在交给 lance 落盘前会经过这道工序，把"差不多对"的数据**强行对齐**到表 schema，避免底层因 schema 不匹配报错。它体现了 LanceDB 对用户输入的宽容。

### 5.2 `infer_vector_columns` / `infer_dimension`：哪些列是向量

`data/inspect.rs` 负责"看数据、下判断"，不改数据。两个函数：

**`infer_dimension`（`inspect.rs:18`）**——判断一个 list 列是不是"定长"（所有行长度相同），是则返回那个维度：

```rust
pub(crate) fn infer_dimension<T>(list_arr: &GenericListArray<T::Native>) -> Result<Option<T::Native>> {
    let len_arr = length(list_arr)?;                    // ① 算出每行的长度
    if len_arr.is_empty() { return Ok(Some(Zero::zero())); }
    let dim = len_arr.as_primitive::<T>().value(0);     // ② 取第一行的长度当候选维度
    let datum = PrimitiveArray::<T>::new_scalar(dim);
    if bool_and(&eq(len_arr.as_primitive::<T>(), &datum)?) != Some(true) {
        Ok(None)                                        // ③ 有任意一行长度不等 → 不是定长 → None
    } else {
        Ok(Some(dim))                                   //    全部相等 → 是定长向量，返回维度
    }
}
```

> 思路很巧：把"所有行长度都相等吗"转化成"长度数组逐元素等于第一个长度，再全体 AND"。`bool_and(eq(lens, lens[0]))` 为真即定长。

**`infer_vector_columns`（`inspect.rs:45`，已验证）**——扫一个 reader 的 schema + 数据，找出"看起来像向量列"的列名：
- `FixedSizeList<float>` → **直接**算向量列（`:54`，定长 + 浮点，铁定是向量）。
- `List<float>` / `LargeList<float>` 且 `strict=false` → 加入待定，再扫数据用 `infer_dimension` 确认"每行等长"才认（`:57-95`）。`strict=true` 时则**只认** `FixedSizeList`。

> **用途**：当用户没指定向量列时，自动推断"该给哪一列建向量索引 / 拿哪一列做向量查询"。这是"智能默认"的数据基础。

### 6.2 `TimeoutStream`：给查询流装一个计时炸弹

`utils.rs:213-216`：

```rust
pub struct TimeoutStream {
    inner: SendableRecordBatchStream,    // 被包住的真实数据流
    state: TimeoutState,                 // 计时状态机
}
```

它是个 `Stream` 包装器：**从第一次 poll 开始计时，超时后下一次 poll 直接返回超时错误**。状态机 `TimeoutState`（`utils.rs:197-206`）有三态：

```rust
enum TimeoutState {
    NotStarted { timeout },                                    // 还没开始，只记着时限
    Started { deadline: Pin<Box<tokio::time::Sleep>>, timeout },// 已启动，deadline 是个倒计时
    Completed,                                                  // 已超时/已终结
}
```

核心是 `poll_next`（`utils.rs:247`，**已验证**）的三态机：

```rust
fn poll_next(mut self: Pin<&mut Self>, cx: &mut Context) -> Poll<Option<Self::Item>> {
    match &mut self.state {
        TimeoutState::NotStarted { timeout } => {                      // ① 首次被 poll
            if timeout.is_zero() {                                     //    时限为 0 → 立刻超时
                return Poll::Ready(Some(Err(Self::timeout_error(timeout))));
            }
            let deadline = Box::pin(tokio::time::sleep(*timeout));     //    启动倒计时
            self.state = TimeoutState::Started { deadline, timeout: *timeout };
            self.poll_next(cx)                                        //    递归立刻进入 Started 分支
        }
        TimeoutState::Started { deadline, timeout } => match deadline.poll_unpin(cx) {
            Poll::Ready(_) => {                                        // ② 倒计时已到 → 超时
                let err = Self::timeout_error(timeout);
                self.state = TimeoutState::Completed;
                Poll::Ready(Some(Err(err)))
            }
            Poll::Pending => {                                         // ③ 没超时 → 转发给真实流
                let inner = Pin::new(&mut self.inner);
                inner.poll_next(cx)
            }
        },
        TimeoutState::Completed => Poll::Ready(None),                  // ④ 超时后流终结
    }
}
```

> **Rust 知识点：`Poll` 三态与 `Stream`**。异步流被运行时反复"轮询（poll）"。每次 poll 返回 `Poll::Ready(Some(x))`（出了一个值）、`Poll::Ready(None)`（流结束）或 `Poll::Pending`（还没好，待会再来）。`TimeoutStream` 的精妙在于：它把"超时倒计时"和"真实数据流"**赛跑**——先 poll 倒计时（`deadline.poll_unpin`），倒计时还 `Pending`（没到点）才去 poll 真实数据。一旦倒计时 `Ready`，立刻吐超时错误。
>
> **比喻**：`TimeoutStream` 是给传菜推车装了个**计时炸弹**：开始上菜（首次 poll）即点火，时间一到还没上完，就直接给顾客端上一张"超时"错误单。
>
> 注入点在 `table.rs:1799`：`TimeoutStream::new_boxed(inner, timeout)`，给查询结果流套上超时（呼应 06 查询链路）。

### 6.3 类型校验门禁与表名校验

`utils.rs` 还有一批"门禁函数"，决定某列/某名字是否合法。

**向量类型门禁** `supported_vector_data_type`（`utils.rs:174`，**已验证**）：

pub fn supported_vector_data_type(dtype: &DataType) -> bool {

## 9. 小结：这些设施如何支撑前面所有篇

把六个文件和前面链路篇的连接点收个网：

| 文件 | 它是什么 | 被哪些链路反复借用 |
|---|---|---|
| `error.rs` | 统一投诉单：一个 `Error` 枚举 + `Result<T>` 别名 + `From` 自动翻译 | **全部**——每个 `?`、每个 `Result` 都在用它（03/04/05/06） |
| `io/object_store.rs` | 镜像双写库管，建在 object_store/lance 三层抽象之上 | 03 连接、04 写入（经 `patch_with_store_wrapper` 注入） |
| `arrow.rs` | 数据入口扩展点 `IntoArrow` + 标准传菜推车 `SendableRecordBatchStream` | 02 基石、04 写入（`into_arrow`）、06 查询（结果流） |
| `ipc.rs` | Arrow ↔ 字节的打包台 | remote 模块（云端 HTTP 传输） |
| `data/sanitize.rs` | 写入前的摆盘对齐 `coerce_schema` | 04 写入链路 |
| `data/inspect.rs` | 向量列推断 `infer_vector_columns` | 05 建索引、06 查询（智能默认列） |
| `utils.rs` | 给 lance 参数打补丁、超时流、建索引类型门禁、表名校验 | 03/04/05/06 几乎处处 |

一句话总结全篇：**这六个文件没有一个属于"主菜"，但每道主菜都离不开它们。** 它们是 LanceDB"组装而非重造"哲学的另一种体现——错误模型组装 snafu，存储抽象组装 object_store，数据入口组装 Arrow，序列化组装 arrow_ipc。LanceDB 真正自己写的，只是把这些零件**粘合**成一套自洽的横切设施，让上层链路能心无旁骛地编排业务。

读到这里，你已经掌握了贡献 LanceDB 核心引擎所需的"后勤地图"：知道新错误往哪加（`impl From`）、新数据源往哪接（`impl IntoArrow`）、新索引的类型门禁往哪改（`supported_*`）。下次在链路篇里再看到这些零件一闪而过，你会知道它们的全貌就藏在本篇。
