## 0. 这一篇要回答的问题

一句话：**LanceDB 自己几乎不"造轮子"，它是个总装厂，把三家供应商的零件拼成一辆车。** 这三家供应商是：

- **Arrow** —— 数据的"普通话"。所有数据在内存里都长成 Arrow 的 `RecordBatch`，在三巨人之间端来端去。
- **DataFusion** —— 查询的"执行引擎"。一条查询最终被编译成 DataFusion 的 `ExecutionPlan`（执行计划），由它驱动跑起来。
- **lance** —— 数据的"存储后端"。磁盘上怎么存、向量索引（IVF/PQ/HNSW/SQ）怎么建、`Scanner` 怎么扫，全是 lance 的活。

> **比喻总钥匙（沿用并扩展餐厅家族）**：
> - **lance = 后厨**：食材仓库（磁盘列存格式）+ 灶台（`Scanner` 扫描器）+ 几道招牌菜算法（IVF/PQ/HNSW 向量索引）。
> - **DataFusion = 传菜流水线**：`ExecutionPlan` 是一张「工序单」，`UnionExec`/`RepartitionExec`/`ProjectionExec` 是流水线上的一个个工位。
> - **Arrow = 餐盘**：`RecordBatch`。无论后厨还是前厅，所有菜都用同一种餐盘端，通用、不用换盘。
> - **LanceDB 自己 = 餐厅经理**：不下厨、不传菜，只负责把客人的话翻译给后厨和流水线，再把成品端给客人。它写的代码大多是**薄薄的"翻译/适配层"**。

把分工画成一张图：

```
                        ┌─────────────────────────────┐
   你的数据 ──IntoArrow──▶│  Arrow RecordBatch (餐盘)    │◀── 贯穿全栈的数据载体
                        └──────────────┬──────────────┘
                                       │
                  ┌────────────────────┼────────────────────┐
                  ▼                    ▼                    ▼
          ┌──────────────┐   ┌──────────────────┐   ┌──────────────┐
          │   写入路径     │   │   LanceDB 编排层    │   │   查询路径     │
          │              │   │ (翻译/适配, 自己写)  │   │              │
          │ lance Dataset │   │ Builder→BuildParams│   │ lance Scanner │
          │   落盘         │   │ Stream 三方互转     │   │  ↓ create_plan│
          └──────────────┘   │ DistanceType 桥接   │   │ DataFusion    │
                  ▲          └──────────────────┘   │ ExecutionPlan │
                  │                                  │  ↓ execute_plan│
              lance(后厨)                            │ → Arrow 流回用户│
                                                     └──────┬───────┘
                                                  DataFusion(流水线)
```

记住这三句钉死职责的话，后面全是它的注脚：

1. **lance** = 磁盘列存格式 + `Dataset`/`Scanner` + 向量索引算法。
2. **DataFusion** = 查询执行引擎，提供 `ExecutionPlan` trait 与物理算子。
3. **Arrow** = 内存列存与数据交换格式，`RecordBatch`/`Schema` 贯穿全栈。

## 1. 为什么要"组装"——数据库的三件分工

一个能跑向量检索的数据库，至少要回答三个独立的问题：

| 问题 | 谁来答 | 类比 |
|---|---|---|
| 数据在**内存里**长什么样？怎么在模块间传？ | **Arrow** | 内存里的"通用数据结构" |
| 数据在**磁盘上**怎么存？索引怎么建？怎么扫？ | **lance** | 文件格式 + 存储引擎 |
| 一条**查询**怎么编排成可执行的步骤、并行跑起来？ | **DataFusion** | 查询优化器 + 执行器 |

这三件事在工程上是**正交**的——内存格式不关心磁盘怎么存，执行引擎不关心字节怎么编码。历史上每一件都有人花了多年打磨出工业级实现。LanceDB 的选择是：**不重造，全借**，自己只写把它们粘合起来的胶水。

这个选择在 `Cargo.toml` 里就能一眼看穿。先看 lance 系列（workspace 根 `Cargo.toml:23-33`）：

```toml
lance = { version = "=0.26.0", features = ["dynamodb"],
          tag = "v0.26.0-beta.1", git = "https://github.com/lancedb/lance" }   # ① 精确锁版本 + git tag
lance-io      = { version = "=0.26.0", tag = "v0.26.0-beta.1", git = "..." }
lance-index   = { version = "=0.26.0", tag = "v0.26.0-beta.1", git = "..." }
lance-linalg  = { version = "=0.26.0", tag = "v0.26.0-beta.1", git = "..." }
lance-table   = { version = "=0.26.0", tag = "v0.26.0-beta.1", git = "..." }
lance-datafusion = { version = "=0.26.0", tag = "v0.26.0-beta.1", git = "..." }
lance-encoding   = { version = "=0.26.0", tag = "v0.26.0-beta.1", git = "..." }
```

注意 `version = "=0.26.0"`（`=` 表示**精确等于**，不是默认的"兼容即可"）+ `git` + `tag`。这不是从 crates.io 拉的发布版，而是**直接指向 lancedb/lance 仓库的某个 git tag**。

> **教学点：连体婴版本锁定**。`=0.26.0` + git tag 意味着 LanceDB 和 lance 不是普通的"用第三方库"关系，而是**同一团队的孪生仓库**。改 lance 的接口会**直接打断 LanceDB 的编译**，必须严格对齐版本。你贡献代码时如果遇到"lance 某方法签名变了"，得去 lance 仓库对应 tag 看，而不是 crates.io。

再看 Arrow（`Cargo.toml:34-42`）和 DataFusion（`Cargo.toml:44-49`）——它们没有被整包引入，而是**拆成一堆细粒度 crate 按需取用**：

```toml
# Note that this one does not include pyarrow          ← Cargo.toml:34 的原注释
arrow        = { version = "54.1", optional = false }   # arrow-array/-data/-ipc/-ord/-schema/-arith/-cast 全部 =54.1
...
datafusion   = { version = "46.0", default-features = false }      # ① 关掉默认特性
datafusion-common = { version = "46.0", default-features = false } # ① 同样关掉
datafusion-catalog / -execution / -expr / -physical-plan = "46.0"
```

> **教学点：为什么拆这么细、还 `default-features = false`？** 编译期裁剪。LanceDB 只用到 Arrow/DataFusion 的一部分，按 crate 拆开就能只编译需要的那块，`default-features = false`（`Cargo.toml:46`）进一步关掉用不上的可选功能，减小体积、加快编译。**贡献者加依赖时应沿用这种最小化习惯**——别图省事引整包。

三大依赖版本（2026-06 main 分支快照）：**lance 系列 `=0.26.0`（tag `v0.26.0-beta.1`）、arrow `54.1`、datafusion `46.0`**。

> **Rust 知识点：Cargo 版本语义**
> | 写法 | 含义 | 类比 |
> |---|---|---|
> | `"54.1"` | 兼容 54.1 的任意版本（`^54.1`，即 `>=54.1, <55`） | npm 的 `^54.1` / pip 的 `~=54.1` |
> | `"=0.26.0"` | **精确**只接受 0.26.0 | npm 的 `54.1.0`（精确）/ pip 的 `==0.26.0` |
> | `git = "...", tag = "..."` | 从 git 仓库的某 tag 拉源码编译 | npm 装 git 仓库 / pip 的 `git+https://...@tag` |

## 2. Arrow：内存列式格式 —— 数据交换的"普通话"

Arrow 是一种**内存里的列式数据格式**。和你熟悉的"一行一个对象"（行式）相反，列式把同一列的值在内存里连续摆放，对分析型扫描（"把这一列全读出来算个平均"）极友好，也方便 SIMD 加速。它的核心类型只需记三个：

| Arrow 类型 | 是什么 | 类比 |
|---|---|---|
| `RecordBatch` | 一批数据（若干行 × 若干列），列式存储 | 一个 DataFrame 分片 / 一页表格 |
| `Schema` | 这批数据的"表头"：每列叫什么、什么类型 | 表结构定义 |
| `SchemaRef` | `Arc<Schema>`，可共享的 schema 句柄 | 指向同一份表头的多个引用 |

LanceDB 把 Arrow 当作**贯穿全栈的"普通话"**：用户给的数据先变成 `RecordBatch` 才能写入；查询结果也以 `RecordBatch` 流的形式返回。证据在 `arrow.rs`——这是全库最基础的工具文件，可它**开篇就同时依赖 Arrow 和 DataFusion**：

```rust
pub use arrow_schema;                                                    // arrow.rs:6   直接 re-export Arrow 的 schema
use datafusion_common::DataFusionError;                                  // arrow.rs:7   借 DataFusion 的错误类型
use datafusion_physical_plan::stream::RecordBatchStreamAdapter;          // arrow.rs:8   借 DataFusion 的流适配器
```

### 2.1 `IntoArrow`：用户数据进门的"安检口"

任何要写进 LanceDB 的数据，都得先过 `IntoArrow` 这道门，转成 Arrow：

```rust
pub trait IntoArrow {                                                    // arrow.rs:119
    fn into_arrow(self) -> Result<Box<dyn arrow_array::RecordBatchReader + Send>>;
}

impl<T: arrow_array::RecordBatchReader + Send + 'static> IntoArrow for T { // arrow.rs:126  ①
    fn into_arrow(self) -> Result<Box<dyn arrow_array::RecordBatchReader + Send>> {
        Ok(Box::new(self))
    }
}
```

> ① 这是个**泛型一揽子实现（blanket impl）**：凡是已经实现了 Arrow `RecordBatchReader` 的类型 `T`，自动就满足 `IntoArrow`。换句话说，"已经是 Arrow 数据"的东西免检直接放行。其它语言/格式（如 Polars DataFrame）则各写各的 `into_arrow` 把自己转成 Arrow。

### 2.2 三国海关：三套流类型的互转

这里有个非 Rust 读者**一定会绊倒**的坑：异步数据用"流"（Stream，可理解为异步迭代器）表示，而三巨人各有各的流类型：

- **lance 的流**：`lance::io::RecordBatchStream`
- **LanceDB 自己的流**：`SendableRecordBatchStream`（`arrow.rs:57`）
- **DataFusion 的流**：`datafusion_physical_plan::SendableRecordBatchStream`

LanceDB 先定义自己的流接口和类型别名：

```rust
pub trait RecordBatchStream: Stream<Item = Result<arrow_array::RecordBatch>> {  // arrow.rs:48
    fn schema(&self) -> Arc<arrow_schema::Schema>;
}
pub type SendableRecordBatchStream = Pin<Box<dyn RecordBatchStream + Send>>;     // arrow.rs:57
```

> **两个"同名陷阱"**：LanceDB 的 `SendableRecordBatchStream`（`arrow.rs:57`）和 DataFusion 的 `datafusion_physical_plan::SendableRecordBatchStream` **名字一模一样，却是两个不同的类型**。读代码看到这个名字，先确认它来自哪个模块，否则会困惑"为什么还要转换"。

正因为是三套不同类型，跨边界传数据必须"换护照"。`arrow.rs` 里专门写了**三个转换 impl**，就像三国边境的三个海关：

| 转换方向 | 实现位置 | 干什么 |
|---|---|---|
| lance 流 → LanceDB 流 | `arrow.rs:59-68` | `impl From<I> for SendableRecordBatchStream`，把任意 lance 流包成自家流 |
| LanceDB 流 → DataFusion 流 | `arrow.rs:74-82`（`into_df_stream`） | 用 `RecordBatchStreamAdapter` 包装，并把 LanceDB 错误转成 `DataFusionError::External` |
| DataFusion 流 → LanceDB 流 | `arrow.rs:154-162`（`IntoArrowStream`） | 把 DataFusion 错误转成 `Error::Runtime`，包回自家流 |

看其中一个（lance → LanceDB，`arrow.rs:59-68`）：

```rust
impl<I: lance::io::RecordBatchStream + 'static> From<I> for SendableRecordBatchStream {  // ①
    fn from(stream: I) -> Self {
        let schema = stream.schema();
        let mapped_stream = Box::pin(stream.map(|r| r.map_err(Into::into)));             // ② 顺手翻译错误
        Box::pin(SimpleRecordBatchStream { schema, stream: mapped_stream })
    }
}
```

再看 LanceDB → DataFusion（`arrow.rs:74-82`），注意它如何**翻译错误**：

```rust
fn into_df_stream(self) -> datafusion_physical_plan::SendableRecordBatchStream {
    let schema = self.schema();
    Box::pin(RecordBatchStreamAdapter::new(
        schema,
        self.map_err(|ldb_err| DataFusionError::External(ldb_err.into())),  // ③ 闭包：LanceDB 错误→DataFusion 错误
    ))
}
```

> **Rust 陷阱：跨库的错误必须手动翻译**。三套库各有自己的 `Error` 类型。Rust 的 `?` 运算符想自动传播错误，前提是"目标错误类型能从源错误类型 `From` 转过来"。跨到 DataFusion 边界时没有现成的 `From`，所以得用 `.map_err(|e| ...)` 这个闭包（③）**手动把一种错误翻成另一种**。这是 Rust `Result` 体系最常见的"摩擦点"。比喻：每个海关不仅换护照（类型），还得换签证（错误）。

> **Rust 陷阱：`Pin<Box<dyn Trait + Send>>` 是什么妖怪？**（`arrow.rs:57`）
> | 零件 | 作用 | 一句话 |
> |---|---|---|
> | `dyn RecordBatchStream` | 运行时多态 | "面向接口的指针"，类似 Java 接口引用 |
> | `Box<...>` | 堆分配 | 把大小不定的东西装箱放堆上 |
> | `Pin<...>` | 钉住内存地址 | async 自引用结构要求地址不能动 |
> | `... + Send` | 跨线程通行证 | 可以安全地塞给别的线程 |
>
> 非 Rust 读者把这一整坨**当成"一个可跨线程传递的异步迭代器句柄"**即可，不必拆解。

## 3. DataFusion：查询执行引擎 —— 把查询编译成"工序单"

DataFusion 是一个用 Rust 写的**查询引擎**：你给它一棵"执行计划树"，它负责并行、分批、流式地把结果跑出来。LanceDB 借的核心是两样东西：

1. `ExecutionPlan` trait —— "执行计划"这个抽象本身。一棵 `ExecutionPlan` 树就是一张「工序单」。
2. 一组现成的**物理算子**（工序单上的"工位"），LanceDB 偶尔需要亲手拼装计划时会用到。

`table.rs` 头部把这些物理算子明明白白导进来：

```rust
use datafusion_physical_plan::display::DisplayableExecutionPlan;   // table.rs:16  渲染计划成文本(explain)
use datafusion_physical_plan::projection::ProjectionExec;          // table.rs:17  投影(选列/造列)
use datafusion_physical_plan::repartition::RepartitionExec;        // table.rs:18  重分区
use datafusion_physical_plan::union::UnionExec;                    // table.rs:19  合并多路
use datafusion_physical_plan::ExecutionPlan;                       // table.rs:20  计划 trait
```

### 3.1 `ExecutionPlan` 是查询层的"公共货币"

LanceDB 查询层的核心 trait `ExecutableQuery`，其 `create_plan` 方法**直接返回 DataFusion 类型**：

```rust
fn create_plan(                                                    // query.rs:551
    &self,
    options: QueryExecutionOptions,
) -> impl Future<Output = Result<Arc<dyn ExecutionPlan>>> + Send;  // query.rs:554  ← 返回 Arc<dyn ExecutionPlan>
```

返回类型是 `Arc<dyn ExecutionPlan>`。这说明 **DataFusion 的 `ExecutionPlan` 就是 LanceDB 查询层流通的"公共货币"**——查询的每一步都围着它转。

> **Rust 知识点：`Arc<dyn ExecutionPlan>`**。`Arc` = 原子引用计数智能指针（**印多张遥控器控同一台电视**：`clone` 只是计数 +1，不复制计划本身）；`dyn ExecutionPlan` = 面向"执行计划接口"编程，运行时才知道具体是哪种算子。合起来 = **多个持有者共享同一个查询计划对象**，且能跨线程。

### 3.2 多数时候：让 lance 把 Scanner "编译"成计划

绝大多数查询，LanceDB **不亲手拼计划**，而是把意图填进 lance 的 `Scanner`，再让 lance 自己 `create_plan` 编译出 DataFusion 计划（详见 §4）。这是 lance↔DataFusion 的**关键缝合点之一**，留到 §4 讲。

### 3.3 少数时候：亲手拼装计划（`multi_vector_plan`）

只有在 lance 的 `Scanner` 表达不了的场景，LanceDB 才直接调 DataFusion 物理层 API 手搓计划。**多向量查询**就是这样一处（`table.rs:1109` 起的 `multi_vector_plan`）：对每个子查询计划加一列 `query_index` 标记它来自第几个查询，然后合并、收敛到单分区：

```rust
let projection = ProjectionExec::try_new(projections, plan).unwrap();  // table.rs:1143  ① 给每路计划注入 query_index 列
// ...对每路都做完投影后...
let unioned = Arc::new(UnionExec::new(projected_plans));               // table.rs:1148  ② 把多路 union 成一路
let repartitioned = RepartitionExec::try_new(                         // table.rs:1150  ③ 重分区
    unioned,
    datafusion_physical_plan::Partitioning::RoundRobinBatch(1),        // table.rs:1152      收敛到 1 个分区
).unwrap();
Ok(Arc::new(repartitioned))                                           // table.rs:1155
```

> **比喻**：`ProjectionExec`（投影工位）给每盘菜贴上"这是第几号查询点的"标签；`UnionExec`（合并工位）把几条流水线的菜汇到一条；`RepartitionExec` + `RoundRobinBatch(1)`（收口工位）把所有菜归拢到一个出菜口。这是 LanceDB **直接当流水线工程师**的少数地方——平时它只下订单，这里破例亲自排工位。

### 3.4 列名等"语义约定"也借自 lance/lance_index

连"距离列叫什么名、全文检索打分列叫什么名"这种约定，LanceDB 都**复用 lance 的定义**，而不自立门户（`query.rs` 头部）：

```rust
use lance::{ arrow::RecordBatchExt, dataset::{scanner::DatasetRecordBatchStream, ROW_ID} }; // query.rs:14-16
use lance_index::scalar::inverted::SCORE_COL;   // query.rs:19  全文检索的"分数"列名
use lance_index::scalar::FullTextSearchQuery;   // query.rs:20  全文检索查询类型
use lance_index::vector::DIST_COL;              // query.rs:21  向量检索的"距离"列名
```

## 4. lance：磁盘列存 + 存储/索引引擎 —— 真正的后厨

lance 是 LanceDB **真正的存储后端**，负责三件大事：磁盘列存格式、`Dataset`/`Scanner` 读写、向量索引算法。`table.rs` 头部的导入清单，本身就是一张"我从 lance 借了什么"的账单：

```rust
use lance::dataset::builder::DatasetBuilder;                         // table.rs:22  打开数据集
use lance::dataset::scanner::Scanner;                               // table.rs:25  扫描器
use lance::dataset::{ InsertBuilder, ..., WriteParams };            // table.rs:30-33 写入
use lance::index::vector::utils::infer_vector_dim;                 // table.rs:34  推断向量维度
use lance_datafusion::exec::{analyze_plan as lance_analyze_plan, execute_plan}; // table.rs:36 执行计划
use lance_index::vector::hnsw::builder::HnswBuildParams;            // table.rs:38  HNSW 建索引参数
use lance_index::vector::ivf::IvfBuildParams;                      // table.rs:39  IVF
use lance_index::vector::pq::PQBuildParams;                        // table.rs:40  PQ
use lance_index::vector::sq::builder::SQBuildParams;               // table.rs:41  SQ
use lance_index::{DatasetIndexExt, IndexType};                    // table.rs:42-43 建索引扩展 trait
use lance_table::format::Manifest;                                // table.rs:44  表元数据格式
```

> **Rust 知识点：`use ... as ...` 重命名导入**（`table.rs:36`）。`analyze_plan as lance_analyze_plan` 把导入的 `analyze_plan` 改个名，因为本 crate 内可能已有同名符号，避免撞车。类比 Python 的 `import x as y`。

### 4.1 缝合点一：lance `Scanner` → DataFusion `ExecutionPlan`

这是全篇最重要的一处缝合（`table.rs` 的 `create_plan`）。流程是：**从 `Dataset` 拿一个 `Scanner` → 把查询的各项意图逐一设进去 → 让 lance 把它编译成 DataFusion 计划**。

```rust
let mut scanner: Scanner = ds_ref.scan();                  // table.rs:2119  ① 后厨点起灶台(拿 Scanner)
// ... 逐项设置扫描意图：
scanner.nearest(&column, query_vector, limit)?;           // table.rs:2136/2142  最近邻搜索
scanner.limit(...)?;  scanner.nprobs(query.nprobes);       // table.rs:2149/2153  限制/探针数
scanner.filter(sql)?;                                      // table.rs:2193       SQL 过滤
scanner.full_text_search(fts.clone())?;                   // table.rs:2205       全文检索
scanner.distance_metric(distance_type.into());            // table.rs:2213       距离度量(注意 .into() 桥接,见 §4.4)
// ...
Ok(scanner.create_plan().await?)                          // table.rs:2216  ② 把"点好的菜单"编译成"工序单"
```

> **比喻**：`ds_ref.scan()` 是后厨点起灶台拿到一张空菜单；中间那一串 `scanner.xxx()` 是在菜单上勾选"要最近邻、限 10 条、加这个过滤、按 cosine 算距离"；最后 `scanner.create_plan()`（`table.rs:2216`）把这张**点好的菜单编译成流水线的工序单**（`Arc<dyn ExecutionPlan>`）。妙处在于：**lance 既是后厨，又兼任"把订单转成工序单"的工头**——它知道自己的磁盘布局和索引，所以由它来生成执行计划最合适。

### 4.2 缝合点二：执行计划 → Arrow 流（`query.rs`）

计划生成后，谁来"按工序单出菜"？是 lance 包装过的 DataFusion 执行器（`query.rs`）：

```rust
let plan = self.create_plan(options.clone()).await?;          // query.rs:1092  拿到 ExecutionPlan
let inner = execute_plan(plan, Default::default())?;          // query.rs:1093  ① 来自 lance_datafusion::exec, 执行!
// ...
Ok(DatasetRecordBatchStream::new(inner).into())              // query.rs:1099  ② 结果转回 LanceDB 的 Arrow 流
```

> ① `execute_plan` 来自 `lance_datafusion::exec`（`query.rs:18` 导入）——又一次"委托 lance"。② 末尾的 `.into()` 触发 §2.2 那个 `From<lance 流>` 转换，把 lance 出来的结果流换护照成 LanceDB 自家的 `SendableRecordBatchStream` 还给用户。`analyze_plan`（运行计划并收统计）同理委托 lance：`lance_analyze_plan(plan, Default::default()).await?`（`table.rs:2233`）。

### 4.3 索引参数翻译：点菜单（Builder）→ 备料卡（BuildParams）

面向用户的索引 Builder 定义在 `index/vector.rs`，它们只是**收集参数的"点菜单"**，本身不含任何算法。四种 Builder：`IvfFlatIndexBuilder`（`index/vector.rs:178`）、`IvfPqIndexBuilder`（:224）、`IvfHnswPqIndexBuilder`（:290）、`IvfHnswSqIndexBuilder`（:338）。

真正建索引时，`table.rs` 把这些 Builder **翻译成 lance 的索引参数类型**。以 IVF-PQ 为例（`table.rs:1512`）：

```rust
let lance_idx_params = lance::index::vector::VectorIndexParams::ivf_pq(  // table.rs:1512
    num_partitions as usize,
    /*num_bits=*/ 8,                       // ① 用户没填的内部参数,这里写死
    num_sub_vectors as usize,
    index.distance_type.into(),            // ② DistanceType 桥接到 lance(见 §4.4)
    index.max_iterations as usize,
);
```

IVF-HNSW-PQ 则把三段子参数分别翻译再组合（`table.rs:1574-1589`）：

```rust
let mut ivf_params = IvfBuildParams::new(num_partitions as usize);      // table.rs:1574
let hnsw_params = HnswBuildParams::default()                           // table.rs:1577
    .num_edges(index.m as usize)                                       // table.rs:1578
    .ef_construction(index.ef_construction as usize);                  // table.rs:1579
let pq_params = PQBuildParams { num_sub_vectors: ..., ..Default::default() }; // table.rs:1580
let lance_idx_params = VectorIndexParams::with_ivf_hnsw_pq_params(     // table.rs:1584
    index.distance_type.into(), ivf_params, hnsw_params, pq_params);
```

翻译完，**真正"建"的动作再次落到 lance**（IVF-Flat 处，`table.rs:1472-1480`，四种索引同款）：

```rust
dataset.create_index(                          // table.rs:1473
    &[field.name()], IndexType::Vector, None, &lance_idx_params, replace,
).await?;
```

> **比喻**：`IvfPqIndexBuilder` 是客人填的**点菜单**（友好字段：分多少区、几次迭代），`VectorIndexParams::ivf_pq(...)`（`table.rs:1512`）是后厨内部的**备料卡**（带 `num_bits=8` 这类内部参数）。LanceDB 在交单前把菜单换成备料卡，**算法实现一行都没写**——全在 lance。

> **Rust 知识点：扩展 trait `DatasetIndexExt`**。`dataset.create_index(...)` 这个方法**并不定义在 lance 的 `Dataset` 类型本身**，而来自 `lance_index::DatasetIndexExt`（`table.rs:42` 导入）。这是"扩展 trait"模式：从外部 crate 给一个你不拥有的类型**附加方法**，必须 `use` 那个 trait 才能调用 `.create_index()`。非 Rust 读者常困惑"方法到底定义在哪"——答案是另一个 crate 的 trait 里。

> **Rust 知识点：宏生成 setter（方法"凭空出现"）**。`index/vector.rs:48` 起用 `macro_rules!` 定义了 `impl_distance_type_setter!`、`impl_ivf_params_setter!` 等宏，再在各 Builder 的 `impl` 块里 `impl_distance_type_setter!()` 一行展开（如 `index/vector.rs:199/251/322`）。读 Builder 时你会发现某些 setter 方法"凭空出现"——其实是宏在**编译期展开**生成的。类比：代码模板批量生成重复方法。

### 4.4 对外稳定枚举、对内桥接 lance：`DistanceType`

§4.1/§4.3 反复出现的 `.into()`，桥接的是 `DistanceType`。LanceDB **没有直接暴露 lance 的距离类型**，而是自己定义了一个枚举（`lib.rs:222-247`）：

```rust
#[derive(Debug, Copy, Clone, PartialEq, Serialize, Deserialize)]
#[non_exhaustive]                              // lib.rs:222  ① 保留未来加变体的权利
pub enum DistanceType { L2, Cosine, Dot, Hamming }  // lib.rs:224-246
```

然后用**双向 `From`** 和底层算法库 `lance_linalg::distance::DistanceType` 互转（`lib.rs:255-275`）：

```rust
impl From<DistanceType> for LanceDistanceType {       // lib.rs:255  LanceDB → lance
    fn from(value: DistanceType) -> Self {
        match value { DistanceType::L2 => Self::L2, /* ... */ }
    }
}
impl From<LanceDistanceType> for DistanceType { /* ... */ }   // lib.rs:266  lance → LanceDB
```

> **教学点：适配层=翻译官**。LanceDB 自己的 `DistanceType` 是"对客人说的话"，`From`/`Into` 转换是把客人的话翻译成后厨（`lance_linalg`）听得懂的术语。**对外暴露稳定 API、对内桥接 lance**——这是整个 LanceDB 的典型模式（`SendableRecordBatchStream`、各 `IndexBuilder` 同理）。

> **Rust 陷阱：`#[non_exhaustive]`**（`lib.rs:222`）。这个标记宣告"这个枚举将来可能加新变体"。后果是：**下游对它 `match` 必须写 `_` 通配分支**，否则将来加变体会编译失败。这是库作者保留向后兼容扩展权的方式。**贡献者改这个枚举要格外小心**——它是对外稳定 API 的一部分；相比之下，改 §2.2 那些内部桥接逻辑要安全得多。

## 5. 三者如何在一次请求里接力

把前面的零件串成一条完整生命周期。**写入路径**（左）和**查询路径**（右）共用 Arrow 这只餐盘：

```
 写入: table.add(data).execute()                  查询: table.query()...execute()
        │                                                 │
        │ ① IntoArrow::into_arrow (arrow.rs:119)          │ ① 把查询意图设进 lance Scanner
        ▼                                                 ▼   ds_ref.scan() (table.rs:2119)
   Arrow RecordBatch ─────[ 同一只餐盘 ]────────┐         scanner.nearest/filter/limit...
        │                                       │         │
        │ ② 交给 lance Dataset 写盘              │         │ ② scanner.create_plan() (table.rs:2216)
        ▼                                       │         ▼   → Arc<dyn ExecutionPlan>  (DataFusion)
   lance: 列存落盘, 产生新版本                    │         │
   (后厨把食材入库)                              │         │ ③ execute_plan(plan) (query.rs:1093)
                                                │         ▼   (lance_datafusion 驱动流水线跑起来)
                                                │    DatasetRecordBatchStream
                                                │         │
                                                └─────────┤ ④ .into() 换护照 (arrow.rs:59)
                                                          ▼   → LanceDB SendableRecordBatchStream
                                                     Arrow 流 回到用户手里 (query.rs:1099)
```

逐步对应三巨人：

| 步骤 | 谁主导 | 行号 |
|---|---|---|
| 用户数据 → Arrow | LanceDB 适配层（`IntoArrow`） | `arrow.rs:119` |
| 写盘 / 持久化 | **lance** | `table.rs`（`InsertBuilder`，见 09 篇 §4.2） |
| 查询意图 → `Scanner` → 计划 | LanceDB 编排 + **lance** 编译 | `table.rs:2119`、`2216` |
| 执行计划 → 出结果 | **DataFusion**（由 lance_datafusion 驱动） | `query.rs:1093` |
| 结果流 → 还给用户 | LanceDB 适配层（流互转） | `query.rs:1099`、`arrow.rs:59` |

**一条链路里，Arrow 全程在场（餐盘），lance 管两头（入库 + 编译计划 + 出菜执行器），DataFusion 管中间（按工序单跑），LanceDB 只在接缝处当翻译官。**

## 6. 边界澄清：哪些是 lancedb 自己的、哪些是借来的

这是贡献者最该带走的一张表——**改哪儿安全、改哪儿危险，取决于它属于谁**。

| 东西 | 属于谁 | 在哪取证 |
|---|---|---|
| `RecordBatch` / `Schema` / `SchemaRef`（内存数据） | **Arrow**（借） | `arrow.rs:6` re-export |
| `ExecutionPlan` trait + 物理算子（Union/Repartition/Projection） | **DataFusion**（借） | `table.rs:17-20` |
| 计划的执行器 `execute_plan` / `analyze_plan` | **lance**（借，`lance_datafusion`） | `query.rs:1093`、`table.rs:2233` |
| 磁盘列存格式 + `Dataset` / `Scanner` / `InsertBuilder` | **lance**（借） | `table.rs:22-33` |
| 向量索引算法（IVF/PQ/HNSW/SQ）+ `*BuildParams` | **lance**（借，`lance_index`） | `table.rs:38-41` |
| 距离计算实现 | **lance**（借，`lance_linalg`） | `lib.rs:218` |
| 列名约定 `ROW_ID` / `DIST_COL` / `SCORE_COL` | **lance**（借） | `query.rs:16/19/21` |
| 对外的 `DistanceType` 枚举（稳定 API） | **LanceDB 自己** | `lib.rs:224` |
| 自家流类型 `SendableRecordBatchStream` + 三方互转 | **LanceDB 自己** | `arrow.rs:57/59/74/154` |
| `IntoArrow` / `IntoArrowStream` 入门转换 | **LanceDB 自己** | `arrow.rs:119/137` |
| 各索引 `Builder`（点菜单）+ Builder→BuildParams 翻译 | **LanceDB 自己** | `index/vector.rs:178`、`table.rs:1512` |

> **三个"组装而非重造"的铁证**，钉死结论：
> 1. **向量索引**：LanceDB 只把 Builder 翻译成 lance 的 `VectorIndexParams`/`*BuildParams`（`table.rs:1512-1589`），算法全在 lance。
> 2. **查询执行**：委托 `lance_datafusion::exec::execute_plan`（`query.rs:1093`）与 `scanner.create_plan()`（`table.rs:2216`）。
> 3. **距离计算**：用 `lance_linalg::distance::DistanceType`（`lib.rs:218`）。
>
> **给贡献者的安全指南**：改"LanceDB 自己的"桥接/适配逻辑（流互转、Builder 翻译）相对安全；改"对外稳定 API"（`#[non_exhaustive]` 的 `DistanceType`）要谨慎；想改"借来的"行为（索引算法、磁盘格式），多半要去 **lance 仓库**改，再回来对齐版本 tag。

## 9. 小结 & 下一篇

- **三巨人分工钉死一句话**：Arrow = 内存列存/数据交换（餐盘，`RecordBatch` 贯穿全栈）；lance = 磁盘列存 + `Dataset`/`Scanner` + 向量索引算法（后厨）；DataFusion = 查询执行引擎 + `ExecutionPlan`/物理算子（流水线）。
- **LanceDB 自己写的多是薄适配层**：定义自家 trait（`RecordBatchStream`/`IntoArrow`）、把 Builder 翻译成 lance 的 `*BuildParams`、把 lance `Scanner` 转成 DataFusion 计划、再把结果流转回 Arrow。
- **两个关键缝合点**：`table.rs:2216`（lance `Scanner` → DataFusion 计划）与 `query.rs:1093`（执行计划 → Arrow 流）。记住它们，整条数据流就串起来了。
- **"组装而非重造"是 LanceDB 的灵魂**——README 那句口号在 `table.rs:1512`、`query.rs:1093`、`lib.rs:218` 三处有字面证据。

理解了三大基石后，再回到 `09 Table 解剖（上）`：你会发现那篇里 `NativeTable` 的每个方法"拿锁 + 构造 lance 参数 + 委托 lance"的套路，正是本篇"组装"心智模型在单个文件里的落地。**接下来的篇章会逐个钻进巨人内部**——`DatasetConsistencyWrapper` 怎么管 lance `Dataset` 的一致性、查询计划在 DataFusion 里怎么调度、Arrow 列存怎么编码。本篇是它们共同的地图。
