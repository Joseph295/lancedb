## 0. 这一篇要回答的问题

一句话：**LanceDB 的 Rust 核心 crate 到底由哪些零件组成，它们怎么分层，我该从哪个文件读起。**

先给一个锚点比喻。把 LanceDB 想象成一座**自动化图书馆**：

- 你（用户）走到**前台**说"我要存这批书 / 我要找跟这本最像的书"——前台就是 `Connection` / `Table`。
- 前台不亲自搬书，它把活儿派给**后厨/书库管理员**——本地书库（`NativeTable`）或云端书库（`RemoteTable`）。
- 真正的钢筋水泥（书架、检索卡片、搬运车）不是 LanceDB 自己造的，而是**站在三个巨人肩膀上**：`lance`（磁盘上的书架格式）、`arrow`（内存里的标准托盘）、`datafusion`（搬书的施工队）。

这就是本系列反复强调的**核心心智模型**：

> **LanceDB 核心层是"总包工头"，负责组装而非重造**——它把 lance（磁盘列存）、Arrow（内存列存）、DataFusion（执行引擎）三个成熟构件拼装成一个好用的向量数据库，而不是自己从零炼钢。

整座建筑的剖面图：

```
        你的代码 (Rust / Python / JS)
              │
   ┌──────────▼───────────┐
   │      绑定层 (薄壳)      │   nodejs/ (napi)   python/ (pyo3)
   │  只做类型转换 + 转发     │   都用 path 依赖核心 crate
   └──────────┬───────────┘
              │  调用 lancedb::*
   ┌──────────▼───────────┐
   │   核心层 lancedb crate │  ← 本系列主战场  rust/lancedb/src
   │  Connection / Table /  │     "组装而非重造"
   │  query / index / ...   │
   └──────────┬───────────┘
              │  use lance::* / arrow::* / datafusion::*
   ┌──────────▼───────────────────────────────────┐
   │                  基石层 (三巨人)                 │
   │  lance 0.26      arrow 54.1      datafusion 46.0 │
   │  磁盘列存格式      内存列存格式      SQL 执行引擎      │
   └───────────────────────────────────────────────┘
```

下面六节，§1 讲它是什么，§2 拆三层，§3 用代码坐实"组装而非重造"，§4 给核心层模块地图（这是本篇最实用的一张表），§5 预览一个请求怎么走，§6 给你一条阅读路线。

## 1. LanceDB 是什么

`lib.rs` 顶部 4–16 行是整个库的"门口介绍牌"（Rust 里 `//!` 开头是**库级文档注释**，会被渲染进 API 文档）。它自报家门（`lib.rs:4-5`）：

> LanceDB 是一个为向量检索而生、带持久化存储的开源数据库，极大简化了 embedding 的检索、过滤与管理。

`lib.rs:8-14` 列出的核心特性，翻成人话：

| 特性（`lib.rs` 行） | 人话解释 |
|---|---|
| `:8` 生产级向量检索、**无服务器** | 进程内嵌入式运行，不用单独起一个数据库服务 |
| `:9` 存储向量 + 元数据 + **多模态** | 文本、图片、视频、点云都能塞 |
| `:10` 向量相似 + **全文检索 + SQL** | 三种检索能力一站式 |
| `:11` **Rust / Python / JS 原生** | 三种语言都有原生绑定（这就是 §2 的绑定层） |
| `:12` **零拷贝、自动版本化** | 时间旅行不需要额外基础设施 |
| `:13` 建向量索引支持 **GPU** | 注意 `:16` 脚注：仅 Python SDK |

它能接三种"地址"（`lib.rs:49-52`），这决定了你的数据存哪儿：

| 路径形式 | 含义 |
|---|---|
| `/path/to/database` | 本地文件系统 |
| `s3://...` / `gs://...` | 云对象存储 |
| `db://dbname` | Lance Cloud（云托管） |

**心智锚点**：LanceDB ≈ "一个嵌入在你进程里的、专精向量检索的图书馆"。它不是一个你要去连接的远程服务（除非你用 `db://`），而是一个库（crate / 包），`cargo add lancedb` 就装进来了（`lib.rs:20-24`）。

## 2. 三层架构全景图

把上面那张剖面图按"职责"逐层说清。

### 2.1 绑定层（binding，薄壳）

位置：仓库里的 `nodejs/` 和 `python/` 两个目录（**不在** `rust/lancedb/src` 里）。

它们是给 JS / Python 程序员用的"翻译窗口"：把 JS/Python 的对象翻译成 Rust 能懂的类型，调用核心层，再把结果翻译回去。关键证据是——**它们都用 `path` 直接依赖核心 crate**：

- `nodejs/Cargo.toml:21`：`lancedb = { path = "../rust/lancedb" }`，用 `napi` 2.16（`nodejs/Cargo.toml:22`）做 Node.js 桥接。
- `python/Cargo.toml:18`：`lancedb = { path = "../rust/lancedb", default-features = false }`，用 `pyo3` 0.23 + `abi3-py39`（`python/Cargo.toml:20`）做 CPython 桥接；编出来的 Python 扩展库名叫 `_lancedb`（`python/Cargo.toml:13`）。

两者都把 `remote` / `fp16kernels` 这两个 feature 转发给核心 crate（`nodejs/Cargo.toml:36-37`、`python/Cargo.toml:37-38`），意思是"绑定层不重新发明开关，只是把核心层的开关引出来"。

> **为什么绑定层这么薄？** 因为真正的逻辑全在核心层。绑定层只做"类型转换 + 转发"，所以本系列基本不碰它——你读懂了核心层，三种语言的行为就都懂了。

### 2.2 核心层（`rust/lancedb` crate）—— 本系列主战场

位置：`/Users/xujunhong/lancedb/rust/lancedb/src`，顶层 17 个 `.rs` 文件共约 9169 行，加上子模块约 8978 行。

这一层定义了所有对外概念：怎么连库（`Connection`）、怎么管表（`Database`）、表长什么样（`Table` / `BaseTable`）、怎么查（`query`）、怎么建索引（`index`）、怎么算 embedding（`embeddings`）。**它本身几乎不碰磁盘 I/O 的底层细节，而是调用基石层。**

### 2.3 基石层（三巨人）

核心层站在三个成熟构件上（版本来自根 `Cargo.toml`）：

| 巨人 | 版本 | 角色（比喻） | 它负责什么 |
|---|---|---|---|
| **lance** | `=0.26.0`（根 `Cargo.toml:24`） | 地基钢筋 | 磁盘上的列式存储格式、版本管理、向量索引落盘 |
| **arrow** | `54.1`（根 `Cargo.toml:35`） | 标准托盘 | 内存里的列式数据格式（`RecordBatch` / `Schema`），零拷贝传递 |
| **datafusion** | `46.0`（根 `Cargo.toml:44`） | 施工队 | SQL / 查询计划的执行引擎 |

> **三巨人肩膀（比喻家族）**：lance = 地基钢筋（磁盘列存格式），arrow = 工地内的标准托盘（内存列存），datafusion = 施工队（执行引擎）。LanceDB 核心层是总包工头，把三者组装成楼，自己不炼钢。

## 3. "组装而非重造"——用依赖与导入作证据

这不是一句口号，代码里有铁证。

### 3.1 证据一：`Cargo.toml` 把三巨人全锁死版本

根 `Cargo.toml` 把 lance 全家桶锁在同一个版本、同一个 git tag（根 `Cargo.toml:24-33`）：

```toml
lance         = { version = "=0.26.0", ... }                       # 根 Cargo.toml:24
lance-io      = { version = "=0.26.0", tag = "v0.26.0-beta.1", ... } # :27
lance-index   = { version = "=0.26.0", tag = "v0.26.0-beta.1", ... } # :28
lance-linalg  = { version = "=0.26.0", tag = "v0.26.0-beta.1", ... } # :29
lance-table   = { version = "=0.26.0", ... }                       # :30
lance-datafusion / lance-encoding = ...                            # :32-33
```

`=0.26.0` 里的 `=` 是 Cargo 的**精确版本锁**（不是 `^0.26` 那种"兼容即可"）——这说明核心层和 lance 是"贴身共舞"，版本必须严丝合缝。

核心 crate 自己的 `rust/lancedb/Cargo.toml` 则把这些都 `workspace = true` 引进来（`rust/lancedb/Cargo.toml:31-38`），同时直接依赖 arrow 全家桶（`:14-20`）和 datafusion 的子 crate（`:22-26`：`datafusion-catalog` / `-common` / `-execution` / `-expr` / `-physical-plan`）。

其它几个支撑性依赖也值得记一眼：

| 依赖（`rust/lancedb/Cargo.toml` 行） | 作用 |
|---|---|
| `:41` `tokio`（`rt-multi-thread`） | 异步运行时（`async/await` 的"发动机"） |
| `:43` `async-trait` | 让 trait 里能写 `async fn` 的宏（见 §4 陷阱） |
| `:28` `snafu` | 结构化错误类型（`error.rs` 的基础） |
| `:39` `moka` | 异步缓存 |
| `:45` `futures` | 异步流 / 组合子工具箱 |

### 3.2 证据二：`lib.rs` 直接把 lance 的类型拿来用

最直白的一处在 `lib.rs:218`：

```rust
use lance_linalg::distance::DistanceType as LanceDistanceType;  // ① 把 lance 的距离类型起个别名
```

然后 LanceDB 自己的 `DistanceType` 枚举（`lib.rs:224-247`，有 `L2` / `Cosine` / `Dot` / `Hamming` 四种）干脆通过 `From` **直接和 lance 的类型互转**（`lib.rs:255-264`）：

```rust
impl From<DistanceType> for LanceDistanceType {        // ① 我的类型 → lance 的类型
    fn from(value: DistanceType) -> Self {
        match value {
            DistanceType::L2 => Self::L2,              // ② 一一对应,本质就是转发
            DistanceType::Cosine => Self::Cosine,
            DistanceType::Dot => Self::Dot,
            DistanceType::Hamming => Self::Hamming,
        }
    }
}
```

LanceDB 没有重新实现"什么是 L2 距离"，它只是给 lance 的距离类型套了一层自己的壳（为了不在公开 API 里暴露 lance 内部类型）。**这就是"组装而非重造"最小、最干净的一个样本。**

> **Rust 陷阱 · `#[non_exhaustive]`（`lib.rs:222`）**：`DistanceType` 枚举头上有 `#[non_exhaustive]`。它的意思是"我以后可能还会加新的距离类型"，因此**下游用 `match` 处理它时必须写一个 `_ =>` 兜底分支**，否则上游一加变体，你的代码就编译不过。类比：给 API 留了一张"以后还会加菜"的免责声明。

### 4.1 `pub mod` vs `pub use`：门牌图 vs 大门口的名牌

`lib.rs` 干了两件事，别混淆：

- **`pub mod ...`（`:193-210`）**：声明"有哪些楼"，决定**文件树结构**。
- **`pub use ...`（`:216-219`、`:292`）**：把几个最常用的符号"提"到 crate 顶层，决定**外部能写多短的路径**：

```rust
pub use connection::Connection;     // lib.rs:216  → 用户写 lancedb::Connection
pub use error::{Error, Result};     // lib.rs:217  → lancedb::Error / lancedb::Result
pub use table::Table;               // lib.rs:219  → lancedb::Table
pub use connection::connect;        // lib.rs:292  → lancedb::connect(...)
```

> **门牌总览（比喻）**：`lib.rs` 像小区入口的楼栋分布图——`pub mod` 列出有哪些楼，`pub use` 是把几个常用住户的名字直接贴在大门口，省得访客走进深巷找。

> **Rust 陷阱 · `pub mod` / `pub use` 对照你熟悉的语言**：
> | Rust | Python 类比 | 作用 |
> |---|---|---|
> | `pub mod table;` | 目录里有 `table.py` | 声明模块存在 |
> | `pub use table::Table;` | `__init__.py` 里 `from .table import Table` | 把深层符号提到包顶层，外部少写一截路径 |

### 4.2 三件核心抽象，先混个脸熟

后面几篇会反复出现这三个名字，这里先建立关系（详见 **09 Table 解剖·上**）：

| 抽象 | 源码位置 | 比喻 | 一句话 |
|---|---|---|---|
| `Database`（trait） | `database.rs:151` | 图书馆的"书库总管" | 管表：建表 / 开表 / 改名 / 删表，返回 `Arc<dyn BaseTable>` |
| `BaseTable`（trait） | `table.rs:408` | **用工合同** | 规定"一张表必须会做哪些事"（`schema` / `count_rows` / `query` …） |
| `Table`（struct） | `table.rs:500` | **服务员** | 用户手里的门面，自己不干活，把请求转给后厨 |

两种"后厨"都签了 `BaseTable` 这份合同：本地的 `NativeTable`（`table.rs:1178`）和云端的 `RemoteTable`。运行时靠 `as_any().downcast_ref::<NativeTable>()` 区分（`table.rs:1170-1172`）。守着底层 lance `Dataset` 的"金库保安"是 `DatasetConsistencyWrapper`（`table/dataset.rs:19`，本质 `Arc<RwLock<DatasetRef>>`）。

看一眼 `Database` 合同的真身（`database.rs:151-167`）：

```rust
pub trait Database:
    Send + Sync + std::any::Any + std::fmt::Debug + std::fmt::Display + 'static  // ① 一串"通行证"约束
{
    async fn table_names(&self, request: TableNamesRequest) -> Result<Vec<String>>;        // 列表
    async fn create_table(&self, request: CreateTableRequest) -> Result<Arc<dyn BaseTable>>; // ② 返回"合同对象"
    async fn open_table(&self, request: OpenTableRequest) -> Result<Arc<dyn BaseTable>>;
    async fn rename_table(&self, old_name: &str, new_name: &str) -> Result<()>;
    async fn drop_table(&self, name: &str) -> Result<()>;
    async fn drop_all_tables(&self) -> Result<()>;
    fn as_any(&self) -> &dyn std::any::Any;                                                 // ③ 给向下转型用
}
```

> **Rust 陷阱 · `Send + Sync + 'static`（`database.rs:152`）**：这是给"跨线程异步"用的保证书。`Send` = 可以安全地在线程间移动，`Sync` = 可以安全地被多线程共享引用，`'static` = 不借用任何临时数据。Python / JS 因为 GIL / 单线程帮你免了这层心智负担，Rust 则把它写进编译器强制。

> **Rust 陷阱 · `Arc<dyn BaseTable>`（贯穿全篇）**：`dyn` = 运行时多态（类似 Java 接口 / Python 鸭子类型），`Arc` = 原子引用计数的多所有者智能指针。合起来 = 一个"可多处持有、运行时分派的表对象"。比喻：`Arc` 像印了多张遥控器，都能控同一台电视；电视只有一台，遥控器发完了（计数归零）电视才关。

> **Rust 陷阱 · `as_any()` + `downcast_ref`（`table.rs:1170-1172`）**：Rust 没有 `isinstance`。要把 `&dyn BaseTable` 向下转成具体的 `&NativeTable`，必须先 `as &dyn Any` 再 `downcast_ref`，返回 `Option`（因为可能根本不是那个类型）。对应 Python 的 `isinstance(x, NativeTable)` 后再 cast。

> **Rust 陷阱 · `async fn` in trait（`database.rs:155` 等）**：trait 里的 `async fn` 返回的是一个 `Future`，调用处必须 `.await`。较老的 Rust 对此支持有限，所以本 crate 依赖 `async-trait`（`rust/lancedb/Cargo.toml:43`）这个宏，把 `async` 方法脱糖成"返回 `Box<dyn Future>`"。比喻：`#[async_trait]` 是让接口方法能 `async` 的胶水。

## 5. 一个请求的粗略链路预览

把库级文档里的示例（`lib.rs:40-191`）串成一条线，看一个典型工作流怎么穿过这些模块。**这里只画"经过哪些门"，不展开门后的逻辑（留给 Part1 及后续篇）**：

```
① connect("data/...")           lib.rs:43 / connect = lib.rs:292
        │  ConnectBuilder (点菜单)  connection.rs:633
        ▼  .execute().await
   Connection  connection.rs:455    ← 握住一个 Arc<dyn Database>
        │
② db.create_table("t", batches)  lib.rs:116
        │  CreateTableBuilder<true> (有数据版点菜单)  connection.rs:92
        ▼  .execute().await        → Database::create_table  database.rs:157
   Arc<dyn BaseTable>              ← 落地成 NativeTable  table.rs:1178
        │
③ table.add(batch).execute()     (向已有表追加数据)
        ▼  Table(服务员) 转发给 BaseTable(合同)  table.rs:500 / 408
④ table.create_index(&["vector"], Index::Auto)  lib.rs:142
        ▼  index 模块  index.rs:23 (enum Index, 含 Auto)
⑤ table.query().nearest_to(&[1.0; 128]).execute()  lib.rs:180-188
        ▼  query 模块: Query → nearest_to → VectorQuery
          query.rs:680 / 734 / 852
        ▼  最终编译成 DataFusion 的 ExecutionPlan,交给基石层执行
```

几个值得记住的链路要点：

- **几乎每一步都是"先建 Builder，再 `.execute().await`"**（`connect` / `create_table` / `add` / `create_index` / `query` 全都是这个节奏）。这就是"点菜单"模式：链式勾选项 → `.execute()` 才真正下单。
- `create_table` 有两个版本，靠 `CreateTableBuilder<const HAS_DATA: bool>`（`connection.rs:92`）在**类型层面**区分"有没有给数据"。

> **Rust 陷阱 · const 泛型 `CreateTableBuilder<const HAS_DATA: bool>`（`connection.rs:92`）**：Rust 允许用一个编译期布尔值生成两个不同的类型——`CreateTableBuilder<true>`（已带数据，`connection.rs:103`）和 `CreateTableBuilder<false>`（空表，`connection.rs:189`）。这样编译器就能强制"该走哪条路"，而不是等到运行时才 `if` 检查。Python/JS 只能运行时判断，Rust 把它提前到编译期。

> **点菜单（比喻）**：`connection.rs` 里一串 Builder（`ConnectBuilder` `:633` / `CreateTableBuilder` `:92` / `OpenTableBuilder` `:353`）都是点菜单，链式勾选项后 `.execute()` 才真正下单。

完整的入口链路会在 **Part1** 逐行展开，这里只要先有"请求是怎么流动的"这张地图即可。
