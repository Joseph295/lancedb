## 0. 本篇要回答的问题

读到这里，你已经吃透了核心引擎的森林与树木。但「看懂」和「能改」之间还隔着一条河：

1. 我电脑上怎么把这堆 Rust + Python + Node 的混合体**跑起来、编出来、测过去**？
2. 我改了核心库 `rust/lancedb` 的一个函数签名，**到底还要动哪些文件**才能让三端不报错？
3. CI 那一排红绿灯各自在查什么？我**本地怎么先把它们点绿**，避免提交后被打回？
4. PR 标题、commit、测试、文档——哪些是**硬性会卡住合并**的规矩？

> **比喻锚点**：贡献一次代码，像往一座**已经营业的餐厅**加一道新菜。后厨（`rust/lancedb` 核心）是真正掌勺的；前厅有两位**同声传译**（pyo3 译给 Python 客人、napi-rs 译给 JS 客人，见 17 篇）。你改了后厨的菜谱（核心 API 签名），两位译员的稿子（`python/src` / `nodejs/src` 的 `.rs`）**必须同步重写**，否则连「编译」这一关——相当于餐厅开门前的试营业——都过不去。这一篇就是带你走完「领工牌 → 进后厨 → 改菜谱 → 让三位传译对齐 → 通过卫生检查（CI）→ 上菜（PR）」的全套流程。

一张「贡献者视角」的全景图：

```
 ① fork+clone+upstream          ② 挑 good first issue 并认领
        │                                │
        ▼                                ▼
 ┌────────────────────────────────────────────────┐
 │  你的工作区  (一个 monorepo)                       │
 │                                                  │
 │   rust/lancedb   ← 核心 / 唯一真理源 (后厨)         │
 │      │  use lancedb::...                          │
 │      ├──────────────┬───────────────┐            │
 │      ▼              ▼               ▼            │
 │  python/src/*.rs  nodejs/src/*.rs  java/...      │
 │  (pyo3 同传)       (napi 同传)       (jni)         │
 │      │              │                            │
 │      ▼              ▼                            │
 │  python/lancedb   nodejs/lancedb                 │
 │  (Python API)     (TS API)                       │
 └──────────────────────────┬───────────────────────┘
        │  ③ 本地 build/test/lint
        ▼
 ④ conventional commit + 写测试 + 更新 docs
        │
        ▼
 ⑤ 推到 fork → 开 PR → 三套 CI 亮灯 → review → merge
```

记住这张图的一个铁律（本篇 §6 会逐文件展开）：**`rust/lancedb` 是唯一真理源，所有绑定都 `use lancedb::...` 调它**。改了核心，编译器会从核心一路「红」到每个绑定，逼你把每位传译的稿子都对齐。

## 1. 开发环境搭建

### 1.1 fork / clone / upstream

第一步永远是 fork 出自己的副本，再把官方仓库挂成 `upstream`。`CONTRIBUTING.md:20-32` 给的就是这四条：

```bash
# CONTRIBUTING.md:22-25 —— clone 你自己 fork 出来的副本
git clone https://github.com/<username>/lancedb.git
cd lancedb

# CONTRIBUTING.md:29-32 —— 把官方仓库挂为 upstream，方便日后同步主干
git remote add upstream https://github.com/lancedb/lancedb.git
git fetch upstream
```

> **为什么要 upstream？** 你的 `origin` 指向自己的 fork（你有写权限、PR 从这里推）；`upstream` 指向官方（你只读、用来同步别人合进去的新代码）。日常节奏是：从 `upstream/main` 拉最新 → 在自己分支上干活 → 推到 `origin` → 开 PR 回 `upstream`。

### 1.2 三端共同的前置依赖

无论你最终改哪一端，有两样东西**三端都要装**（`python/CONTRIBUTING.md:19-21`、`nodejs/CONTRIBUTING.md:21-23`）：

| 依赖 | 作用 | 安装方式 |
|---|---|---|
| **Cargo**（Rust 工具链） | 编译核心库与所有 `.rs` 绑定 | 用 [rustup](https://rustup.rs/) 安装 |
| **protoc**（Protocol Buffers 编译器） | 编译 lance/lancedb 用到的 `.proto` 定义 | 见 grpc.io 的 protoc 安装文档 |

**Rust 版本有两个数字，别搞混**：

- `rust-toolchain.toml:2` 把开发用工具链 pin 在 `channel = "1.83.0"`。你 `cd` 进仓库后，rustup 会**自动切换**到 1.83.0——这是「开发时用哪个编译器」。
- `Cargo.toml:21` 的 `rust-version = "1.78.0"` 是 **MSRV**（Minimum Supported Rust Version，最低支持版本），是「发布给用户时承诺能编译的最低门槛」。CI 有专门的 msrv job 用 1.78.0 跑 `cargo check`（`rust.yml:187-223`，`matrix.msrv: ["1.78.0"]` 见 `:193`），防止你不小心用了 1.78 还没有的新语法。

> **Rust 知识点：两个版本号的分工**。`rust-toolchain.toml` 是给 rustup 看的「本仓库默认编译器」；`rust-version` 是写进 crate 元数据的「兼容下限」。前者越新越好（开发体验），后者越旧越好（用户覆盖面）。两者并不矛盾——日常用 1.83，CI 额外拿 1.78 验一遍「向下兼容」。

### 1.3 各语言的运行时

按你要改的目标补装：

| 端 | 额外运行时 | 出处 |
|---|---|---|
| **Python** | Python **3.9+** | `python/CONTRIBUTING.md:19` |
| **Node** | 文档写 Node.js 14+（`nodejs/CONTRIBUTING.md:21`），但 **实际要求 `node >= 18`** | `nodejs/package.json:68-70` 的 `engines`；CI 测 node 18/20 |

> **注意文档与现实的一处出入**：`nodejs/CONTRIBUTING.md:21` 写「Node.js 14 or later」，但 `nodejs/package.json:69` 的 `engines` 明确是 `"node": ">= 18"`，CI 也只在 18/20 上跑。**以 18+ 为准**——这正是给贡献者顺手修一行文档的 good-first-issue（见 §7）。

Python 与 Node 各自的开发环境：

```bash
# Python: python/CONTRIBUTING.md:25-29 —— 建虚拟环境并装 maturin
python -m venv venv
source venv/bin/activate
pip install maturin          # maturin 负责把 Rust 绑定编译成 Python 扩展

# Node: nodejs/CONTRIBUTING.md:27-29 —— 一条命令搞定
npm install
```

## 2. 仓库工作区结构回顾（呼应 00）

LanceDB 是一个 **Rust 核心 + 多语言绑定的 monorepo**。权威结构说明在 `CONTRIBUTING.md:64-74`：

```
仓库根
├── rust/lancedb/   ← 核心库 (Rust)。CONTRIBUTING.md:69 称之 "src/lancedb"
├── rust/ffi/node/  ← 旧的 node FFI crate
├── python/         ← Python 包 (CONTRIBUTING.md:70)
│   ├── src/             ← Rust 绑定源码 (pyo3)          python/CONTRIBUTING.md:11
│   └── python/lancedb/  ← Python 包源码                  python/CONTRIBUTING.md:12
│   └── python/tests/    ← 单测 (实际路径，见 §4)
├── nodejs/         ← TypeScript 包 (CONTRIBUTING.md:71)
│   ├── src/             ← Rust 绑定源码 (napi-rs)         nodejs/CONTRIBUTING.md:12
│   ├── lancedb/         ← TS 包源码                       nodejs/CONTRIBUTING.md:13
│   └── __test__/        ← 单测                            nodejs/CONTRIBUTING.md:14
├── node/           ← **已废弃**的旧 TS 包 (CONTRIBUTING.md:72)
├── java/           ← Java 包 (CONTRIBUTING.md:73)
└── docs/           ← 文档 (CONTRIBUTING.md:74)
```

`CONTRIBUTING.md:66-67` 一句话点破整座大楼的承重墙：

> The core library is written in Rust. The Python, Typescript, and Java libraries are wrappers around the Rust library.

### 2.1 Cargo workspace 成员（含一个悖论）

`Cargo.toml:1-11`：

```toml
[workspace]
members = [
    "rust/ffi/node",        # 旧 node ffi
    "rust/lancedb",         # ★ 核心库
    "nodejs",               # napi 绑定 crate
    "python",               # pyo3 绑定 crate
    "java/core/lancedb-jni",# jni 绑定
]
# Python package needs to be built by maturin.   ← Cargo.toml:9 的注释
exclude = ["python"]        # Cargo.toml:10：又把 python 排除！
resolver = "2"              # Cargo.toml:11
```

> **「python 既是成员又被 exclude」的悖论**：`members`（:6）列了 `python`，`exclude`（:10）又把它排掉。原因写在 `:9` 的注释里——**Python 包必须由 maturin 构建**，不能走普通 `cargo build`。所以列进 `members` 是为了让 workspace 元数据完整、IDE 能识别，`exclude` 则是告诉 `cargo build --workspace` 别去普通编译它。这正解释了为什么 Python 端用 `maturin develop`（`make develop`）而不是 `cargo`。
>
> **比喻**：Cargo workspace 是一栋楼里的多个工位——`rust/lancedb` 是中央厨房（后厨），`nodejs`/`python` 是两个对外窗口。但 Python 这个工位特殊，它不烧楼里的中央灶（cargo），而是**自带一台 maturin 烤箱**，所以在花名册（workspace 编译列表）上被划掉。

### 2.2 绑定确实「调」核心库（编译期的硬依赖证据）

不是口头说说——两端绑定的 `.rs` 文件第一行 import 就 `use lancedb::...`：

```rust
// nodejs/src/table.rs:7-9
use lancedb::ipc::ipc_file_to_batches;
use lancedb::table::{
    AddDataMode, ColumnAlteration as LanceColumnAlteration, Duration, NewColumnTransform,
    OptimizeAction, OptimizeOptions, Table as LanceDbTable,
};

// python/src/table.rs:10-13
use lancedb::table::{
    AddDataMode, ColumnAlteration, Duration, NewColumnTransform, OptimizeAction, OptimizeOptions,
    Table as LanceDbTable,
};
```

两端都从**同一个** `lancedb` crate 里 import 同一批类型。**这就是 §6「改核心必须同步绑定」的物理基础**：改了 `lancedb::table::Table` 的方法签名，这两个文件会立刻编译失败。

## 3. build / test / lint：三端命令大全

三端工具链各不相同，先记住这张对照表（后面逐端展开）：

| 维度 | Rust 核心 | Python | Node |
|---|---|---|---|
| 构建 | `cargo build` | `maturin develop`（= `make develop`） | `npm run build`（含 `napi build`） |
| 格式化 | `cargo fmt` | `ruff format` | `biome format` |
| Lint | `cargo clippy` | `ruff check` | `biome check` |
| 类型检查 | （编译器自带） | `pyright` | `tsc` |
| 测试 | `cargo test` | `pytest` | `jest`（`npm test`） |
| 测试目录 | 源文件内联 `mod tests` | `python/python/tests/` | `nodejs/__test__/` |

### 3.1 Rust 核心：cargo build / test / clippy / fmt

下列命令都取自 CI 的真实步骤，本地照跑即可提前点绿对应红绿灯：

```bash
# 格式检查 (rust.yml:51)：--check 只检查不改，不合规则报错
cargo fmt --all -- --check

# Lint (rust.yml:53)：-D warnings 把所有警告升级成错误 —— clippy 不让你带任何警告过关
cargo clippy --workspace --tests --all-features -- -D warnings

# 测试 (rust.yml:123)：--locked 强制用 Cargo.lock 锁定的精确依赖版本，保证可复现
cargo test --all-features --locked

# 改了依赖后的全量构建验证 (rust.yml:80)
cargo build --benches --all-features --tests

# MSRV 检查 (rust.yml:223)：CI 会用 1.78.0 跑这条，确保没用新语法
cargo check --workspace --tests --benches --all-features
```

> **Rust 陷阱：`--all-features` / `--locked`**。Cargo 的 feature 是**编译期开关**（`Cargo.toml` 的 `[features]` 段定义可选依赖，如 `openai`、`polars`、`remote`）。`--all-features` 一次打开全部，确保所有可选代码路径都被编译；`--locked` 则锁死依赖版本，让 CI 与你本地编出来的二进制一致。Python 的 extras（下面 `--extras tests,dev,embeddings`）概念类似，但那是**运行时**依赖，不是编译期开关。

### 3.2 Python：maturin + Makefile

Python 端几乎所有命令都封装进 `python/Makefile`，从仓库根目录的 `python/` 子目录里跑：

```bash
make develop    # Makefile:8  = maturin develop --extras tests,dev,embeddings
                #              用 maturin 编译 Rust 绑定，并把包装成「可编辑安装」(editable)
make format     # Makefile:11-13 = cargo fmt + ruff format python
make check      # Makefile:16-19 = cargo fmt --check + ruff format --check + cargo clippy + ruff check python
make test       # Makefile:36 = pytest python/tests -vv --durations=10 -m "not slow and not s3_test"
make typecheck  # Makefile:28 = pyright
make doctest    # Makefile:32 = pytest --doctest-modules python/lancedb
```

注意 `make check`（`Makefile:16-19`）**同时跑 Rust 和 Python 两套检查**——因为 Python 包里既有 `src/*.rs`（要 `cargo fmt`/`clippy`）又有 `python/lancedb/*.py`（要 `ruff`）。

CI 里 ruff 的版本是**钉死的**（`python.yml:40-45`），本地最好对齐以免格式判定不一致：

```bash
pip install ruff==0.9.9      # python.yml 固定版本
ruff format --check .
ruff check .
```

> **为什么 Python 用 `maturin develop` 而不是 `cargo build`？** 回到 §2.1 的悖论：Python 包被 workspace `exclude`，普通 cargo 不会构建它。maturin 才知道如何把 `python/src/*.rs`（pyo3 绑定）编成 `.so`/`.pyd` 扩展，再让 `python/python/lancedb` 这个纯 Python 层 import 它。**改了 `python/src/*.rs` 后，必须重跑 `make develop` 才能让改动生效**，否则你 import 的还是旧扩展。

### 3.3 Node：napi-rs + npm scripts

```bash
npm install
npm run build      # package.json:77 = build:debug + tsc + 把 .node 拷进 dist/
npm run lint       # package.json:84 = biome check . && biome format .
npm run lint-fix   # package.json:85 = biome check --write . && biome format --write .
npm test           # package.json:87 = jest --verbose
```

`npm run build` 的核心是 `build:debug`（`package.json:75`），它调 `napi build`：

```bash
# package.json:75
napi build --platform --no-const-enum --dts ../lancedb/native.d.ts --js ../lancedb/native.js lancedb
# 产物：① 原生二进制 *.node ② 给 TS 用的类型声明 native.d.ts ③ JS 胶水 native.js
```

> **关键：`native.d.ts` 是自动生成的**。`napi build` 会根据 `nodejs/src/*.rs` 里 `#[napi]` 标注的函数，**自动生成** `../lancedb/native.d.ts` 类型声明。所以你在 Rust 绑定里改了签名，重跑 `npm run build` 才会刷新这份 `.d.ts`，TS 层才看得到新签名（呼应 17 篇讲的「napi 自动生成 d.ts」）。

Node 的 lint CI 步骤**也包含 Rust 端**（`nodejs.yml:51-58`），因为 `nodejs/` 下既有 TS 又有 `src/*.rs`：

```bash
# nodejs.yml:52-58
cargo fmt --all -- --check
cargo clippy --all --all-features -- -D warnings
npm ci
npm run lint-ci        # package.json:81 = biome ci .
```

还有一个**容易踩的坑**——文档需手动重新生成并提交（`nodejs.yml:115-120`）：

```bash
npm run docs   # package.json:82 = typedoc 生成 ../docs/src/js
# CI 随后跑 git diff --exit-code；若你改了公共 API 却没重生成文档，diff 非空 → CI 红
```

## 4. 测试惯例

### 4.1 Rust：单测内联在源文件底部

和 Python/JS「单独测试目录」不同，**Rust 单测直接写在被测源文件的底部**，包在一个 `#[cfg(test)] mod tests` 里。`rust/lancedb/src/table.rs:2435-2467` 就是标准范式：

```rust
#[cfg(test)]                       // table.rs:2435 —— 条件编译：只有 cargo test 时才编译这一段
#[allow(deprecated)]               // table.rs:2436
mod tests {
    use std::sync::Arc;
    // ……
    use tempfile::tempdir;         // table.rs:2457 —— dev-dependency，建临时目录
    use super::*;                  // table.rs:2459 —— 把父模块（被测项）全导进来

    #[tokio::test]                 // table.rs:2465 —— 异步测试宏，自动起 tokio runtime
    async fn test_open() {
        let tmp_dir = tempdir().unwrap();              // table.rs:2467 —— 建临时目录，测完自动清理
        let dataset_path = tmp_dir.path().join("test.lance");
        // ……用 NativeTable::open(...) 打开，再 assert_eq!
    }
}
```

同样的 `#[cfg(test)] mod tests` 模式遍布核心库（`connection.rs`、`query.rs`、`arrow.rs` 等都有），异步测试**统一**用 `#[tokio::test]`。

> **Rust 陷阱：`#[cfg(test)]` 是编译期开关**。这是「条件编译属性」——只有 `cargo test` 时才把 `mod tests` 编进去，正常 `cargo build`（release 产物）**根本不含这段测试代码和 `tempfile` 这类 dev-dependency**。Python/JS 没有这种「测试代码不进产物」的编译期开关。
>
> **比喻**：`#[cfg(test)]` 是餐厅的**员工通道**——测试代码和临时餐具（tempfile）只在「试营业」（`cargo test`）时存在；正式对客出餐（release build）时，这扇门压根不编进大楼。

> **Rust 陷阱：`#[tokio::test]`**。lancedb 核心是全异步的，方法签名几乎都是 `async fn`，结果要 `.await`。但 Rust 的 `async fn` **必须在一个运行时（runtime）上 `.await`**，不能像 JS 那样裸调。`#[tokio::test]` 替代普通 `#[test]`，自动起一个 tokio runtime 来跑你的 `async fn`，所以你才看到几乎每个测试都带它。

### 4.2 只跑一个测试

```bash
# Rust：按测试函数名过滤（cargo test 后接子串）
cargo test test_open

# Python (python/CONTRIBUTING.md:74-77)：
pytest -vv python/tests/test_table.py            # 单文件
pytest -vv python/tests/test_table.py::test_basic # 单个测试

# Node (nodejs/CONTRIBUTING.md:72-75)：
npm test -- table.test.ts                                    # 单文件
npm test -- table.test.ts --testNamePattern=merge\ insert    # 单个测试
```

> **一处文档/现实出入（已实证）**：`python/CONTRIBUTING.md:75` 和 `Makefile:36` 写的路径是 `python/tests`，但**从仓库根目录运行时，真实路径是 `python/python/tests/`**（已 `ls` 验证 `python/python/tests/test_table.py` 存在；CI 的 run_tests action 用的就是 `python/python/tests`）。文档里的 `python/tests` 是「相对于 `working-directory=python` 的简写」。读者在根目录直接跑 pytest 时，要写双层 `python/python/tests`。

### 4.3 「无测试不合并」是硬规矩

`CONTRIBUTING.md:48-49` 明文：

> Unit test all bug fixes and new features. Your code will not be merged if it doesn't have tests.

并且 `CONTRIBUTING.md:61-62` 还要求**测错误路径**：写测试时要覆盖出错的情况，并确保错误信息可读。

这些惯例你在前面 17 篇里已多次遇到，这里汇总成「贡献时照着写」的清单：

### 5.1 License header 强制检查

每个源文件**开头必须有两行 SPDX**，否则 `license-header-check.yml:24-31` 的 CI 直接红。模板（`rust/license_header.txt:1-2`，Rust/TS 用 `//`、Python 用 `#`）：

```rust
// SPDX-License-Identifier: Apache-2.0
// SPDX-FileCopyrightText: Copyright The LanceDB Authors
```

实证：`rust/lancedb/src/lib.rs:1-2`、`nodejs/src/table.rs:1-2`、`python/src/table.rs:1-2`、`python/python/lancedb/__init__.py:1-2` 全是这两行（Python 版用 `#` 前缀）。**新建文件时第一件事就是粘这两行**。

### 5.2 三端 lint 工具各不相同

| 端 | 格式化 | Lint | 严格度 |
|---|---|---|---|
| Rust | `rustfmt`（`cargo fmt`） | `clippy` | CI 用 `-D warnings`，**任何警告即失败** |
| Python | `ruff format` | `ruff check` | 版本钉死 `ruff==0.9.9`（`python.yml:40`） |
| Node | `biome format` | `biome check` | config 在 `nodejs/biome.json` |

pre-commit 钩子（`.pre-commit-config.yaml`）会在你 `git commit` 前**自动**跑这些：对 Python 用 ruff（rev `v0.9.9`），对 `nodejs/` 用 biome（`@biomejs/biome@1.8.3`），外加 check-yaml / end-of-file-fixer / trailing-whitespace 通用钩子。安装方式见 `python/CONTRIBUTING.md:36-39`（`make develop` 装 pre-commit 本体，再 `pre-commit install`）与 `nodejs/CONTRIBUTING.md:36-38`。

## 6. 改一处核心的完整流程（呼应 17）

这是本篇的**机制核心**。假设你要给 `BaseTable` 加一个方法——比如 `count_deleted_rows()`。「唯一真理源」原则（§2.2）意味着改动会沿一条固定路径**传染**到三端。

### 6.1 改动会编译失败的「红色传染链」

```
① rust/lancedb/src/table.rs
   - BaseTable trait 加方法签名 (呼应 09 §1：合同新增一条职责)
   - impl BaseTable for NativeTable 补实现 (table.rs:1886+，本地后厨兑现)
   - impl BaseTable for RemoteTable 补实现 (remote/，云端后厨兑现，呼应 15)
   - Table 门面加转发方法 (table.rs:499+，服务员加一句传话)
        │  ← 到此核心库自洽，cargo build 能过
        ▼  但绑定 crate 仍 use lancedb::...，若它们也要暴露新方法：
② python/src/table.rs   —— 加 #[pymethods] 方法，调 self.inner.count_deleted_rows()
③ nodejs/src/table.rs   —— 加 #[napi] 方法，同样转发
        │
        ▼  上层语言 API 再封一层：
④ python/python/lancedb/table.py   —— Python 侧 Table 暴露给用户
⑤ nodejs/lancedb/table.ts          —— TS 侧 Table 暴露给用户
        │
        ▼  类型声明 / 文档：
⑥ python 的 .pyi 存根（若有） / nodejs 的 native.d.ts (自动生成，npm run build 刷新)
⑦ 各端补测试 + nodejs 跑 npm run docs 重生成 typedoc
```

### 6.2 为什么「编译失败」是好事

这正是 Rust + 「唯一真理源」的红利：**你不可能偷偷漏掉某一端**。改了 `BaseTable` 的方法签名后：

- `rust/lancedb` 内部，`NativeTable`/`RemoteTable` 若没补实现 → **trait 没实现完整，编译失败**。
- `python/src/table.rs`、`nodejs/src/table.rs` 若调用了变化的签名 → **类型不匹配，编译失败**。

编译器像一条警报链，从核心一路响到每个绑定，逼你把每位「同声传译」的稿子都对齐。**对照动态语言**：在纯 Python/JS 项目里改个函数签名，漏改的调用点要等运行时才炸；这里编译期就全抓出来了。

> **比喻**：核心库（Rust）讲的是「母语」，pyo3 和 napi-rs 是两位同传译员，把同一句话（同一个函数签名）分别翻成 Python 和 JS。改了原话（核心 API），两位译员的稿子（`python/src`、`nodejs/src` 的 `.rs`）都得跟着改——**否则编译这一关就过不去**。

### 6.3 别忘了 CI 的 paths 过滤

三个 workflow 各自**只在对应目录变更时触发**：

| workflow | 触发条件（paths） |
|---|---|
| `rust.yml:8-11` | 改 `Cargo.toml` / `rust/**` / `rust.yml` |
| `python.yml:8-10` | 改 `python/**` |
| `nodejs.yml:8-12` | 改 `nodejs/**` |

> **实务含义（容易翻车）**：如果你只改了 `rust/`（核心）却**没动** `python/`、`nodejs/`，那么 python/nodejs 的 CI **不会自动跑**，绑定是否还编得过就没人验。所以「改核心 + 同步绑定」的 PR，要确保**三个目录都有改动**，三套 CI 才会全亮——这恰好和 §6.1 的红色传染链一致：真要对外暴露新方法，本来就该三端都动。
>
> **比喻**：CI 的 paths 过滤像**分区报警器**——只动了厨房（`rust/`）就只响厨房的警报，不会惊动前厅（python/nodejs）的检查。想让三处警报都响，提交时三个区域都得动到。

## 7. 找 good-first-issue 的思路

`CONTRIBUTING.md:11-16` 给的官方入口：去 [good first issue](https://github.com/lancedb/lancedb/contribute) 标签挑 issue，**先在 issue 下留言认领**，避免和别人重复劳动。

但更高阶的玩法是**从代码本身嗅出待办**。前面 09 §3.4 已经示范过一个经典信号——`table.rs` 里 `BadVectorHandling` 的多数变体标了 `#[allow(dead_code)]` 并指向 issue #992，那就是「挖了坑还没填」的功能。通用嗅探套路：

| 线索 | 含义 | 怎么搜 |
|---|---|---|
| `#[allow(dead_code)]` + 注释指向 issue | 占位功能，半成品 | `grep -rn 'allow(dead_code)' rust/lancedb/src` |
| `// TODO` / `// FIXME` | 作者自己标的待办 | `grep -rn 'TODO\|FIXME' rust/lancedb/src` |
| 「临时 API，将来移除」类注释 | 技术债，可能有重构 issue | 如 09 §2.4 提到的 `as_native` |
| 文档与现实不一致 | 低风险文档修复（最适合第一个 PR） | 如本篇 §1.3 的 node 14 vs 18、§4.2 的 `python/tests` 路径 |

> **给新人的建议**：你的**第一个 PR 最好小而无争议**——修一行过时文档、补一个缺失的 license header、给一个 `unwrap` 加更友好的错误信息（呼应 `CONTRIBUTING.md:61-62` 要求测错误路径）。先把「fork→改→测→PR→CI 绿→合并」这条流水线走通一遍，再去碰核心逻辑。

## 8. 提交 PR 的规范

### 8.1 Conventional Commits 是**机器强制**的

`CONTRIBUTING.md:55-58` 要求 PR 标题用 conventional commit 前缀：

```
feat: adding foo API          # 新功能
fix: issue with foo API       # bug 修复
docs: adding foo API documentation # 文档
```

这不只是约定——`dev.yml:21-48` 有一个 **commitlint job**，用 `@commitlint/config-conventional` 校验 PR 的标题与描述，**失败会自动评论提示**（`dev.yml:49-81`）。

> **比喻**：conventional commit 前缀 = **快递面单的分类码**。`feat`/`fix`/`docs` 不是给人看的客套话，而是机器（semantic-release）据此自动决定**版本号涨幅**、自动生成 changelog 的扫描码。贴错码，CI 直接退件。因为 PR 标题会成为 squash merge 的 commit message，进而驱动版本号——**前缀写错会直接 CI 失败**。

### 8.2 PR 最佳实践清单（`CONTRIBUTING.md:44-62`）

1. **所有 bugfix/feature 必须带测试**，否则不合并（:48-49）。
2. **改了公共 API 要更新 `docs/`**（:50）。
3. **每个 PR 尽量只解决一个问题**，控制改动量（:51-52）。
4. 提交 review 前**先自审**，确保改动意图清晰（:53-54）。
5. PR 标题用 **conventional commit**（:55-58）。
6. WIP 用 **draft PR**；非 draft 即视为 ready-for-review（:59-60）。
7. **测错误路径**，错误信息要可读（:61-62）。

### 8.3 提交前自检清单（把 CI 提前点绿）

```bash
# —— 改了 rust/lancedb 核心 ——
cargo fmt --all -- --check
cargo clippy --workspace --tests --all-features -- -D warnings
cargo test --all-features --locked

# —— 改了 python/ ——
cd python && make check && make test && make typecheck

# —— 改了 nodejs/ ——
cd nodejs && npm run build && npm run lint && npm test
npm run docs   # 若动了公共 API，重生成文档并提交，否则 nodejs.yml CI 红

# —— 通用 ——
pre-commit run --all-files   # 跑 ruff/biome/license header 等钩子
# PR 标题写成 feat:/fix:/docs: 开头
```

## 9. 本篇出现的 Rust 语法点 · 速查

| 语法 | 一句话 | 出现处 |
|---|---|---|
| `#[cfg(test)]` | 条件编译；只有 `cargo test` 才编译，release 产物不含 | `table.rs:2435` |
| `#[tokio::test]` | 自动起 tokio runtime 跑 `async fn` 测试 | `table.rs:2465` |
| `#[allow(dead_code)]` | 压制「未使用代码」警告；常配 issue 注释标占位功能 | 09 §3.4 / `table.rs:240` 区 |
| `use super::*;` | 测试模块把父模块（被测项）全导进来 | `table.rs:2459` |
| `--all-features` | 编译期打开全部可选依赖 | `rust.yml:53` |
| `--locked` | 锁死 `Cargo.lock` 版本，保证可复现 | `rust.yml:123` |
| `-D warnings`（clippy） | 把所有警告升级成错误 | `rust.yml:53` |
| `use lancedb::...`（绑定里） | 绑定 crate 依赖核心 crate 的编译期硬链接 | `nodejs/src/table.rs:7`、`python/src/table.rs:9` |
| `#[napi]` / `#[napi(catch_unwind)]` | napi-rs 导出函数；catch_unwind 把 panic 转成 JS 异常 | `nodejs/src/table.rs:20,64` |
| `#[pyclass]` / `#[pymethods]` / `#[pyo3(signature=..)]` | pyo3 导出类/方法/默认参数 | `python/src/table.rs:62,69,148` |

> **FFI 异常处理回顾（呼应 17）**：`#[napi(catch_unwind)]`（`nodejs/src/table.rs:64`）—— Rust panic 默认会让线程/进程崩溃，跨 FFI 到 JS 很危险；catch_unwind 把 panic 捕获并转成 JS 端可 `catch` 的异常。这是「同声传译」在异常处理上的体现。
>
> **pyo3 默认参数回顾**：`#[pyo3(signature = (updates, r#where=None))]`（`python/src/table.rs:148`）—— `r#where` 里的 `r#` 是「原始标识符」前缀。`where` 是 Rust 关键字，加 `r#` 才能当普通参数名用，从而映射到 Python 端的 `where` 参数。

## 10. 动手验证

1. **跑通流水线**：fork → clone → `cargo build`（核心）→ `cd python && make develop && make test`。把 §3 的命令逐条跑一遍，确认本地环境健康。
2. **数 workspace 成员**：打开 `Cargo.toml`，对照 §2.1，确认 `python` 既在 `members`（:6）又在 `exclude`（:10），读懂 `:9` 注释解释的悖论。
3. **抓「红色传染链」**：在 `nodejs/src/table.rs` 和 `python/src/table.rs` 顶部搜 `use lancedb::`，确认两端都 import 同一个 crate（§2.2）。想象你把 `lancedb::table::Table` 删一个方法，推演哪些文件会编译失败。
4. **定位一个 good-first-issue 线索**：`grep -rn 'TODO\|allow(dead_code)' rust/lancedb/src`，挑一处读懂上下文；或验证 §1.3、§4.2 两处文档/现实出入，这本身就是可提的文档 PR。
5. **试发一个最小 PR**：建一个 `docs:` 前缀的分支，修一行过时文档，本地 `pre-commit run --all-files` 通过后推到 fork，开 draft PR，观察三套 CI 哪些被触发（§6.3 的 paths 过滤）。

## 11. 小结 & 全套 18 篇文档全景索引

**本篇三句话**：

- **环境**：三端共需 Cargo + protoc；Rust 用 cargo，Python 用 maturin（因被 workspace `exclude`），Node 用 napi-rs；版本 pin 在 1.83（开发）/ MSRV 1.78（兼容下限）。
- **机制**：`rust/lancedb` 是唯一真理源，绑定都 `use lancedb::...`。改核心会沿编译期「红色传染链」逼你同步 `NativeTable`/`RemoteTable`/`Table` 门面 + `python/src` + `nodejs/src` + 上层语言 API + 文档，一处都漏不掉。
